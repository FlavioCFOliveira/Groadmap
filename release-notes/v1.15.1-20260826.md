# Release Notes — Groadmap v1.15.1

**Date:** 2026-08-26
**Type:** Patch by decision — **contains backward-incompatible changes** (see Breaking Changes)
**Tag:** `v1.15.1`
**Previous release:** `v1.15.0` (2026-08-21)

---

## Executive Summary

Groadmap `v1.15.1` is a correctness release, and nothing else. Two sprints —
**90 completed tasks across 87 commits** — land together, and both were governed by
the same exclusive rule: fix the defects Groadmap has today; do not hunt for
features, and do not complete features that were never built. A defect was defined,
and enforced, as a divergence between what the software **does** and what it is
**specified** to do, reproducible against the built binary. Ninety times over, that
test was applied before any code was written.

**The number is `1.15.1` and the release is not backward-compatible.** That is a
deliberate choice by the project owner, recorded here rather than hidden. A strict
reading of Semantic Versioning 2.0.0 would require `MAJOR`, because invocations that
succeeded on `1.15.0` now fail on `1.15.1`. If you drive `rmp` from a script, an
agent, or a CI step, read [Breaking Changes](#breaking-changes) in full before you
upgrade. The version number does not warn you; this document does.

**What actually changed is the CLI's discipline about its own contract.** A stray
positional argument used to be **ignored across the whole CLI** — and on
`task remove` that silence deleted some of the tasks you named and reported success.
Every command now declares its maximum positional count and one shared enforcement
point refuses the excess with exit `2`, before the database is opened. An unknown
subcommand now exits **127**, the code three published surfaces had been promising
for months while the binary returned `2`. A failing invocation now writes **zero
bytes to stdout**, where an unknown command used to print two kilobytes of help
there.

**Free text is validated the same way everywhere, and the order is specified.**
Length cap, then UTF-8 encoding, then control characters, then trim, then
emptiness — one order, seven write paths, eight fields, by flag and on standard
input. Along the way: bytes that are not valid UTF-8 are refused instead of stored;
a leading or trailing vertical tab or form feed no longer slips past the
control-character rule; a whitespace-only title is refused rather than accepted; and
the length caps now count **Unicode code points instead of bytes**, so a 255-character
Japanese title is accepted where it was previously refused at roughly a third of the
documented limit.

**The knowledge graph stops answering the wrong question.** A relationship read
bound by a reverse or undirected pattern returned the **wrong edge** whenever a node
pair carried edges in both directions; a relationship write bound by such a pattern
was silently ignored and reported success. Both are now refused with exit `6`,
before the store is opened, across all five `graph` subcommands and the web query
bar. Graph reads also take a shared advisory lock, because opening the store is not
a read-only operation on disk.

The database schema advances **two migrations, `1.12.0` → `1.14.0`**, applied
automatically and in order on the first command run against an existing roadmap.
They make each sprint's task order **total and dense**, and they repair the gaps
that four write paths had already committed on every installation. See
[Upgrade Notes](#upgrade-notes).

The pre-release vulnerability scan required as step 1 of the release procedure was
run against this tree and reported **`No vulnerabilities found`**.

## Highlights

- **BREAKING — a stray positional argument is refused across the whole CLI.** Every
  command declares its maximum positional count and one shared enforcement point,
  reached by construction from that declaration, refuses the excess with exit `2`
  and `Error: invalid input: unexpected argument "X"`, before the store is opened.
  The destructive instance it closes: `rmp task remove 2 3` used to delete task `2`,
  discard the `3`, and exit `0`.
- **BREAKING — an unresolved subcommand exits `127`, not `2`.** The binary moved to
  the contract, which two tables in `SPEC/ARCHITECTURE.md` and the machine-readable
  AI contract had published all along. Six dispatching families are affected, and
  all six now list `127` in their help.
- **BREAKING — a failing invocation writes nothing to stdout.** An unknown command
  used to write 2091 bytes of general help there, with the AI-agent hint appearing
  once per channel in a single invocation.
- **BREAKING — free text that is not valid UTF-8 is refused, not stored.** Eight
  fields, both input paths, exit `6`. Knowledge-graph property values are covered by
  the same rule, on all five `graph` subcommands, because an invalid byte used to be
  silently replaced with U+FFFD and the store then held something nobody wrote.
- **BREAKING — a leading or trailing VT or FF no longer evades the control-character
  rule**, and a whitespace-only value in a required free-text field is refused rather
  than accepted. Stored values are trimmed.
- **BREAKING — reverse and undirected relationship patterns are refused in the graph
  family.** A read through such a pattern reported the wrong edge; a write through
  one was silently discarded and reported success. Five subcommands and the web query
  bar, exit `6` and HTTP `400` respectively.
- **BREAKING — dozens of error messages were rewritten.** One rule, one sentence:
  priority, severity, `--limit`, entity ids, `--max-tasks`, and the position bound
  converge on `<field> must be between <lo> and <hi>, got N`. Anything matching
  `rmp` stderr by string will need updating.
- **WIDENING — length caps count Unicode code points, not bytes.** 255 four-byte
  emoji, which is 1020 bytes, is now accepted; the SQLite `CHECK` always counted
  characters, so it is the Go layer that stopped dissenting.
- **WIDENING — the audit date filters accept the date-only form** that the
  specification, the AI contract, and the README all published. A bare date means the
  first instant of that day in UTC, which is now specified.
- **The task order of a sprint is total and dense.** `position` is `UNIQUE` within a
  sprint, and every member holds exactly one of `0..N-1`. Two migrations enforce it
  and repair what four write paths had already left behind.
- **Reads of the knowledge graph stop mutating its store.** A read takes a shared
  advisory lock across the store open, because GoGraph's recovery repairs the
  directory a concurrent writer publishes into.
- **`install.sh` verifies the published SHA-256 before extracting**, and stages every
  download in a directory created by `mktemp -d`, closing a time-of-check /
  time-of-use window through which a local user could swap the verified archive.
- **Eleven new end-to-end modules and five new Go packages.** The registered E2E
  suite grows from 51 modules to **62**, and the Go packages from 9 to **14**. Most of
  this release's durable value is in the gates: dozens of the fixes below ship with a
  test that fails if the defect returns, and the non-vacuity of each was proved by
  reintroducing the defect and watching the test go red.

## Breaking Changes

**This release makes invocations that succeeded on `1.15.0` fail on `1.15.1`, and it
changes the text of dozens of error messages.** Every change below was verified by
running the shipped binary; the exit codes and the strings are quoted from that run,
not paraphrased. None has an opt-out, an environment variable, or a compatibility
flag.

The changes fall into three groups: **new refusals** (input that used to be accepted
is now rejected), **changed exit codes and output channels**, and **changed error
text**. A fourth group, **widenings**, is listed after them: those cannot break a
caller, but they change what the binary accepts and belong in the same reading.

### 1. A stray positional argument is refused across the whole CLI

Every command now declares its maximum positional count, and one shared enforcement
point — reached by construction from that declaration, in the only place in the
binary that invokes a subcommand handler — refuses anything beyond it.

| Invocation | On `1.15.0` | On `1.15.1` |
|------------|-------------|-------------|
| `rmp task remove 2 3` | Exit **0**; task `2` deleted, `3` discarded in silence | Exit **2**; **nothing deleted** |
| `rmp roadmap create alpha beta` | Exit 0; `alpha` created, `beta` ignored | Exit **2**; **neither created** |
| `rmp backlog show-next 5 10` | Exit 0; trailing token tolerated | Exit **2** |
| `rmp version check`, `rmp --help sprint` | Exit 0 | Exit **2** |
| `rmp task get 1 2` (arity boundary) | Exit 0 | Exit **2** |

Twenty paths were measured as changing from silently ignored to refused, across the
`task`, `sprint`, `audit`, `backlog`, `roadmap` and `stats` families and the global
forms. The line, verified against the binary:

```
Error: invalid input: unexpected argument "3"
```

**The `graph` family is not new here** and is listed only so that nobody re-tests it:
it already refused a stray token on `1.15.0`, with the contractual hint naming the two
sources a Cypher query may come from, and its line is byte-identical on `1.15.1`:

```
Error: invalid input: unexpected argument "MATCH (n) RETURN n" (graph queries use --query or stdin)
```

**The refusal precedes the store.** `rmp task remove -r <roadmap-that-does-not-exist> 3 4`
exits `2`, not the `4` a missing roadmap gives — which is how the ordering was
established rather than assumed.

**`task remove` is the destructive instance and the reason this rule exists.** Its
specification always said that ids are comma-separated precisely so that a mistyped
list loses no data. The contract was correct and simply unenforced. The comma form
is untouched: `rmp task remove 2,3` still removes both.

`SPEC/COMMANDS.md § Positional Arity by Command` publishes the declared maximum for
every command in the CLI, and a test compares that table against the live registry in
both directions.

### 2. An unresolved subcommand exits `127`, not `2`

| Invocation | On `1.15.0` | On `1.15.1` |
|------------|-------------|-------------|
| `rmp bogus` (unresolved top-level command) | Exit 127 | Exit 127 — **unchanged** |
| `rmp task bogus` | Exit **2** | Exit **127** |
| `rmp sprint bogus`, `rmp backlog bogus`, `rmp audit bogus`, `rmp graph bogus`, `rmp roadmap bogus` | Exit **2** | Exit **127** |
| `rmp task` (a bare family) | Exit 0, help on stdout | Exit 0 — **unchanged** |

The binary moved to the contract, not the contract to the binary: two tables in
`SPEC/ARCHITECTURE.md` and the machine-readable AI contract had published `127` for
this case all along. **The line changes with the exit code**, because the classification
sentinel that mapped the case to `2` went with it:

```
1.15.0: Error: invalid input: unknown task subcommand: bogus
1.15.1: Error: unknown task subcommand: bogus
```

`Error: unknown command: bogus`, for the top-level case, is unchanged.

**One carve-out stays at exit `2` and is documented in two places:** an unrecognised
scope selector on `--ai-help`, where the name selects a contract section rather than
being dispatched.

All five family help screens that were missing it — `task`, `sprint`, `backlog`,
`audit`, `graph` — now list `127` in their Exit codes block, as `roadmap` already
did, and the six corresponding `DOCS/commands/*.md` pages carry the same row.

### 3. A failing invocation writes zero bytes to stdout

On `1.15.0`, `rmp <unknown>` wrote **2091 bytes** of general help to **stdout** on a
failing invocation, prefixed by a second copy of the AI-agent hint, so the hint
appeared once per channel in a single run.

| Invocation | stdout on `1.15.0` | stdout on `1.15.1` |
|------------|--------------------|--------------------|
| `rmp bogus` | **2091 bytes** of help | **0 bytes** (stderr grows from 104 to 2190 bytes) |
| `rmp task bogus` | 0 bytes | 0 bytes (unchanged) |
| `rmp`, `rmp --help` | 2090 bytes | 2090 bytes (unchanged) |

**The stdout leak was confined to the unresolved top-level command**; an unresolved
subcommand already wrote nothing there. The stderr growth is the family help now being
appended after the error, described below.

The invoked family's help now follows the error on **stderr**, which is what
`SPEC/COMMANDS.md` required and `SPEC/HELP.md` contradicted; the contradiction was
resolved in favour of `COMMANDS.md`. The scope is deliberately narrow: only a
dispatch failure — an unresolved command or subcommand name — appends help. A missing
parameter, an unknown flag, a bad enum value, a not-found resource, and a database
error keep the error line and the hint alone.

**A consumer that read a failing invocation's stdout gets an empty stream.** A
consumer that parses stderr sees the family help appended after the error line.

### 4. Free text that is not valid UTF-8 is refused

Eight free-text fields — the four on `task`, the two on `sprint`, the comment body,
and `completion_summary` — refused nothing on `1.15.0` and stored the bytes as
supplied. They now refuse with exit `6`:

```
Error: validation error: title: the value is not valid UTF-8
```

The rule covers both input paths, the flag and standard input, and the bounded
standard-input reader was already carrying raw bytes rather than repairing them to
U+FFFD — a property that is now a stated requirement of its contract rather than an
accident.

**Knowledge-graph property values are covered by the same rule**, and there the
consequence was worse than a stored oddity: the Cypher engine decodes the query to
runes before its grammar runs and replaces every invalid byte with U+FFFD, so the
store held a value nobody wrote and the command reported success. The encoding rule
therefore binds **all five** `graph` subcommands, reads included, because an invalid
byte makes a statement match a literal that was never supplied — a read reports
success having found nothing, and a `DELETE` reports success having removed nothing:

```
Error: validation error: graph create cannot write property "key": the value is not
valid UTF-8. The byte 0xff at offset 19 of the query begins no valid UTF-8 sequence,
and the engine replaces every such byte with U+FFFD before it parses the query, so
the store would hold a value different from the one supplied while the command still
reported success. Supply the query as well-formed UTF-8
```

The **control-character** rule on graph property values deliberately does **not**
extend to reads: it objects to what is stored, and refusing a read that names a
control character would make existing data unreadable rather than merely unwritable.

### 5. A leading or trailing VT or FF no longer evades the control-character rule

`task edit` and the comment layer trimmed the value **before** checking it, and
`strings.TrimSpace` treats U+000B (VT) and U+000C (FF) as whitespace — so a title of
`"\vTitle"` was silently accepted with the VT stripped, and a body consisting only of
a VT was reported as never having arrived. Both are CWE-150 holes and both are closed:

```
Error: validation error: title: control characters are not allowed
```

**Only the leading and trailing positions changed.** An interior VT or FF was already
refused on `1.15.0`, with the identical message; the hole was that `strings.TrimSpace`
ran first and both characters are whitespace to it, so an edge-positioned one was
stripped before the check ever saw it.

Three input-side trims were found, one more than the two that were known, and each
hid the next: `task edit` trimmed while building its updates map; the comment body
resolver judged absence on the normalised value; and behind that, the bounded reader
discarded a forbidden rune it had already recorded.

The change was bounded by measurement rather than by argument. A 655-probe
differential sweep against the previous binary returned 599 identical results, 56
changed, and **zero cases that went from refused to accepted**. The 16
accepted-to-refused are exactly VT and FF at an edge on the four `task edit` fields.

### 6. A whitespace-only value in a required free-text field is refused

`sprint create` accepted a whitespace-only title while `task edit` rejected one. The
rule is now uniform, and **the value that is stored is the trimmed one**:

```
Error: validation error: title cannot be empty
```

Three consequences a caller may notice, all measured against both binaries:

| Invocation | On `1.15.0` | On `1.15.1` |
|------------|-------------|-------------|
| `rmp task create -t "   " ...` | Exit **2**, `Error: required parameter missing: --title` | Exit **6**, `Error: validation error: title cannot be empty` |
| `rmp sprint create -t "   " -d "   "` | Exit **0**; both stored verbatim | Exit **6** |
| `rmp sprint create -t "  Padded Title  " ...` | Stored **with** the padding | Stored as `Padded Title` |

The same exit-code move from `2` to `6` applies to `-fr`, `-tr` and `-ac` on
`task create`. Task fields were already trimmed on storage; the `sprint` pair was not,
which is also why its length cap measured the value as supplied — 255 real characters
surrounded by whitespace were accepted by the `task` commands and refused by the
`sprint` pair. Both now agree.

The whitespace set is Go's `unicode.IsSpace`, which is wider than ASCII: U+00A0 and
U+0085 are covered.

### 7. Reverse and undirected relationship patterns are refused in the graph family

Two defects, one root, both upstream in GoGraph v0.11.0 and both reproduced against
the engine directly with no Groadmap code in the path.

**On the read side**, a relationship variable bound by an incoming or undirected
fixed-length pattern reported the **wrong edge** whenever the node pair carried edges
in both directions: `type(e)` named the wrong relationship, `startNode(e)` and
`endNode(e)` were reversed, and a `WHERE` over either silently dropped the row.
Correction was investigated first and is impossible — the consumer receives a bare
scalar with no relationship identity, and the engine drops the row before anything
reaches Groadmap.

**On the write side**, `SET` and `REMOVE` on a relationship bound by such a pattern
were a **documented no-op** that still reported `PropertiesSet 1`, so the command
exited `0` having written nothing.

Both are now refused with exit `6`, raised **before the store is opened**, across all
five `graph` subcommands, and answered as HTTP `400` with the new kind
`relationship_read_direction` on the web query bar, which builds its own engine and
ran caller-supplied Cypher. The refusal names the direction and gives the rewrite:

```
Error: validation error: graph query cannot read relationship "e": it is bound by an
incoming pattern, ... Rewrite the traversal as outgoing, which resolves correctly
whatever the data: anchor it on the source with MATCH (source)-[e]->(target) ...
RETURN type(e), or, to reach the edges arriving AT a node, on that node with
MATCH (other)-[e]->(target {key:'...'}) ... RETURN type(e) - do not reverse the
arrow. To cover both directions in one read, take the union of the two outgoing legs
```

The concrete measurement, on a node pair carrying `gateway-[:CALLS]->authstore` and
`authstore-[:REPLIES_TO]->gateway`: on `1.15.0`,
`MATCH (gateway)<-[e]-(b) RETURN type(e), e.weight` exited `0` and returned
`CALLS, 1` — the forward edge, where the correct answer is `REPLIES_TO, 2`; the
undirected form returned two rows, **both** `CALLS, 1`. On the write side, an
undirected `SET e.weight = 7` returned `{"ok": true}` at exit `0` having written only
the outgoing edge, and a purely reverse `SET` wrote nothing while reporting the same
success.

**What triggers the refusal is an expression use of the relationship variable**, which
is narrower than "any reverse pattern" and worth knowing precisely. Measured on the
shipped binary: `graph query` and `graph search` are refused; `graph update` and
`graph delete` are refused when the pattern's relationship variable is read or written
(a `SET`, or a `WHERE type(e) = ...`); a plain `DELETE e` that never reads `e` still
succeeds; and `graph create` never reaches the guard at all, because its clause-class
check refuses a `MATCH` query first.

**Refusal costs no reach**, and that was verified rather than assumed: every edge
stays readable and writable through an outgoing pattern anchored on either endpoint.
Detection runs over the engine's own parsed AST, not the query text, so an arrow inside
a string literal cannot trip it and each `UNION` branch is scanned in its own scope.

**If you write Cypher against `rmp graph`, the undirected cross-reference idiom
`MATCH (a)-[:R]-(b)` must be rewritten** as the union of two outgoing legs.

### 8. A schema-introspection query with irregular keyword spacing is refused

`SHOW  INDEXES` with two spaces passed the guard rail, was admitted as an ordinary
read, and died in the engine parser with a diagnostic that listed every clause keyword
except `SHOW` — reading as though `SHOW` were unsupported, when the identical query
with one space worked. It is now refused by the guard rail, with the guard rail's own
message and the accepted spelling, rebuilt from the canonical uppercased keyword so
that no user byte reaches stderr. **The exit code moves from `1` to `6`**, because the
refusal is a validation failure rather than a database error:

| | On `1.15.0` | On `1.15.1` |
|---|-------------|-------------|
| Exit | **1** | **6** |
| stderr | `Error: database error: graph query failed: cypher: parse: unexpected "SHOW" ...` | `Error: validation error: graph query: SHOW INDEXES is a schema-introspection command the engine recognises only with exactly one space ...` |

Single-space `SHOW INDEXES` is accepted on both versions. The web endpoint answers
HTTP `400` with a kind of
its own, `invalid_keyword_spacing`, rather than reusing `not_read_only`, which would
publish a false classification: a `SHOW` is read-only whatever its spacing.

The asymmetry with the DDL class is deliberate and now specified: the DDL pairing
exists to **refuse**, so being wider than the engine only refuses more; the
introspection pairing exists to **admit**, so being wider admits what the engine then
rejects.

### 9. `sprint update` no longer discards a flag supplied empty

`sprintUpdate` treated the empty string as its flag-absent sentinel, so it could not
tell a flag that was not supplied from one supplied empty.

| Invocation | On `1.15.0` | On `1.15.1` |
|------------|-------------|-------------|
| `rmp sprint update 1 -t ""` | Exit **2**, "at least one of ... is required" — false, a flag *was* supplied | Exit **6**, `Error: validation error: title cannot be empty` |
| `rmp sprint update 1 -t "" -d "text"` | Exit **0**; the title silently discarded, one audit entry for two supplied flags | Exit **6**; **nothing mutated** |

Validation runs before the database is opened, so a rejected update mutates nothing by
construction rather than by rollback. `sprint update` and `task edit` now agree on
both exit code and wording for the identical input shape.

### 10. `sprint list` changes its result order and fills two fields

Two independent changes to one command's output.

**The order.** `sprint list` returned sprints by `created_at DESC` and now returns
them by `order_index` ascending — the planned execution order the field exists for.
No order was previously published, so nothing documented breaks; a caller that
depended on the observed sequence does. The order is now a published guarantee in
`SPEC/COMMANDS.md` and is stated on both help surfaces. No tie-break is needed and
that was verified at both layers: the column is `NOT NULL` and its index is unique.

**The fields.** `task_count` was `0` and `tasks` was `null` for every sprint, on every
call. Both are now populated, resolved for the whole listing in **one grouped read**:
measured at the driver boundary, 2 statements for 1, 2, 3, 4, 5 and 50 sprints alike,
and 1 for a roadmap with no sprint. `task_count` is `len(tasks)` rather than a second
`COUNT`, so the two cannot disagree, and an empty sprint yields `[]` rather than
`null`. `tasks` carries ids, not objects.

```json
{"id": 1, "title": "Sprint one", "order": 1, "task_count": 2, "tasks": [1, 2]}
```

**A consumer that special-cased the empty values, or that read the listing's first
element as the newest sprint, must be updated.**

### 11. Dozens of error messages were rewritten

If you match `rmp` stderr by string, assume every match needs re-checking. The
changes are of four kinds.

**A sentinel that was printed twice.** A trailing `%w` whose sentinel text repeated
the words the literal prefix already supplied produced
`invalid task type: BOGUS: invalid task type`. A probe rendering every enum and
validation rejection found **seventeen** such sites across three files, not the one
reported. All now print once, with the value quoted:

```
Error: validation error: invalid task type: "BOGUS"
```

**A whole rule converged onto one sentence.** Six numeric range rules were announced
in different words depending on which command applied them. They now share one
spelling, `<field> must be between <lo> and <hi>, got N`, with the words owned by
`internal/utils` and the comparison owned by `internal/models`:

| Rule | On `1.15.1` |
|------|-------------|
| priority, severity | `Error: validation error: priority must be between 0 and 9, got 99` |
| `--limit` | `Error: validation error: limit must be between 1 and 100, got 0` |
| entity ids (positional and `--entity-id`) | `Error: validation error: task_id must be between 1 and 2147483647, got 0` |
| `--max-tasks` | `Error: validation error: max_tasks must be between 1 and 10000, got 0` |
| `sprint move-to` position | `Error: validation error: position must be an integer between 0 and 2147483647` |

The entity-id rule keeps its **deliberate, published** exit-code split: the eight
comment subcommands classify a positional id outside the range as exit `2` misuse,
every other surface as exit `6`. The class became a parameter; the wording did not.

**One field, two published names.** A free-text field was named with hyphens in one
subcommand's message and with underscores in another's. The canonical spelling is the
underscored one — the database column name, and the name `SPEC/COMMANDS.md` already
published. `SPEC/COMMANDS.md § Published Field Names in Validation Messages` is now
canonical for all eight fields, and the field name is an integer-based enum in Go, so
a call site that spells a field name itself no longer compiles.

**Classification stated once.** The `graph` family wrapped an already-classified error
and printed `Error: validation error: validation error: ...`. It reached all five
subcommands, not the two recorded, and for two of the four roadmap-name rules it did
not double a prefix but **invented** one, printing words the specification does not
contain. Separately, `sprint move-tasks` printed `resource not found` twice; it now
prints it once and keeps the discriminator that says which of the two sprint ids was
missing:

```
Error: resource not found: from sprint 999
Error: resource not found: to sprint 998
```

**A value that breaks two rules at once now reports a different one.** Because the
validation order is uniform, a value that is both over-long and carries a control
character resolves to **length**. Measured on `task create` with a 300-character title
carrying a BEL: `1.15.0` printed
`Error: validation error: title: control characters are not allowed`; `1.15.1` prints
`Error: field exceeds maximum size: title exceeds maximum length of 255 characters`.
The exit code is `6` in both cases, but the sentinel and the message differ. The same
applies to `sprint create -d`. The resolution was decided deliberately and shown sound:
the field length is well defined on malformed input, every undecodable byte counting as
one, so the count is never below what SQLite would measure.

**Two enum refusals were rewritten** so that the parsers own them rather than an
ad-hoc second check: `invalid audit operation: "BOGUS"` and `invalid entity type: "BOGUS"`.

**The date-filter refusal now names the flag and both accepted forms**:
`validation error: invalid date format: notadate` becomes
`validation error: --since: invalid date format: expected RFC3339 (2026-01-01T00:00:00Z) or date-only (2026-01-01): "notadate"`.

**Eight example error strings in the machine-readable AI contract were stale** and are
corrected; the whole `Example.Stderr` surface, all 68 strings, is now driven against
the compiled binary.

### 12. Smaller behavioural changes a caller can observe

- **A no-op position move now writes an audit entry.** `sprint move-to`, `sprint top`,
  and `sprint bottom` returned early when the task was already at the target rank, and
  the early return sat above the audit write. The specification always required the
  entry, and both siblings — `task edit` with an unchanged title, an identical
  `sprint reorder` — already obeyed it. Six invocations, three of them no-ops, now
  produce six entries where the reported sequence produced one.
- **Database failures from the comment subcommands now carry their sentinel.** Three
  sites returned an unclassified error, so `Error: database error: ...` — a line
  `SPEC/COMMANDS.md` publishes in six rows — was never printed. The exit code was
  right only by accident, because an unwrapped error falls back to `1` and
  `ErrDatabase` also maps to `1`.
- **A graph read can now wait, and can now fail.** Opening the store is not read-only
  on disk: GoGraph's recovery removes a stale staging directory and can promote a
  backup snapshot, both of which repair the directory a concurrent writer publishes
  into. A read now takes a **shared** advisory lock across the store open alone. Two
  readers do not exclude one another, but a reader colliding with a writer waits under
  the bounded backoff — six attempts, 2500 ms worst case — and then fails with exit
  `1` and `graph store is busy`, where `1.15.0` returned in 15 ms and destroyed the
  writer's staging directory.
- **An over-long Cypher query is refused by Groadmap, not by the engine.** The limit is
  unchanged at 1 048 576 bytes and now applies at **both** doors, `--query` and standard
  input, before the query is passed on. What changes is where the refusal comes from and
  what it costs: exit `1` and
  `Error: database error: graph query failed: cypher: parse: parse error at 1:0: query too large: ...`
  become exit `6` and `Error: validation error: query exceeds maximum length of 1048576 bytes`,
  and the input is no longer buffered in full first. A `graph` subcommand invoked with
  no `--query` and a terminal on standard input now exits `2` immediately instead of
  waiting for input that will never arrive.
- **The retry policy runs six attempts, not five**, so the exhaustion message changes
  from `failed after 5 attempts` to `failed after 6 attempts`, and the worst-case wait
  from about 1500 ms to 2500 ms.
- **`task next` no longer applies a priority tiebreaker** that `SPEC/COMMANDS.md`
  already said does not order that listing. The stray sort key was removed from
  `GetNextTasks`; the ordering it produced was not reproducible after the position
  migration, so the practical effect on an upgraded roadmap is expected to be nil.
- **Under `AI_AGENT=1`, a suppressed AI-agent hint no longer leaves its separator
  behind.** Each suppressed path loses exactly one byte; every unsuppressed path is
  byte-identical to `1.15.0`.
- **`rmp version` is now a documented invocation form**, and all six global forms
  (`help`, `--help`, `-h`, `version`, `--version`, `-v`) take arity `0`.
- **The `Sprint` object key list in `sprint --help` names all eleven keys**; `title`
  and `order` were missing, and `sprint_title` was missing from two `SprintShowResult`
  sketches.
- **The AI contract's exit-code arrays for `roadmap create` and `roadmap remove` now
  include `2`**, which both subcommands emit from their own argument refusal and both
  help screens already listed.
- **The AI contract's `AuditOperation` enum values gained two members** —
  `entity_type` and `legacy` — so a consumer can tell which entity an operation is
  written against and which four of the 43 values are retained for reading historical
  rows only. The classification is **declared and never inferred from the name**:
  prefix and entity type agree on all 39 operations written today, but labelling a
  group by prefix turns a presentation grouping into a factual claim that becomes
  wrong the day a `TASK_*` operation is written against a sprint. `legacy` is a
  pointer to a boolean so that it publishes `false` and omits absent, rather than
  disappearing from the 39 in use or appearing on every other enum. Additive: no
  existing key changed.

**What did not change, verified by key-set diff against the `1.15.0` binary:** no JSON
key was added, removed, or renamed on the task, sprint, comment, audit-entry,
`sprint show`, `sprint stats`, `stats`, or `roadmap list` objects; no default value,
limit, range, or port moved; and all 52 happy-path command invocations exit identically
on both versions.

### Widenings — input that used to fail and now succeeds

Neither of these can break a caller; both change what the binary accepts.

- **Length caps count Unicode code points, not bytes.** All eight capped free-text
  fields counted `len()` in Go, which is a byte count, while `SPEC/MODELS.md` said
  "255 characters" and the SQLite `CHECK` counted characters in TEXT semantics. Two of
  the three authorities already agreed; the Go layer was the dissenter. A 255-character
  CJK title is now accepted, and 255 four-byte emoji — **1020 bytes** — is accepted, a
  result impossible under byte counting. The message needed no rewording: it always
  read `exceeds maximum length of N characters` and has simply become true. Agreement
  with SQLite is measured, not assumed, and no schema change was needed.
- **The audit date filters accept the date-only form.** `rmp audit list --since 2026-08-01`
  exited `6` on `1.15.0` although `SPEC/COMMANDS.md`, the AI contract, and the README
  all published that form. Both `audit` subcommands now accept the date-only and the
  full RFC 3339 forms through the same entry point `task list` uses.

  **Read this before you use it: a bare date means the first instant of its day in
  UTC**, which makes `--until` effectively exclusive of the day it names. Measured
  against a roadmap holding 19 entries all timestamped `2026-08-26T07:3x`,
  `--until 2026-08-26` returns **0 rows** and `--until 2026-08-27` returns all 19,
  while `--since 2026-08-26` returns all 19. A reader assuming an upper bound meant
  end-of-day would have been wrong and nothing said otherwise; the reading is now
  specified.

  The shared `ParseISO8601` was deliberately **not** widened: its thirteen remaining
  callers parse stored timestamps the code itself wrote, always in full RFC 3339, and
  widening the shared function would have loosened a contract nobody asked to change.

## Upgrade Notes

### Step 1 — Back up the roadmap; the migrations are forward-only

```bash
cp -a ~/.roadmaps/<name> ~/.roadmaps/<name>.pre-v1.15.1
```

**Nothing in this release deletes a row, a column, or a table.** Both migrations
change values and one index; every `sprint_tasks` membership row that existed before
exists after, attached to the same sprint and the same task. There is still no
downgrade path, for the reason in Step 3.

### Step 2 — The migration path: `1.12.0` → `1.14.0`

Two migrations run automatically, in order, on the first command executed against an
existing roadmap. There is nothing to invoke and no flag to pass. Neither adds a
column, and neither rebuilds a table.

| Migration | What it does | Deletes data? |
|-----------|--------------|---------------|
| `1.12.0` → `1.13.0` | Makes each sprint's task order **total**. Renumbers every sprint's positions to a dense `0..N-1` run, then replaces `idx_sprint_tasks_order` with its `UNIQUE` form under the same name | No |
| `1.13.0` → `1.14.0` | Makes each sprint's task order **dense**, repairing gaps already committed. Drops the unique index for the duration of the repair, renumbers, then recreates the index | No |

Both rank each sprint's rows by `position` ascending with `task_id` ascending as the
tie-breaker. **The values change and the sequence never does**: wherever the planned
order was unambiguous it is preserved exactly, and wherever it was ambiguous — two
members sharing a position — it is settled deterministically, the lower `task_id`
taking the lower position.

Three properties are worth knowing before you run them:

- **The repair runs before the constraint exists**, or with it dropped, so the
  intermediate states of a multi-row `UPDATE` cannot violate it. This was measured,
  not assumed: against the pinned driver, a sprint holding positions `0`, `2` and `5`
  whose rows sat in the reverse physical order failed with
  `UNIQUE constraint failed: sprint_tasks.sprint_id, sprint_tasks.position` when the
  index was left in place, and succeeded when it was not.
- **Recreating the index is what makes each migration fail closed.**
  `CREATE UNIQUE INDEX` validates every row, so if a repair ever left two members of
  one sprint sharing a position, the statement fails, the single transaction is rolled
  back, and `_metadata.schema_version` keeps its previous value. The database is left
  exactly as it was.
- **Both are idempotent.** A database that is already dense receives, in every row, the
  value that row already holds.

The second migration exists because teaching the write paths to compact stops new gaps
appearing and does nothing about gaps already committed. The measured instance was a
sprint holding 39 members at positions `0`–`36`, `53` and `57`, produced by the source
side of `sprint move-tasks`. **Every installation that has ever run one of the four
gap-opening paths carries the same damage**, and only a migration reaches those
installations.

The gap was never cosmetic: `sprint move-to`, `sprint top` and `sprint bottom` decide
whether they have work to do by comparing the moved task's **stored** position against
the **target rank**, so over a sparse run a real move was read as no move at all — and
reported as a success.

### Step 3 — Do not run a `1.15.0` binary against a migrated roadmap

This is measured, not theoretical. Once a roadmap reaches schema `1.14.0`, its
`idx_sprint_tasks_order` index is `UNIQUE`. A `1.15.0` binary's `sprint reorder`,
`sprint swap` and `sprint move-to` assign positions **sequentially over values still
occupied**, because the parking step that avoids the collision arrived in this
release. Driving a migrated roadmap with a `1.15.0` binary therefore fails at **exit 1**
with the driver's raw diagnostic:

```
Error: updating position for task 4: constraint failed: UNIQUE constraint failed: sprint_tasks.sprint_id, sprint_tasks.position (2067)
```

The same three commands succeed at exit `0` on `1.15.1`. This was measured on both
binaries against the same migrated database, not inferred — and it was met in practice
during the sprint, when a reorder driven by the `1.15.0` binary still on `PATH` failed
this way while the same operation from a freshly built binary succeeded.

**Reads are unaffected.** No column was added or removed, so an older binary still
lists, gets and filters correctly; the stored `position` integers are simply different
after the first open. It is the three ordering commands that break. Replace the binary
on `PATH` before you drive a migrated roadmap.

### Step 4 — Update your automation

Work through [Breaking Changes](#breaking-changes) in full. The four that break
scripts most often:

1. **Any invocation carrying a surplus positional token now exits `2` and does
   nothing.** Space-separated id lists are the common case: write `2,3`, not `2 3`.
2. **Any check for exit code `2` on a mistyped subcommand must accept `127`.**
3. **Anything that reads a failing invocation's stdout gets an empty stream.**
4. **Anything that matches `rmp` stderr by string must be re-checked**, and anything
   reading `sprint list` must expect a different order and two populated fields.

If you write Cypher against `rmp graph`, rewrite every undirected or reverse
relationship pattern as one or two outgoing legs.

### Step 5 — If you install with `install.sh`, check two prerequisites

The installer is now hard-fail on integrity, which makes two things prerequisites
rather than conveniences:

1. **Every archive must have its `<archive>.sha256` published beside it.** The release
   workflow generates and attaches one per archive, so this holds for an official
   release; a hand-assembled mirror that omits them cannot be installed by the script.
2. **The installing host must have `sha256sum`, `shasum`, or `openssl`, and `mktemp`.**
   Missing any of them, the script exits `1` before requesting a single release asset,
   with a message naming the tool. There is no opt-out flag and none will be added.

### Step 6 — Install and verify

```bash
git checkout v1.15.1
go build -o ./bin/rmp ./cmd/rmp

./bin/rmp --version
# Groadmap version 1.15.1
```

## Why This Is Released as `1.15.1`

**`SPEC/VERSION.md` defines `PATCH` as "Bug fixes, backward compatible". This release
is not backward compatible.** Under a strict reading of Semantic Versioning 2.0.0, a
change that makes a previously successful invocation fail is a `MAJOR` change, and
this release contains a dozen of them. The version number is nevertheless `1.15.1`, by
the project owner's explicit decision, taken after the objection was raised and
answered. The reasoning is recorded here so that it can be reviewed rather than
inferred:

- Every change in the release is the **correction of a divergence** between what the
  software does and what it is specified to do. Nothing new was built. In the
  project's own terms, the binary moved to the contract that was already published —
  the exit code `127`, the comma-separated id list, the "255 characters" cap, the
  date-only filter form, the published error strings. A caller relying on the old
  behaviour was relying on a defect.
- The affected surface is the **roadmap-authoring CLI**, not a library API that other
  code links against. There is no compilation to break and no dependency resolver to
  mislead.
- Every incompatibility **fails loudly and immediately** — a non-zero exit and nothing
  changed — rather than silently altering a result. In several cases the *old*
  behaviour was the silent one: a deleted task the caller did not name, a graph write
  reported as successful that wrote nothing, a title discarded without a word.

**This does not soften the incompatibility, and the version number does not warn
anyone.** A reader who sees `1.15.0 → 1.15.1` and expects a drop-in replacement will
be wrong. If you drive `rmp` from automation, treat this release as a breaking one:
read [Breaking Changes](#breaking-changes) and [Upgrade Notes](#upgrade-notes) before
upgrading, and expect invocations to start failing until they are corrected.

The project set this precedent one release earlier, publishing two backward-incompatible
changes as `1.15.0` and recording the same objection in the same place. The
classification is a project decision; the incompatibility is a fact, and both are
stated.

## Changes by Category

### Fixed — The Command Surface

- **A stray positional argument is refused across the whole CLI.** `checkPositionalArity`
  is called from `Command.DispatchFamily`, the only place in the binary that invokes a
  subcommand handler, so enforcement is reached **by construction** from each command's
  own declaration — covering every command that exists and every command that will be
  added. It was deliberately not put in the flag parser, which is built inside each
  handler from a per-command definition list and would have needed the arity passed at
  more than fifty-eight call sites. The six global forms resolve in `main.go` before any
  command lookup, so they carry a second, deliberate enforcement point, and an AST gate
  asserts every case of that switch calls it.

  Four families already refused a stray token, each in its own words. All four keep
  their exact line, byte for byte, and are exempted by a declaration field rather than
  by a name list inside the dispatcher: `graph` keeps its parenthetical hint, `web` its
  colon-and-unquoted form, `ai-help` its own line, and the comment subcommands the
  canonical one.

- **The comment subcommands ignored a stray positional in all eight cases, not three.**
  The belief that `comment-remove` already rejected leftovers was false: the shared
  parser collects positionals without error and refuses stray flags only. That made the
  worst case destructive — `rmp task comment-remove 1 99` deleted comment `1` and exited
  `0`. Two behaviours were deliberately preserved: a hyphen-prefixed leftover is still
  reported as an unknown flag, and `--body -1` still stores the body `-1`.

- **An unresolved subcommand exits `127`.** `utils.ErrUnknownCommand` is a new sentinel
  and `DispatchError` carries the family and the offending name. Its documentation
  records why it must not be wrapped in `ErrInvalidInput`, which is the wrapper that
  mapped the case to `2`.

- **A failing invocation writes nothing to stdout.** Delivering this required rewriting
  64 help printers to write through an indirect destination rather than `fmt.Print`, and
  that rewrite was proved byte-inert rather than assumed: stdout, stderr and exit code
  were diffed across 80 help surfaces between the previous binary and this one, with 78
  byte-identical and the two that differ being the same intended edit.

- **The invoked family's help follows the error on stderr for a dispatch failure.** This
  settled a contradiction inside the specification — `SPEC/COMMANDS.md` said the help is
  displayed after the error and `SPEC/HELP.md` said help is never auto-appended — in
  favour of `COMMANDS.md`. The AI-agent banner is prepended by the stdout dispatch seam
  and the recovery path deliberately does not go through it, so the help carries no
  banner and the hint stays exactly once, and last.

- **Suppressing the AI-agent hint no longer leaves the blank line that was meant to
  separate it.** The separator now lives inside the `sync.Once` closure that writes the
  hint, so the two are governed by one condition and disappear together. A call-site
  predicate was rejected as the second condition the defect consists of.

### Fixed — Free-Text Validation

- **One validation order, everywhere.** Length cap, UTF-8 encoding, control characters,
  trim, emptiness — across all seven write paths, all eight fields, by flag and on
  standard input. The divergence was wider than recorded: all four `task create` fields
  diverged, not only the title, plus `sprint create`'s description.

  **The cap is first because it is forced, not because it is preferred.** The comment
  body's bounded standard-input read fixes the length verdict the moment the content
  cannot fit and stops reading — its CWE-400 defence — and a reader cannot judge the
  encoding of bytes it has refused to read. The other six paths were moved onto the
  comment path's order, never the reverse.

  The order lives in one place, as a ladder in which each rung strictly extends the one
  below: `InspectFreeText` for the content pair, `ValidateFreeText` for the pair plus the
  refusal constructor, `TrimFreeText` for the triple plus the trim, `RequireFreeText` for
  that plus emptiness. Composition, not a second statement of the order.

  The asymmetry is now specified: **the cap measures the trimmed value**, which is what
  is stored, while **both content checks see the value as supplied**. Reaching the cap is
  never a way past the content rules — a value exactly at the maximum carrying a BEL is
  still refused as a control character.

- **Bytes that are not valid UTF-8 are refused.** The rule covers eight fields, not the
  seven originally reported: `completion_summary`, written by `task stat COMPLETED --summary`,
  was missing from the list and stored invalid UTF-8 just the same. The two checks are
  welded into one function rather than repeated at each call site, and the specification
  states the rule relationally — the encoding check sits immediately before the
  control-character check, wherever that check already runs — so the pair travels as a
  unit and no call site can keep half of it.

- **A leading or trailing VT or FF no longer evades the control-character rule.** The
  general lesson, and the reason it took three passes: when a rule depends on the **order**
  of checks, finding the checks is not enough. A trim, a normalisation, or an early return
  that happens before the validator makes the validator's internal order irrelevant, and
  it will not appear anywhere near the code that looks responsible.

- **A whitespace-only value in a required field is refused, and the stored value is
  trimmed.** The counter-intuitive fact that made this dangerous: `sprint create` was
  correct before this change **only because it did not trim at all**. Adding the trim
  without the ordering would have reproduced the hole `task edit` already carried. The
  observable signature of the correct order is that a value made only of VT is refused as
  a control character and never as empty.

- **Length caps count Unicode code points.** The site list in the report was incomplete:
  the four caps named in `task.go` are eight, because `Task.Validate` and
  `TaskUpdate.Validate` each capped all four fields, and `sprint.go` carried two more that
  were not on the list at all. Graphemes are deliberately not the unit and no
  normalisation is introduced; the UTF-8 rule is what makes the code-point count
  unambiguous.

  The predicted test failure did not happen, and that matters more than the fact:
  `tests/test_16_boundary_unicode.py` was recorded as covering titles at 255 **bytes** and
  passed unchanged, because every boundary case in it was ASCII. It described the defect
  in its prose while proving nothing about it.

- **One field, one published name.** `SPEC/COMMANDS.md § Published Field Names in
  Validation Messages` is canonical for all eight fields. The Go type is an
  **integer-based** enum, which is the point: an untyped string constant does not convert
  to it, so a call site that spells a field name itself does not compile. A string-based
  type would have accepted the same call in silence.

  Found while measuring and fixed in the same cycle: `task edit`'s two field maps were
  iterated in Go's randomised order, so which of two offending fields got named varied
  between runs of the identical command.

### Fixed — The Knowledge Graph

- **A reverse-traversal read reported the wrong edge**, and **a write bound by an
  undirected or incoming pattern was silently ignored**. Both are refused before the store
  is opened, across five subcommands and the web query bar. Detection runs over the
  engine's own parsed AST rather than the query text, so the directions inspected are the
  directions the engine will plan.

  Three findings widen the record: an incoming pattern fails from **either** anchor, so
  the trigger is the pattern direction and not the anchor; `REMOVE` is affected exactly as
  `SET` is; and `DELETE` is not, so the write refusal is scoped not to reach it. A `WITH e`
  between `MATCH` and `SET` happens to repair the write today and was deliberately not
  exempted, because it rests on projection materialisation the engine may elide.

- **Reading the knowledge graph no longer mutates its on-disk store.** Graph reads take a
  **shared** advisory lock on `write.lock`, held across the store open alone. The narrowness
  of the hold is load-bearing and was established three ways: by GoGraph's write-side
  surface being exactly a `RemoveAll` plus a conditional rename, by a probe that deletes
  the whole store directory between open and query and still gets complete results, and by
  `strace` showing nine store syscalls all inside the open. `SPEC/GRAPH.md` carries an
  anti-widening clause naming the four changes that would invalidate the reasoning.

  Measured with a writer holding for four seconds and a marker planted in the staging
  directory: before, the CLI read returned in 15 ms and the HTTP `GET` in 13 ms and **both
  destroyed the marker**; after, both wait 2512 ms and refuse, and the marker survives.

- **Knowledge-graph property values are inside both free-text rules**, with two different
  reaches keyed on the cause rather than on the command. The control-character rule reads
  the **parsed** value, because Cypher decodes escapes inside a string literal, so a query
  of pure ASCII can store a real control character. The encoding rule reads the **raw
  bytes**, because the engine decodes the query to runes before its grammar runs and by
  parse time the evidence is gone. Neither observation point can be moved.

- **The Cypher query read from standard input is bounded**, at 1 MiB, at **both** doors —
  `--query` and standard input — because a maximum that holds on one door refuses there
  what it accepts on the other. A `graph` subcommand supplied no query at all used to wait
  on standard input forever; it now exits `2` immediately. The terminal check is one
  `ioctl` per platform rather than a `Stat` mode test, because `/dev/null` and `/dev/zero`
  are character devices and the mode bit would answer "no query supplied" for a source that
  does supply bytes.

- **A schema-introspection query with irregular keyword spacing is refused by the guard
  rail.** Narrowing the pattern alone refuses nothing, and that is the finding worth
  carrying: the classifier returns "read-only" from its default branch, so a statement that
  stops classifying as introspection is simply admitted as an ordinary read. The fix adds a
  named classification and a deliberate refusal, not a tighter regular expression.

- **The graph family states the validation classification once.** The wrap was made
  conditional rather than deleted, classifying only what arrives unclassified, so the second
  failure mode behind it — an unresolvable home directory, which carries no classification —
  keeps its exit code exactly as it was.

- **The key-uniqueness invariant of the project's knowledge graph is stated and its
  violation is detectable.** The defect was never that the invariant could be violated: it
  was that a violation would be **invisible**, because the byte-wise audit groups on stored
  bytes and reports two Unicode normalisation forms of one key as two groups of one.
  `SPEC/GRAPH.md § Node Key Uniqueness` is now canonical, publishing the invariant, NFC as
  the comparison, why it is not enforced, and a two-step audit that does detect such a pair.
  The NFC rule moved to a leaf package, `internal/unicodenorm`, so the audit could reach it
  without inverting an import arc.

### Fixed — Sprint Task Ordering

- **`position` is `UNIQUE` within a sprint.** There was no active defect — 276 memberships,
  zero collisions — but the invariant held only because the single `INSERT` path happened to
  supply a value, and the web board depends on that order twice over.

  The finding that changed the implementation, measured against the pinned SQLite rather
  than reasoned about: **a plain unique index breaks three commands.** `reorder`, `swap` and
  `move-to` all assign sequentially over values still occupied, so the first write claims a
  position another row still holds. They now park into a disjoint negative range before
  assigning. `MoveTaskToPosition` stopped doing a range shift altogether: it reads the order,
  removes the task, reinserts at the target index and writes the permutation.

  The obvious repair is unsound, and that was measured too: a correlated subquery reads
  SQLite's own partial writes and trades one collision for another.

  A live TOCTOU was found and closed in the same cycle: `ReorderSprintTasks` checked list
  completeness in a read **outside** its write transaction. Reproduced under a concurrent
  add, not hypothesised. All three validations moved inside the transaction.

- **`position` is dense: the members of a sprint hold exactly `0..N-1`.** The schema cannot
  carry the invariant and `SPEC/DATABASE.md` says so with three exhaustive reasons, so the
  guarantee rests on the write paths. Every write path is enumerated and classified; the
  four that opened a gap are all removals and now compact in the same transaction — the
  source side of `sprint move-tasks`, the `ON CONFLICT` branch of `add-tasks`, `task reopen`
  from a sprint status, and `task remove` on a member. **The obligation follows the row
  rather than the command**, since three of the four repair a sprint the caller never names.

- **`sprint add-tasks` re-parents a task that already belongs to another sprint**, and
  `SPEC/COMMANDS.md` now says so. Two specification files contradicted each other; the owner
  ratified what ships, so no behaviour changed. The step was rewritten rather than deleted
  and its numbering preserved deliberately, because two code comments cite "validation step 5"
  by number.

- **The published validation order for sprint task assignment was the reverse of what the
  binary applies.** The exit code is contract, so a caller branching on `4` versus `2` was
  branching on which document it had read. The specification was the wrong side, established
  by measurement: eighteen sibling invocations, each with a nonexistent resource id and a
  malformed second value, report the lexical fault and suppress the existence one — 18 of 18,
  with no counter-example in the CLI. Correcting the code was declined; it would have changed
  a shipped exit code and made these three the only commands opening the database before
  finishing with `argv`. The reported pair was a lower bound: six divergences were found and
  the whole list, now eleven steps, was corrected.

### Fixed — The Audit Log

- **A no-op position move writes its audit entry.** There was one guard, not three:
  `sprint move-to`, `sprint top` and `sprint bottom` all delegate to `MoveTaskToPosition`, and
  the early return sat above the audit write at the tail of the transaction. The guard remains
  and now skips only the position rewrite, because without it a no-op would rewrite every
  membership row of the sprint for nothing.

- **`audit list` validated its enums a second time, in different words**, leaving the model
  parsers with no caller at all. All three sites now route through the parsers. A useful
  asymmetry shaped the fix: `invalid operation` was published **nowhere**, which is exactly
  why its divergence survived while its sibling's did not. **An unpublished string is
  invisible to the only gate that catches this class of drift**, so the specification now
  publishes it.

- **Database failures from the comment subcommands carry their sentinel**, so the six
  published `Error: database error: ...` rows are produced as specified. The sentinel was
  added **in place** and never moved earlier — in `writeError` it follows the switch owning
  the foreign-key, `CHECK` and `NOT NULL` classifications, and in `getComment` it follows the
  no-rows branch — because a blanket wrap ahead of the classifier reddens the classification
  tests while leaving the sentinel test green.

### Fixed — Security

- **`install.sh` verifies the archive against its published SHA-256 before extracting.** The
  mitigation already existed and was already published by the release pipeline; it was simply
  never used. Two security judgements were made rather than defaulted: the script **aborts**
  rather than warning when no hashing tool exists, because the documented invocation is `curl`
  piped into `bash` and whoever benefits from a control that fails open is exactly whoever
  replaced the archive; and there is **no opt-out flag**, because in an installer invoked that
  way a bypass switch is the first thing a malicious instruction asks for.

  `SPEC/DEPLOY.md` states what the check does **not** protect against, which was a requirement
  rather than a courtesy: it detects corruption in transit or at rest and asymmetric
  substitution, and it detects nothing about whoever controls the release, the transport for
  both objects, or `install.sh` itself.

- **`install.sh` no longer stages in a predictable temporary directory.** Every download lands
  in one directory created by `mktemp -d` from an unpredictable template, mode `0700`, verified
  after creation and failing closed. The previous `mkdir -p /tmp/rmp_install_$$` succeeds on an
  existing directory, so a local user could pre-create all 32768 PIDs and swap the archive
  between the verification and the extraction — CWE-367 and CWE-377, defeating the checksum gate
  that had just been added.

  The structural question was decided explicitly: verifying and extracting from one held
  descriptor is the honest fix and is impossible in portable shell, for four simultaneous
  reasons that are recorded in the script. The window is closed the other way instead — a path
  nobody else can open has no time-of-use to reach. The non-obvious check: the parent directory
  is refused when world-writable **without** the sticky bit, because there a local user can
  rename the `0700` directory away after creation.

- **`columnExists` no longer interpolates an unguarded table name into SQL.** The safety was a
  property of the call sites, not of the function, and the `#nosec` that documented it is the
  same annotation that would have kept the scanner silent about a future caller passing a
  variable: **a suppression is a permanent blindfold; it does not expire when its reason does.**
  The empty string is a correctness argument on its own, independent of any attacker:
  `pragma_table_info('')` is valid SQL returning zero rows, so an unguarded empty name reports
  every column absent and the caller then runs an `ALTER TABLE` at a table nobody named.

- **The `.gosec.yaml` register of accepted findings is gated, not merely refreshed.** The proof
  that the gate was the point came from the repository's own history: `v1.15.0` brought the
  register up to date and added no check, and within the day five suppression sites moved
  without it. The gate parses with `go/ast`, because the rule that a `#nosec` counts only at the
  head of a comment group is not expressible in `grep`, and because `grep` is blind to the
  `//gosec:disable` syntax — which is how one would slip past it.

- **Agent worktrees are gitignored.** The `security` target already passed
  `-exclude-dir=.claude/worktrees` to the scanner while git was never told to ignore it, leaving
  a full second checkout one `git add -A` away from the repository.

### Changed — Performance

- **The web sprints page no longer reads any sprint's member tasks.** It paid a full member-task
  read per sprint to produce one integer. The card footer now takes that integer from the
  listing, and the new `sprintsSource` interface carries `ListSprints` alone, so **the N+1 is not
  expressible on this path** rather than merely absent from it. Measured: member-task reads go
  from one per sprint to zero at 0, 1, 3, 5 and 12 sprints, and median page time over 200 sprints
  went from **38.5 ms, linear in sprint count, to 10.9 ms, flat**. The rendered page is
  byte-identical before and after.

- **`sprint list` resolves the whole listing in one grouped read**, measured at the driver
  boundary: 2 statements for 1, 2, 3, 4, 5 and 50 sprints alike, against 2+N for the per-sprint
  alternative on the same instrument.

- **The retry policy is stated once.** The bounded backoff slept four times where the
  specification and the code's own comment promised five. Four sites stated the policy; a fifth
  was found in the web layer, correct then and due to go stale. `internal/backoff` now owns the
  **loop**, not the constants — sharing constants would not have caught this defect, because the
  constants agreed all along and the loop bodies did not. The policy is six attempts, one initial
  plus five retries, waiting before each retry and never after the last: 100/200/400/800/1000 ms,
  2500 ms worst case. Statements of these numbers in production Go drop from four to one, and a
  structural gate holds that only `internal/backoff` may block on a duration in production code.

### Changed — The Read-Only Web Interface

- **The board search finds a task whose title is stored in a different Unicode normalisation
  form.** A term and a task's searchable text are both normalised to NFC before they are folded.
  Normalisation is for comparison only: the bytes `rmp` stores and renders are untouched. NFC and
  not NFD, because the search performs substring containment and under NFD a term of `cafe` would
  match a title spelled with an acute. Two passes and not one, because one pass leaves the result
  outside NFC on 70 of 1 321 226 sequences. Normalisation before the fold, because the two orders
  differ on 74 of those sequences. The behaviour delta is exactly **1117 of 1 112 064 code
  points**, none of them ASCII, at about 29 ns per already-NFC ASCII card.

  `golang.org/x/text` v0.41.0 is admitted as the fourth direct dependency, used **only** for
  canonical decomposition and canonical ordering; the composition step is Groadmap's own, because
  that module at the pinned version composes a supplementary starter as though it were its low 16
  bits across 15 041 pairs.

- **The Kanban column-count badges carry the colour of the status they group.** The rendering had
  already been delivered; what was genuinely missing was the requirement **on the check itself**,
  so that a later rewrite could not satisfy it with an assertion that passes against a hardcoded
  template.

- **The web audit log page shows `commit_hash` and `related_entity_id`**, so the interface no
  longer shows less than the log holds. The presentation is **bound** to the task detail modal's,
  not reimplemented: a test extracts the relevant function body from the served JavaScript and
  fails if the placeholder or either class set diverges, in both directions. The hash renders
  verbatim; abbreviation is the stylesheet's and never the renderer's. Responsiveness was measured
  with headless Chromium at eight widths from 320 to 1920, with the harness itself controlled.

## Known Issues

**This section was rebuilt from scratch for this release.** Every item below was
verified against the code at this tree by running it. Items that `1.15.0` listed were
re-checked the same way rather than copied forward, and those that no longer hold have
been dropped. The historical entries in `CHANGELOG.md` are left exactly as written —
they record what was known at the time, and editing them would destroy the record
rather than correct it.

### Resolved and Therefore Not Carried Forward

- **The graph read path built an in-memory engine where the specification required a
  store-backed one**, recorded under `[1.15.0]` as task #149 and **settled in this
  release**. The owner decided, before any change, that the **specification** was wrong
  and the code was right: `recovery.Open` returns a graph already carrying the last
  committed state, so a store-backed engine over that same state would observe the same
  graph, and making the read path store-backed would have opened a write-ahead-log
  writer on a path that commits nothing. Two further faults were found in the same
  passage — the old parenthetical named three of GoGraph's six constructors, and
  `SPEC/WEB.md` carried a second instance of the same false claim. `SPEC/GRAPH.md
  § Engine Constructor by Path` is now the single authoritative statement, and
  `internal/testenv/engine_constructor_gate_test.go` holds the tree to it, assigning
  each construction site to its table row **without** looking at the constructor —
  because assigning by constructor would let a changed constructor slide the site to
  whichever row accepts it.

- **Two knowledge-graph nodes shared the key `README.md`**, recorded under `[1.15.0]`
  as task #155 and **fixed in this release**. Every `Spec` node is now keyed by its
  repository-relative path, and the model's own Conventions section already stated that
  rule — it was the label table that dissented. `MATCH (n {key:'README.md'})` now
  returns exactly one row. A different instance of the same class remains open and is
  listed below.

- **The local lint gate ran at an unpinned version**, recorded under `[1.15.0]`. The
  gate for this release was run at the pinned `v2.12.2`. The `PATH` hazard that caused
  it is described below, because it has not gone away.

### Open

Ordered by what actually affects a user of this release.

- **A stranded `snapshot.bak` stops every later graph checkpoint, and the write still
  exits 0.** Upstream GoGraph behaviour, unchanged this release — the dependency did not
  move, and it remains pinned at v0.11.0 — and the one item here that can affect you in
  normal use. **Reproduced on this tree, not carried forward on trust:** with a
  non-removable `snapshot.bak` present, `rmp graph create` wrote

  ```
  {"ok": true}
  ```

  to stdout at **exit 0**, and only stderr said anything:

  ```
  Warning: graph checkpoint failed: snapshot write: snapshot: archive live snapshot:
  rename .../graph/snapshot .../graph/snapshot.bak: file exists
  ```

  The exit code is required behaviour, not an oversight: a checkpoint failure *after* a
  durable commit must not fail the write, because the commit is already durable and the
  write-ahead log is intact.

  - **No data is lost.** Verified in the same run: both the node written before the
    obstruction and the node written during it read back correctly afterwards.
  - **Automation can miss it.** The exit code is 0 and stdout is the normal success
    JSON; only stderr says anything.
  - **The WAL grows without bound** while the condition lasts, because only a successful
    checkpoint truncates it.

  It **self-heals**: remove `snapshot.bak` from `~/.roadmaps/<roadmap>/graph/` and the
  next write checkpoints and truncates normally. Watch stderr on `rmp graph create`,
  `rmp graph update`, and `rmp graph delete`.

- **`rmp audit stats` exits `4` for a missing roadmap while its published contract
  declares only `{0, 3, 6}`.** Verified by execution on this tree:
  `rmp audit stats -r no-such-roadmap` exits **4** with
  `Error: resource not found: roadmap "no-such-roadmap"`. An agent branching on the
  contract's `exit_codes` array will not expect it. The behaviour is correct; the
  declaration is incomplete.

- **`DOCS/commands/stats.md` omits exit code `2`, and so does the contract array behind
  it.** Verified by execution: `rmp stats -r <name> <token>` exits **2** through the
  CLI-wide arity rule, while the page publishes only `0`, `3`, and `4` and the registry
  declares `{0, 3, 4}`. This is the worse shape of the defect `roadmap` had, because
  page, array, and help block all agree and all three are wrong. The same sweep reported
  **17 array-versus-help disagreements across 15 subcommands**; the two `roadmap` arrays
  were corrected in this release and the rest were left, being outside the recorded
  defect.

- **`SPEC/COMMANDS.md` publishes a `sprint close` refusal that the binary does not
  write.** The row states exit `6` with the sentinel `invalid input:`, which the
  catalogue maps to exit `2`, so the row contradicts itself as well as the binary.
  Verified by execution: the binary writes
  `Error: validation error: sprint #1 has 1 active task(s) still in progress: #1 (DOING) — use --force to close anyway`
  at exit `6`. The row is invisible to the error-string parity gate because a cell is
  promoted to a published string only when it contains `Error:`, and this one omits the
  prefix. A sweep that inverted the gate's own predicate — 85 tables, 54 error tables,
  286 cells — reported **fifteen further spans** in the sprint region that publish a line
  the binary does not write, every one diverging in wording and not merely in the
  missing prefix. None was corrected: they are new findings, and both sprints fixed
  exclusively what was already recorded.

- **`task list --created-since` and `--created-until` accept both date forms and never
  state the first-instant reading.** The trap that `audit list` now documents — a bare
  date meaning `00:00:00.000Z`, so an upper bound excludes the day it names — applies
  identically here and is documented only on `audit`.

- **`--order` is spelled two ways in its own refusals**, `--order` at the command site
  and `order` in the model. It is invisible to the gate that converged the other range
  rules, because that gate keys on the phrase `must be between` and this rule does not
  use it.

- **Two nodes of the project's own knowledge graph share the key
  `tests/run_tests.py`.** `SPEC/GRAPH.md § Node Key Uniqueness`, published in this
  release, states that a node's `key` is globally unique so that
  `MATCH (n {key:'...'})` without a label is unambiguous. Verified by execution on this
  tree: the key is carried by both a `CodeFile` node and a `Test` node. It is the same
  shape as the `README.md` pair task #155 closed by rekeying, and it is a defect in the
  model — the file genuinely is both — rather than a duplicate to delete. This concerns
  the project's own internal knowledge graph, not any user's roadmap data, and no `rmp`
  command output.

- **On a machine with the snap package installed, `make lint` silently runs the wrong
  linter.** `/snap/bin/golangci-lint` precedes `/home/flavio/go/bin` on the default
  `PATH`, and `SPEC/BUILD.md § Linter` states that a tool's version is part of its
  definition. The `Makefile` deliberately runs whatever `PATH` resolves and says so in a
  comment, so this is an environment hazard rather than a code defect, but it is one
  that produces a green gate that is not the gate the specification defines. Confirm
  with `golangci-lint --version` before trusting a local `make check`; the CI job runs
  the pinned version and is authoritative.
