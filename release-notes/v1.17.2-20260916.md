# Release Notes — Groadmap v1.17.2

**Date:** 2026-09-16
**Type:** Patch by the owner's decision — **but it changes the version line, refuses flags and help tokens it used to act on, changes the outcome of a no-field `task edit`, and makes the web graph endpoint refuse plan statements** (see [Breaking Changes](#breaking-changes))
**Tag:** `v1.17.2`
**Previous release:** `v1.17.1` (2026-09-14)

---

## Executive Summary

Groadmap `v1.17.2` makes the command line do what its specification says with the
arguments it is given. An unrecognised flag is refused wherever it is written, and never
discarded. A help token asks for help only where it stands as a token. A `task edit` with
no fields checks the task it names. The help's exit codes are generated from the AI Agent
Contract. The release also takes the graph engine to GoGraph `v0.14.2`, whose four fixes
make the effect a statement reports equal the effect it applied, and it names the build in
the version line.

**Read the breaking list before you upgrade, because the version number will not warn
you.** A strict SemVer reading of this release gives `MAJOR`. The project publishes
`1.17.2` by the owner's explicit decision, recorded in
[Why This Is Released as `1.17.2`](#why-this-is-released-as-1172-and-what-that-number-hides).

The seven incompatibilities:

1. **`rmp --version` names the build:** `Groadmap version 1.17.2 (commit <commit>)`.
2. **An unrecognised flag written after or between positional arguments is refused**
   with exit code `2` and the unknown-flag line, before the roadmap is opened.
3. **The word `help` is a flag's value when written as one**, and no longer prints the help.
4. **`-r help` is refused** as a reserved roadmap name, with exit code `6`.
5. **`graph serve`, `graph client` and `web` name an unknown flag without its `=value`.**
6. **A no-field `rmp task edit` on a missing task or roadmap exits `4`**, where it exited `0`.
7. **The web graph data endpoint refuses `EXPLAIN` and `PROFILE`** with HTTP `400` and a
   new error `kind`, `plan_prefix`.

There is **no database migration**. The dependencies move to GoGraph `v0.14.2`,
`golang.org/x/text v0.42.0`, `golang.org/x/sys v0.48.0` and `modernc.org/sqlite v1.59.0`.

---

## Highlights

- **A misspelled flag no longer deletes data.** `rmp roadmap remove <name> --foo` removed
  the roadmap on `1.17.1`; it is now refused, and nothing is removed.
- **The graph engine's report matches its effect.** A `SET` that could not store its value
  now fails instead of reporting success. Before, the replacing form also erased the
  node's properties. An undirected `SET` writes both relationships of a pair, and
  `DROP INDEX … IF EXISTS` reports nothing when it removes nothing.
- **Every help lists the exit codes the contract declares**, word for word, because the
  block is generated from the same registry.
- **`rmp graph client` accepts `--query=<cypher>`**, and `rmp graph serve` accepts
  `--socket=<path>`.
- **A released binary names its commit**, and the release workflow refuses to upload one
  that cannot.

## Breaking Changes

Each row below was driven against a binary built from the `v1.17.1` tag and one built from
this release's tree, under an isolated `HOME` (see
[Surface Comparison Against `v1.17.1`](#surface-comparison-against-v1171)).

### 1. The version line names the build

`rmp --version`, `rmp -v` and `rmp version` append the commit the binary was built from.
The Go toolchain records that commit at build time, and the line takes one of three
shapes (`SPEC/COMMANDS.md § Version`, `SPEC/VERSION.md § Build Identification`):

```
# 1.17.1
Groadmap version 1.17.1

# 1.17.2
Groadmap version 1.17.2 (commit <commit>)            # a build from a clean git checkout, as every released binary is
Groadmap version 1.17.2 (commit <commit>, modified)  # a build from a tree with uncommitted changes
Groadmap version 1.17.2 (commit unknown)             # no version-control data, e.g. go run or go install
```

`<commit>` is exactly the first seven characters of the commit hash. The line still
begins with `Groadmap version <version>`, so the version is still its third
whitespace-separated word. `1.17.1`'s specification did not publish the line's exact
form. `SPEC/DATA_FORMATS.md` gave `Groadmap version 1.3.0` only as an example.

**The test to apply:** you are unaffected unless a program compares the whole line with
`Groadmap version <version>`, or reads anything after the version.

### 2. An unrecognised flag after or between positional arguments is refused

The 31 `task`, `sprint`, `roadmap`, `backlog` and `audit` subcommands that read their
positional arguments by position now apply the CLI-wide unknown-flag refusal to a
`-`-prefixed token that stands in no positional slot. The refusal exits `2`, writes
`Error: invalid input: unknown flag: <flag>` and nothing to stdout, and precedes every check
that needs the roadmap and every side effect (`SPEC/COMMANDS.md § Positional Arguments`,
criteria 11 to 18).

| Invocation | `1.17.1` | `1.17.2` |
|---|---|---|
| `rmp roadmap remove <name> --foo` | exit `0`, the roadmap removed | exit `2`, `Error: invalid input: unknown flag: --foo`; nothing removed |
| `rmp task remove -r <name> 1 --foo` | exit `0`, the task removed (two tasks before, one after) | exit `2`, the unknown-flag line; both tasks remain |
| `rmp sprint get -r <name> <missing-id> --foo` | exit `4`, `Error: resource not found: sprint 1` | exit `2`, the unknown-flag line |
| `rmp task add-dep -r <name> 1 --foo 2` | exit `2`, `Error: invalid input: invalid dependency task ID: "--foo" (must be a positive integer)` | exit `2`, the unknown-flag line |
| `rmp task prio -r <name> 1 --foo 3` | exit `6`, `Error: validation error: invalid priority: must be 0-9`; priority unchanged | exit `2`, the unknown-flag line; priority unchanged |
| `rmp audit history -r <name> TASK --foo 1` | exit `2`, `Error: invalid input: invalid entity ID: "--foo" (must be a positive integer)` | exit `2`, the unknown-flag line |

The first three rows are the fix described under
[A misspelled flag after the positional arguments was discarded](#a-misspelled-flag-after-the-positional-arguments-was-discarded).
The last three are the between-positionals case. `1.17.1`'s `SPEC/COMMANDS.md` published
the slot's own refusal for `task add-dep`, `task remove-dep` and the five sprint ordering
commands, and that is the behaviour that changes.

**Unchanged:** a `-`-prefixed token written before the first positional argument, or with
no positional argument after it, still stands in that slot, and the slot's own check still
refuses it: `rmp task get -r <name> --foo` exits `2` with the malformed-id line.

**The test to apply:** you are unaffected unless an invocation writes a flag the
subcommand does not declare after or between its positional arguments.

### 3. The word `help` written as a flag's value is that value

`1.17.1`'s `SPEC/HELP.md` said that each family handler serves `--help`, `-h` and the word
`help` "anywhere in its argument list". `1.17.2` serves a help token only in a **token
position**, which is every position except the value of a flag that the subcommand
declares with a value (`SPEC/HELP.md § Help tokens`). A token carrying `=`, such as
`--help=1`, is not a help token, as it already was not.

| Invocation | `1.17.1` | `1.17.2` |
|---|---|---|
| `rmp task create -r <name> -t help -fr … -tr … -ac …` | exit `0`, the help; nothing created | exit `0`, `{"id": N}`; a task titled `help` |
| `rmp graph client -r <name> --query=help`, with a server running | exit `2`, `Error: invalid input: unknown flag: --query=help` | exit `1`, `Error: graph engine error: graph query failed: cypher: parse: unexpected "help" at 1:0, …`: the statement `help` was sent |
| `rmp task list -r <name> --foo help` | exit `0`, the help | exit `0`, the help (unchanged: a flag the subcommand does not declare takes no value) |

**The test to apply:** you are unaffected unless an invocation passes the word `help` as a
flag's value and expects the help.

### 4. `help` is a reserved roadmap name

| Invocation | `1.17.1` | `1.17.2` |
|---|---|---|
| `rmp task list -r help` | exit `0`, the help | exit `6`, `Error: validation error: "help": roadmap name is a reserved system name` |

`rmp roadmap create help` and `rmp roadmap remove help` still print their help and do
nothing, because `help` stands in a token position there. No command could ever act on a
roadmap of that name, and the reservation says so (`SPEC/COMMANDS.md § Roadmap Name
Validation`). A directory named `help` made outside the CLI is listed by
`rmp roadmap list` and reachable by no command, like one named `con`.

**The test to apply:** you are unaffected unless an invocation passes `-r help` or
`--roadmap help`.

### 5. `graph serve`, `graph client` and `web` name an unknown flag without its `=value`

| Invocation | `1.17.1` | `1.17.2` |
|---|---|---|
| `rmp graph serve -r <name> --zzz=1` | exit `2`, `Error: invalid input: unknown flag: --zzz=1` | exit `2`, `Error: invalid input: unknown flag: --zzz` |
| `rmp graph client -r <name> --zzz=1 -q …` | exit `2`, `Error: invalid input: unknown flag: --zzz=1` | exit `2`, `Error: invalid input: unknown flag: --zzz` |
| `rmp web --zzz=1` | exit `2`, `Error: invalid input: unknown flag: --zzz=1` | exit `2`, `Error: invalid input: unknown flag: --zzz` |

The other commands already named the flag this way. `SPEC/COMMANDS.md § Positional
Arguments`, rule 5, now states it for every command.

**The test to apply:** you are unaffected unless a program matches the unknown-flag line of
one of these three commands, including the `=value`.

### 6. A no-field `rmp task edit` checks the roadmap and the task

`1.17.1`'s `SPEC/COMMANDS.md § Edit Task` published "If no fields are specified, command
succeeds with no changes (exit code 0)", and the binary returned before it opened the
roadmap. `1.17.2` makes the invocation face every check a field-carrying edit faces,
except the checks on field values, in the same order.

| Invocation | `1.17.1` | `1.17.2` |
|---|---|---|
| `rmp task edit -r <name> 999` (no such task) | exit `0` | exit `4`, `Error: resource not found: task 999 not found` |
| `rmp task edit -r <missing> 1` | exit `0` | exit `4`, `Error: resource not found: roadmap "<missing>"` |
| `rmp task edit -r Bad_Name 1` | exit `0` | exit `6`, `Error: Roadmap name must only contain lowercase letters, numbers, underscores, and hyphens` |
| `rmp task edit -r <name> <existing-id>` | exit `0`, nothing changed | exit `0`, nothing changed, no audit entry |

**The test to apply:** you are unaffected unless you run `rmp task edit` with no field
flags and rely on exit `0` when the task or the roadmap may not exist.

### 7. The web graph data endpoint refuses `EXPLAIN` and `PROFILE`

`1.17.1`'s `SPEC/GRAPH.md` said a statement from the web query bar behaves exactly as it
does through `rmp graph client`. The endpoint's response carries nodes and edges and has
no place for a query plan, so an `EXPLAIN` rendered as an empty graph, indistinguishable
from a statement that matched nothing. `1.17.2` asks the engine's own parser whether the
statement carries a prefix, and refuses it without sending it
(`SPEC/WEB.md § Query-Bar Error Handling`, rule 12).

| `GET /roadmaps/{name}/graph/data?q=…` | `1.17.1` | `1.17.2` |
|---|---|---|
| `EXPLAIN MATCH (n) RETURN n` | HTTP `200`, `{"nodes": [], "edges": []}` | HTTP `400`, `plan_prefix` |
| `PROFILE MATCH (n) RETURN n` | HTTP `200`, the nodes | HTTP `400`, `plan_prefix` |
| `MATCH (n) RETURN n` | HTTP `200`, the nodes | HTTP `200`, the nodes |

The refusal body:

```json
{
  "error": "query not run: the query bar cannot show a query plan; remove the EXPLAIN or PROFILE prefix, or run the statement with rmp graph client",
  "kind": "plan_prefix"
}
```

**The error object's `kind` gains a third value**, beside `invalid_limit` and `execution`
(`SPEC/DATA_FORMATS.md`). The `limit` is resolved first and the prefix second, both
before any server is looked up, so a prefixed statement is refused with `400` even when no
graph server is running. `rmp graph client` still runs both prefixes.

**The test to apply:** you are unaffected unless a client of the graph data endpoint sends
a prefixed statement, or handles `kind` as a closed set of two values.

## New in This Release

### `rmp graph serve` and `rmp graph client` accept the joined flag form

`--socket=<path>`, `--query=<cypher>` and `-q=<cypher>` are read exactly as the separate
forms are, and the value is the text after the first `=`, later `=` characters included.
`--socket=` and `--query=` supply an empty value, which is the missing-parameter error. The
roadmap selector is still read in the separate form only: `--roadmap=<name>` selects no
roadmap, and the invocation exits `3` (`SPEC/COMMANDS.md § Serve Options` and
`§ Client Options`; `SPEC/GRAPH.md § Cypher Input Source and Precedence`, rule 4).

| Invocation | `1.17.1` | `1.17.2` |
|---|---|---|
| `rmp graph client -r <name> --query="RETURN 1 AS one"` | exit `2`, `Error: invalid input: unknown flag: --query=RETURN 1 AS one` | exit `0`, `{"columns": ["one"], "rows": [[1]]}` |
| `rmp graph serve --roadmap=<name>` | exit `3`, `Error: no roadmap selected: use -r <name> or --roadmap <name>` | exit `3`, the same line (unchanged) |

## What Was Silently Wrong Before

### A misspelled flag after the positional arguments was discarded

Thirty-one subcommands read their positional arguments by position and never looked at
the tokens left after them. `SPEC/COMMANDS.md § Positional Arguments`, rule 5, already
required an unrecognised flag to be refused. Instead, the command did its work:
`rmp roadmap remove <name> --foo` deleted the roadmap at exit `0`. `rmp sprint add-tasks`
also read every token after the sprint id as part of its id list, so such a flag was
refused as a malformed task id. It now reads only its second positional argument as the
list. See [Breaking Changes, 2](#2-an-unrecognised-flag-after-or-between-positional-arguments-is-refused).

### The graph engine reported effects it had not applied

GoGraph `v0.14.2` fixes four defects, and `rmp graph client` exposed each of them. Driven
against both binaries through a running server:

| Statement | `1.17.1` (GoGraph `v0.14.1`) | `1.17.2` (GoGraph `v0.14.2`) |
|---|---|---|
| `MATCH (a {key:'a'}), (b {key:'b'}) SET a.ref = b` | exit `0`, `{"ok": true}`; nothing stored | exit `1`; node `a` unchanged |
| `MATCH (a {key:'a'}), (b {key:'b'}) SET a = {other: b}` | exit `0`, `"propertiesWritten": 2`; **node `a` left with no properties at all** | exit `1`; node `a` keeps `key` and `name` |
| `MATCH (a)-[r:R]-(b) SET r.w = 1` over `a→b` and `b→a` | two rows, `"propertiesWritten": 2`; `r.w` reads back `null` and `1` | two rows, `"propertiesWritten": 2`; `r.w` reads back `1` and `1` |
| `DROP INDEX nope IF EXISTS` (no such index) | exit `0`, `"indexesRemoved": 1` | exit `0`, `{"ok": true}`, no counters |

- **#2816 — a property value the engine cannot store.** A node, a relationship or a path
  assigned to a property was dropped while the statement reported success. On a replacing
  form, the dropped entry still cleared the element's existing properties. The engine now
  raises `InvalidPropertyType`. The caller reads the ordinary engine failure at exit `1`,
  with generic text, as [Known Issues](#known-issues) describes.
- **#2817 — an undirected `SET` over a reciprocal pair.** Both rows addressed the same
  stored relationship. `SPEC/GRAPH.md § What Groadmap Does Not Check`, item 4, is narrowed
  to `REMOVE`, because every assignment form now reaches the relationship the pattern
  bound, in either direction.
- **#2818 — `DROP INDEX … IF EXISTS`** counted a removal that never happened.
- **#2819 — three client faults were masked as "An internal error occurred".** They now
  cross the server as client errors, so `rmp graph client` writes the engine's diagnostic
  after `Error: graph engine error: graph query failed: `, still at exit `1`. Two of the
  three were driven against both binaries:

  | Statement | `1.17.1` | `1.17.2` |
  |---|---|---|
  | `CREATE (:<a 70000-byte label>)` | `… graph query failed: An internal error occurred. See server logs for details (session: <id>).` | `… graph query failed: txn: field too long for its WAL length prefix: node label is 70000 bytes, maximum 65535` |
  | `CREATE CONSTRAINT … REQUIRE n.title IS NOT NULL` over a node that has no `title` | `… graph query failed: An internal error occurred. See server logs for details (session: <id>).` | `… graph query failed: cypher: cannot create NOT NULL constraint on (:Spec).title: exec: constraint violation: pre-existing node has a null value` |

  The third, an unsupported schema definition, is stated by GoGraph's changelog and was
  not reproduced here: the statement tried, `CREATE FULLTEXT INDEX …`, is a parse error
  under both binaries.

### The help's exit codes contradicted the contract

Twenty-nine subcommand helps omitted exit codes that their AI Agent Contract entry
declared. The `Exit codes` block of all 55 subcommand helps is now rendered from the
command registry, which also generates the contract. Codes appear in the contract's order,
code `0` included, each followed by its conditions word for word, wrapped at 80 code
points. `graph client` keeps the two remedies its code `1` entry carries. The block
changes wording and layout on every subcommand help; see
[Surface Comparison](#surface-comparison-against-v1171).

### The contract omitted conditions the binary produces

- Nine subcommands that refuse an id outside `1`-`2147483647` with exit `6` declared no
  code `6`, and now do: `sprint get`, `show`, `remove`, `open-tasks` and `stats`, and
  `task subtasks`, `remove-dep`, `blockers` and `blocking`. The subcommands that already
  declared code `6` gain the range condition beside their others.
- `sprint move-tasks` declares its refusals of a `CLOSED` source or destination sprint.
- `sprint update` declares the code-`2` refusal of an invocation that supplies no field.
- `task stat` declares its missing positional argument.
- The 31 subcommands of [Breaking Changes, 2](#2-an-unrecognised-flag-after-or-between-positional-arguments-is-refused)
  declare the unknown-flag condition on code `2`.

`schema_version` stays `2.0.0`, and no key is added or removed.

### Two builds of different commits printed the same version line

The line now names the commit. Both release workflows build with `-buildvcs=true`, and
each build job runs `go version -m` on the binary it built and fails before upload when
the output carries no `vcs.revision`. No workflow passes `-X`, which the linker ignored for
the `version` constant anyway, and `SPEC/DEPLOY.md` no longer claims an `-X main.version`
flag (`SPEC/DEPLOY.md § How a Released Binary Carries Its Commit`).

### `install.sh` reinstalled an up-to-date `rmp` every time

`get_current_version` searched the version line for a `v` that the line never carried, so
it found no installed version and downloaded the release again. It now takes the third
word of the first line, provided the first two are `Groadmap version` and the third is
`MAJOR.MINOR.PATCH`. It then compares that word with the latest tag, minus its `v`, by
string equality. With the latest release installed, it prints `Current version: …` and
`Already up to date (…)`, and exits `0` without downloading. It reads the `1.17.1` line
and the `1.17.2` line alike (`SPEC/DEPLOY.md § Installed Version Detection`).

### `make lint` and `make security` ran whichever tool `PATH` found first

On the development machine, that was a snap `golangci-lint v2.13.2`, ahead of the pinned
`v2.13.1`. Both targets now run the binary in `go env GOBIN`, or else in the `bin`
directory of the first `GOPATH` entry. A caller can name another binary with
`GOLANGCI_LINT=` or `GOSEC=`. Each target refuses, naming both versions, a binary whose
version differs from the pin (`SPEC/BUILD.md § Local Tool Resolution`). A test holds the
`Makefile`'s copy of the pins equal to the specification's.

### Published error strings disagreed with the binary

`SPEC/COMMANDS.md § Published Error Strings Are Exact` now governs all eight specification
files that publish an error string, and undeclared placeholders were either declared or
replaced. `sprint close` publishes its active-task refusal and its `--force` warning, the
`sprint show` not-found row matches the binary, and `task add-dep` and `task remove-dep`
publish separate format and range rows for each id. `SPEC/GRAPH.md` no longer describes a
store fallback that does not exist: a client with no server exits `1` with the no-server
line. `tests/test_55_error_string_parity.py` reads the eight files and grows from 152 to
178 strings.

`gosec v2.28.0`.

## Known Issues

Each item is stated in the specification or in the code, as cited.

- **`modernc.org/libc` is a later release than `modernc.org/sqlite` requires**
  (`v1.76.0` against `v1.75.7`). The driver runs transpiled SQLite inside that C runtime,
  and its author requires the two versions to match. A defect caused by the mismatch would
  be a runtime defect in the storage engine, and no validation gate detects it. The
  project accepts the risk deliberately (`SPEC/BUILD.md § SQLite Driver Rules`, rules 2
  to 4).
- **A failed graph statement can replace an existing relationship.** A statement that
  creates a relationship between two nodes already joined in the same direction, and then
  fails before it commits, leaves one of the existing relationships replaced by the new
  one, with the new type and no properties. The caller still reads a line saying nothing
  was written. The replacement lives in the server's memory until a checkpoint makes it
  permanent (`SPEC/GRAPH.md § Error Handling and Exit Codes`, rule 9). This is an engine
  defect, and it is not new: the same statement driven against `1.17.1` replaced
  `OLD {p: 1}` with `NEW {}`, exactly as `1.17.2` does.
- **Three engine hazards report success** (`SPEC/GRAPH.md § What Groadmap Does Not
  Check`):
  - item 4: a relationship property `REMOVE` persists only where the pattern walked the
    relationship in its stored direction;
  - item 8: a relationship bound by `MERGE` or `CREATE` over a node pair that more than one
    relationship joins in the pattern's direction is not reliably the one matched or
    created;
  - item 9: a list property holding `null` is not stored as written.
- **A property value the engine cannot store is refused with generic text.** The caller
  reads `Error: graph engine error: graph query failed: An internal error occurred. See
  server logs for details (session: <id>).`. The engine's diagnostic, which names the key,
  goes only to the server's stderr (`SPEC/DATA_FORMATS.md § One Realisation of the
  Mapping`).
- **The published field-length line has no producer.** An over-long field arrives through
  the parse/execution line, ending in the engine's diagnostic, and not through the line
  `SPEC/COMMANDS.md § Client Error Cases` publishes for it (`SPEC/GRAPH.md § Field Length
  Limits`, rule 13).
- **The web query bar's prefix check runs outside the 5-second budget.** The engine's
  parser takes no context. On the development machine, the costliest input found at its
  1 MiB ceiling parsed in 2.44 s to 2.72 s and allocated 1.46 GiB, for one request
  (`internal/web/data.go`, `refusePlanPrefix`; rmp task #499).
- **`SPEC/DEPLOY.md § Release Checklist` still lists "Documentation updated
  (`SPEC/VERSION.md`, `SPEC/README.md`)".** The specification carries no version state
  (`SPEC/VERSION.md`), and this release changes neither file.

## Internal Changes

These change no output of the binary.

- **Test integrity.** Every test that cites a specification acceptance criterion now names
  the criterion it discusses. A new gate,
  `internal/testenv/spec_criterion_citation_gate_test.go`, fails when a citation exceeds
  its file's criteria count. The `test_70` probes now reach the paths they name, and
  several assertions that accepted any error now require the specific one.
- **`test_70` harness.** It no longer leaves `rmp graph serve` processes running after
  each run, and it fails, rather than leaks, when one survives. A server that hangs midway
  through its startup line now fails the start at its timeout.
- **A gate against the default logger.** `TestNoProductionCodeLogsThroughTheDefaultLogger`
  fails on any non-test call to `slog`'s package-level logging functions.
- **New end-to-end modules:** `test_71_install_version_detection`,
  `test_72_unknown_flag_beside_positionals`, `test_73_help_exit_codes_contract` and
  `test_74_help_tokens_and_joined_flags`.
- **Comments that restated measured figures** in `internal/backoff`,
  `internal/graphclient` and `internal/commands` now cite
  `SPEC/IMPLEMENTATION.md § Retry Logic`, which is canonical for them.

## Upgrade Notes

### Step 1 — If a program reads `rmp --version`, read the third word

```bash
rmp --version | awk '{print $3}'
# 1.17.2
```

### Step 2 — Remove undeclared flags written after or between positional arguments

Run each stored invocation once. An exit `2` naming an unknown flag names the token to
remove. A flag the subcommand declares is unaffected.

### Step 3 — Do not pass `help` as a flag value or as a roadmap name

A title, a query or another value of `help` is now stored or sent as written. `-r help`
exits `6`.

### Step 4 — Check the exit code of a no-field `rmp task edit`

It now exits `4` when the task or the roadmap does not exist, and `6` when the roadmap
name is invalid.

### Step 5 — Send plan statements through `rmp graph client`

The web graph data endpoint answers `EXPLAIN` and `PROFILE` with HTTP `400` and
`"kind": "plan_prefix"`. A client that switches on `kind` must accept that value.

### Step 6 — There is no database migration

The SQLite schema version is unchanged at `1.14.0`, and GoGraph `v0.14.2` changes no store
format (see [Store Round Trip](#store-round-trip)). A downgrade to `1.17.1` brings back the
four engine defects this release fixes.

### Step 7 — Install and verify

```bash
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install.sh | bash
rmp --version
# Groadmap version 1.17.2 (commit <commit>)
```

`<commit>` is the first seven characters of the commit the `v1.17.2` tag names, with no
`modified` marker (`SPEC/DEPLOY.md § Release Checklist`).

## Why This Is Released as `1.17.2`, and What That Number Hides

Semantic Versioning 2.0.0 requires the `MAJOR` version to be incremented "if any backward
incompatible changes are introduced to the public API". It permits a `PATCH` increment
only "if only backward compatible bug fixes are introduced". `SPEC/VERSION.md` defines
`PATCH` as "Bug fixes, backward compatible". This release changes seven behaviours that
`1.17.1` exhibited, listed under [Breaking Changes](#breaking-changes). Four of them had
been published by `1.17.1`'s own specification:

1. the refusal of a flag written between two positional arguments, which
   `SPEC/COMMANDS.md` gave as the slot's own line;
2. the help-token rule, which `SPEC/HELP.md` gave as "anywhere in its argument list";
3. the no-field `task edit`, which `SPEC/COMMANDS.md` gave as exit code `0`;
4. the web graph data endpoint, which `SPEC/GRAPH.md` said behaves as `rmp graph client`
   does.

The strict reading therefore gives `2.0.0`.

The project publishes `1.17.2` by the **owner's explicit decision**, taken on 2026-09-16
and recorded here.

This is the seventh consecutive release published under a smaller digit than the strict
reading gives, each by a decision recorded at the time:

1. `1.15.0` as a `MINOR`;
2. `1.15.1` as a `PATCH`;
3. `1.15.2` as a `PATCH`;
4. `1.16.0` as a `MINOR`, after it was first tagged as `2.0.0`, withdrawn and renumbered;
5. `1.17.0` as a `MINOR`;
6. `1.17.1` as a `PATCH`;
7. `1.17.2` as a `PATCH`.

**The `1.17.0` record is incomplete.** Its `CHANGELOG.md` entry says `1.17.0` was
published "on the same footing as its three predecessors", and names `1.15.0`, `1.15.2`
and `1.16.0`. It omits `1.15.1`, which had shipped breaking changes as a `PATCH` by the
owner's decision. That entry is left as published, and the omission is recorded here.

**Do not read the patch digit as a promise that nothing breaks.** The test to apply is
short:

> Upgrading is safe unless one of the following applies to you:
>
> - a program of yours matches the whole `rmp --version` line;
> - you write an undeclared flag after or between positional arguments, pass the word
>   `help` as a flag value, or pass `-r help`;
> - you match an unknown-flag line of `graph serve`, `graph client` or `web` including its
>   `=value`;
> - you rely on `rmp task edit` with no fields exiting `0` for a task or roadmap that may
>   not exist;
> - a client of yours sends `EXPLAIN` or `PROFILE` to the web graph data endpoint, or
>   treats its error `kind` as a closed set.

**What did not change, and why it does not soften the above.** No command, subcommand or
flag was removed. The top-level exit-code catalogue and the contract's `schema_version` are
unchanged. The graph server package, `internal/graphserve`, is unchanged apart from its
tests. There is no database migration. These are reasons the release is not *more* disruptive than it is; none of them
makes it a patch.

## What Is Not In This Release

- **No option to bound an idle session or a parked write.** `rmp graph serve` declares no
  timeout flag, and Groadmap arms no deadline of its own (`SPEC/GRAPH.md`).
- **No authentication or transport security on the graph server.** The socket's file
  permissions are the whole of the access control, and the engine prints a warning for
  each at startup.
- **No engine-side class for an over-long field.** See [Known Issues](#known-issues).
