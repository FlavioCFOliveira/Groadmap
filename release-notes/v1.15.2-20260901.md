# Release Notes — Groadmap v1.15.2

**Date:** 2026-09-01
**Type:** Patch by decision — **adds a feature and contains backward-incompatible changes** (see What Is New and Breaking Changes)
**Tag:** `v1.15.2`
**Previous release:** `v1.15.1` (2026-08-26)

---

## Executive Summary

Groadmap `v1.15.2` gives the knowledge graph a schema. `rmp graph update` becomes the
subcommand through which a roadmap's graph indexes and constraints are created, listed
and dropped. One sprint, five tasks, one feature commit.

**The version number tells you neither of the two things you need to know.** It does not
warn you that three published contracts were narrowed, and it does not announce that
there is something new to use. `SPEC/VERSION.md` defines `PATCH` as "Bug fixes, backward
compatible", and this release is neither purely one nor entirely the other. The number
is `1.15.2` by the project owner's explicit decision, taken after `1.16.0` was
recommended and `2.0.0` was considered. The reasoning is recorded in
[Why This Is Released as `1.15.2`](#why-this-is-released-as-1152) so that it can be
reviewed rather than inferred. If you drive `rmp` from a script, an agent, or a CI step,
read [Breaking Changes](#breaking-changes) before upgrading. If you use the knowledge
graph at all, read [What Is New](#what-is-new--schema-management-for-the-knowledge-graph),
because nothing else will tell you the feature exists.

**The sprint set out to survey the engine and found three defects of Groadmap's own.**
The plan was to establish what GoGraph offers, then expose it. What the survey
established instead was that of the four obstacles between Groadmap and index
management, **three were Groadmap's own and not one was visible from outside**:

- The graph checkpoint — which runs after **every** graph write — wrote a snapshot that
  carried no schema at all, and then truncated the write-ahead log in which the
  `CREATE INDEX` and `CREATE CONSTRAINT` events were the only surviving record.
- Both engine constructors then discarded whatever schema the store open did recover, so
  `SHOW INDEXES` reported an empty schema whatever the store held, at exit `0`.
- The web graph data endpoint answered a schema-introspection query with an empty graph
  and HTTP `200`, indistinguishable from a query that genuinely matched nothing.

**Together those made a `UNIQUE` constraint stop being enforced across a restart, and
admit duplicates in silence.** None of it was reachable through `rmp` on `1.15.1`,
because the guard rail refused every DDL clause on all five subcommands — which is
exactly what kept the defects invisible, and what would have made this release's feature
inert had the two shipped together.

The fourth obstacle is upstream and remains: the engine's DDL parser silently discards a
trailing clause. Groadmap refuses mixed statements itself for that reason, with a
structural check rather than a keyword scan.

The dependency moves to **GoGraph v0.12.0**, a non-breaking pre-1.0 `MINOR` release.
There is **no database migration**; the SQLite schema version is unchanged.

**No performance win is claimed, because none was measured**, and this document corrects
a figure the project had been repeating on the subject. See
[On Scale](#on-scale-and-a-figure-this-project-had-been-repeating).

## Highlights

- **NEW — `rmp graph update` is the schema subcommand.** Index and constraint DDL and
  schema introspection, on top of the `SET`/`REMOVE` it already accepted. It is the one
  `graph` subcommand that accepts more than one operation class, and it accepts three.
  The other four are unchanged.
- **NEW — indexes and constraints now survive.** A constraint created in one invocation
  keeps its declared name, is listed identically by `graph update`, `graph query` and
  `graph search`, and is **still enforced** in a later process: a duplicate is refused.
- **FIXED — the graph checkpoint erased every index and constraint definition from
  disk.** The operation meant to make the graph durable destroyed the schema declared
  over it. Measured: `Indexes=1` before the checkpoint, **`Indexes=0`** after.
- **FIXED — a `UNIQUE` constraint stopped being enforced across a restart.** The
  consequence of the above, and the one that costs data rather than convenience: the
  next process admitted the duplicate the constraint had refused, with no error anywhere.
- **FIXED — `SHOW INDEXES` on `graph query` and `graph search` reported an empty schema
  whatever the store held**, at exit `0`, because both engine constructors discarded the
  recovered schema.
- **BREAKING — the web graph data endpoint answers schema introspection with HTTP `400`,
  not `200`.** It used to return an empty graph and no explanation.
- **BREAKING — `invalid_keyword_spacing` leaves the web endpoint's published `kind`
  enum**, replaced by `schema_introspection`. Removing a published value is a contract
  narrowing, and it was chosen deliberately.
- **BREAKING — the `graph update` operation-class refusal string is retired and
  replaced.** Same exit code, same condition, different words.
- **Dependency: GoGraph `v0.11.0` → `v0.12.0`**, adopted for a constructor introduced
  there that hydrates each index from the snapshot instead of rebuilding it by a full
  graph scan on every invocation.
- **UPGRADE HAZARD — do not run a `1.15.1` or older binary against a graph that carries
  schema.** Its first successful write destroys the schema and disables enforcement,
  silently. See [Upgrade Notes](#upgrade-notes).

## What Is New — Schema Management for the Knowledge Graph

`rmp graph update` mutates existing graph elements, and is now also the subcommand
through which the graph's schema is managed. It is the only `graph` subcommand that
accepts more than one operation class, and it accepts three: a `SET`/`REMOVE` write,
schema-mutating DDL, and schema introspection.

`graph create`, `graph query`, `graph delete` and `graph search` are **unchanged**. They
keep refusing every DDL clause, and `query` and `search` keep accepting schema
introspection as the read-only class it already was.

The surface is raw Cypher through the existing `--query` / standard-input path. There is
no structured `index` verb; the engine's own DDL is what you write.

### Accepted statements

```
CREATE INDEX [name] [IF NOT EXISTS] FOR (n:Label) ON (n.property)
                                    [OPTIONS {indexType: 'hash' | 'btree'}]
DROP INDEX <name> [IF EXISTS]

CREATE CONSTRAINT [name] [IF NOT EXISTS] FOR (n:Label)
                         REQUIRE n.property IS UNIQUE | IS NOT NULL
DROP CONSTRAINT <name> [IF EXISTS]

SHOW INDEXES | SHOW CONSTRAINTS
    (singular aliases SHOW INDEX and SHOW CONSTRAINT accepted;
     optional YIELD / WHERE / RETURN tail)
```

Constraints are in scope deliberately, beyond the sprint's own title, so that one
subcommand owns the schema rather than two-thirds of it.

### A worked example

Each command below is a separate process invocation, and that is the point: the schema
survives between them, which before this release it did not.

```bash
rmp graph update -r myproject --query "CREATE INDEX spec_key FOR (n:Spec) ON (n.key)"
# {"ok": true}                                                        exit 0

rmp graph update -r myproject --query "SHOW INDEXES"
# {"columns":["name","state","type","entityType","labelsOrTypes","properties"],
#  "rows":[["spec_key","ONLINE","hash","NODE",["Spec"],["key"]]]}     exit 0

rmp graph query  -r myproject --query "SHOW INDEXES"
# identical listing — the three CLI surfaces agree                    exit 0

rmp graph update -r myproject --query "DROP INDEX spec_key"
# {"ok": true}                                                        exit 0
```

And a constraint, with the property that matters:

```bash
rmp graph update -r myproject \
  --query "CREATE CONSTRAINT spec_key_uq FOR (n:Spec) REQUIRE n.key IS UNIQUE"
# {"ok": true}                                                        exit 0

rmp graph create -r myproject --query "CREATE (n:Spec {key:'auth'})"
# {"ok": true}                                                        exit 0

rmp graph create -r myproject --query "CREATE (n:Spec {key:'auth'})"
# Error: database error: graph create failed: exec: constraint violation:
#   UNIQUE constraint on (Spec).key: value "auth" already exists      exit 1
```

The third invocation is the release. On `1.15.1` the definition would have been gone
from disk before that command ran, and the duplicate would have been stored.

### Index kinds, shape, and naming

- **Kinds are `hash` (the default) and `btree`**, selected with
  `OPTIONS {indexType: 'btree'}`. They are GoGraph's own vocabulary and deliberately not
  Neo4j's `RANGE`/`TEXT`/`POINT`.
- **An index or a constraint covers a single node property.** Composite and
  relationship-property forms are refused by the engine.
- `SHOW INDEXES` yields `name`, `state`, `type`, `entityType`, `labelsOrTypes`,
  `properties`, ordered deterministically by name. `state` is always `ONLINE`, because
  every index is built synchronously, and `entityType` is always `NODE`.
- **A declared name is used verbatim**, with no suffix appended. **An omitted name is
  derived** as `<lowercased label>_<property>_<type>`, so
  `CREATE INDEX FOR (n:Spec) ON (n.title)` becomes `spec_title_hash`.
- **Removal is by name only.** `SHOW INDEXES` is the authoritative report of the name an
  unnamed object was given.

### Altering and recreating are two invocations, and cannot be atomic

**The engine has no `ALTER INDEX`.** `REBUILD INDEX` and `CREATE OR REPLACE INDEX` do not
exist either. All three were probed directly against the parser at v0.12.0 rather than
inferred from documentation, and each fails identically with
`cypher: parse: unexpected "<KEYWORD>" at 1:0`.

Changing an index is therefore:

```bash
rmp graph update -r myproject --query "DROP INDEX spec_ord"
rmp graph update -r myproject \
  --query "CREATE INDEX spec_ord FOR (n:Spec) ON (n.ord) OPTIONS {indexType:'btree'}"
```

Two invocations, and **they cannot be made atomic**. Atomicity is not merely absent but
unreachable: schema DDL does not run inside a transaction, so no invocation can wrap the
pair. **Between the two, the index does not exist**, and a failure of the second half
leaves it dropped and not recreated. Recreating an index — a rebuild — is the same pair
with an identical definition. Both halves are O(N) in the label's population, because
`CREATE INDEX` back-fills from the data already in the graph.

### One statement per invocation

A schema statement carrying a further clause is refused with exit `6`, before the store
is opened:

```bash
rmp graph update -r myproject \
  --query "CREATE INDEX ix FOR (n:Spec) ON (n.key) MATCH (m:Spec) SET m.reviewed = true"
# Error: validation error: graph update accepts one schema statement per invocation,
#   and this query carries "MATCH (m:Spec) SET m.reviewed = true" after it. ...
#                                                                     exit 6
```

**Groadmap refuses this rather than delegating it, and the refusal is load-bearing.** The
engine's schema parser stops as soon as its grammar is satisfied and discards whatever
follows with no error and no notification, returning success — so unrefused, the command
would create the index, drop the `MATCH ... SET`, print `{"ok": true}` and exit `0` for a
statement half of which never ran. See
[The Upstream Defect That Remains](#the-upstream-defect-that-remains).

**The check is structural, not a keyword scan.** It walks the engine's own DDL grammar to
find where the statement ends, so a property legitimately named after a clause is
accepted:

```bash
rmp graph update -r myproject --query "CREATE INDEX spec_set FOR (n:Spec) ON (n.set)"
# {"ok": true}                                                        exit 0
```

Before refusing, the grammar mirror is checked against the engine's real parser: the
refusal stands only when the isolated head's plan is identical to the whole statement's.
On disagreement the query is **admitted** and the engine decides, so a mirror that drifts
from the engine fails open rather than closed.

### Output shape

| Statement | Output | Exit |
|-----------|--------|------|
| `CREATE INDEX`, `DROP INDEX`, `CREATE CONSTRAINT`, `DROP CONSTRAINT` | `{"ok": true}` | 0 |
| `SHOW INDEXES`, `SHOW CONSTRAINTS` | `{"columns": [...], "rows": [[...]]}` | 0 |

A schema-introspection command returns the `{columns, rows}` listing **although it
carries no `RETURN` clause**. `SPEC/DATA_FORMATS.md § Graph Write Result` therefore
changes its discriminator from "has a `RETURN` clause" to "produces result columns". For
every data-writing query the two coincide exactly; they part company only on the schema
statements, and the old wording had been false since before this release for a reason
nobody had noticed.

### Failure classes and their exit codes

Two of these are the opposite of what a reader expects.

| Failure | Exit | Who refuses |
|---------|------|-------------|
| Operation-class mismatch under `graph update` | **6** | Guard rail |
| `SHOW` whose two keywords are not separated by exactly one space | **6** | Guard rail |
| A second clause after a schema statement | **6** | Guard rail |
| Duplicate `CREATE INDEX` / `CREATE CONSTRAINT` | **1** | Engine |
| `DROP` naming an object that does not exist | **1** | Engine |
| A definition the engine does not support | **1** | Engine |
| `CREATE CONSTRAINT` the existing data does not satisfy | **1** | Engine |
| DDL whose keywords are irregularly spaced | **1** | Engine (parse error) |

Groadmap cannot know whether an object exists without opening the store, so that check
belongs to the engine and arrives as a database error. Write `IF NOT EXISTS` or
`IF EXISTS` to make a create or a drop a silent no-op instead of a failure.

The last row is a deliberate, specified cost rather than an oversight. The DDL matcher is
tolerant of whitespace **because its job on the other four subcommands is to refuse**;
narrowing it to produce a better diagnostic on `update` would reopen the hole those four
depend on. `CREATE  INDEX ix FOR (n:Spec) ON (n.key)` with two spaces is admitted by the
guard rail and refused by the engine's grammar at exit `1`. Nothing is created, and the
graph is byte-identical afterwards.

### Help and the AI contract

Both `rmp graph --help` and `rmp graph update --help` document the accepted statements,
the one-statement rule, the absent `ALTER INDEX`, and both exit codes. The
machine-readable contract gains two pitfalls,
`graph_schema_two_statements_in_one_query` and `graph_schema_failure_exit_code`, and
`graph_guard_rail_mismatch` is rewritten to say that `update` accepts three classes.

## Breaking Changes

**Three published contracts were narrowed.** Each breaks an invocation that succeeded on
`1.15.1`. A fourth change was reported as breaking and, measured, is not; it is recorded
below with the measurement rather than left out.

Every before/after in this section was produced by running **both binaries** against the
same store, not by reading the diff.

### 1. The web graph data endpoint refuses schema introspection: HTTP `200` becomes `400`

`GET /roadmaps/<roadmap>/graph/data?q=SHOW INDEXES` returned `{"nodes":[],"edges":[]}` at
HTTP `200` against a store that held indexes. The user saw an empty graph, and nothing
distinguished that from a query which genuinely matched nothing.

| Request | On `1.15.1` | On `1.15.2` |
|---------|-------------|-------------|
| `?q=SHOW INDEXES` | `200`, `{"nodes":[],"edges":[]}` | **`400`**, `kind: schema_introspection` |
| `?q=SHOW CONSTRAINTS` | `200`, `{"nodes":[],"edges":[]}` | **`400`**, `kind: schema_introspection` |
| `?q=SHOW  INDEXES` (two spaces) | `400`, `kind: invalid_keyword_spacing` | **`400`**, `kind: schema_introspection` |
| `?q=MATCH (n) RETURN n` | `200` | `200` — unchanged, asserted as the control |

The body now reads:

```json
{
  "error": "query rejected: this page draws a graph of nodes and edges, and a schema listing is neither, so it cannot be shown here. Run rmp graph query to report the indexes and constraints the store holds.",
  "kind": "schema_introspection"
}
```

The refusal happens **before the store is opened**, like the endpoint's other guard-rail
rejections, and the message is a fixed string carrying no request-derived text.

**Migration.** A caller reading a schema listing through the web endpoint must move to
`rmp graph query` or `rmp graph update`, both of which report it in full. The page draws
nodes and edges; its response shape carries no tabular rows
(`SPEC/DATA_FORMATS.md § Graph View Data`), and rendering one would have meant changing
the response shape, the handler and the front end — larger than the rest of the sprint.

Two alternatives were considered and rejected: leaving the endpoint as it was and merely
narrowing the acceptance criterion, which keeps a misleading empty result; and extending
the endpoint to render tabular rows.

### 2. `invalid_keyword_spacing` is withdrawn from the endpoint's published `kind` enum

The endpoint's `kind` value set stays closed at **five** values, and one of them is
replaced:

| | On `1.15.1` | On `1.15.2` |
|---|---|---|
| 1 | `not_read_only` | `not_read_only` |
| 2 | `invalid_limit` | `invalid_limit` |
| 3 | **`invalid_keyword_spacing`** | **`schema_introspection`** |
| 4 | `relationship_read_direction` | `relationship_read_direction` |
| 5 | `execution` | `execution` |

**Removing a published value is a contract narrowing, not an addition.** It was put back
to the owner with that consequence stated and chosen deliberately. The reason is the
endpoint's own published principle — one `kind` per distinct correction the caller must
make. With the class refused outright at every spacing, `invalid_keyword_spacing` would
have told the user to fix the spacing, and fixing it would have earned a second refusal
under a different stated reason: two kinds, one correction, two round trips.

**Migration.** A client that branches on `kind` must rename the case. A client that only
displays `error` needs no change.

**The CLI is untouched.** `graph query`, `graph search` and now `graph update` keep the
keyword-spacing rejection exactly as specified, because those surfaces **accept** the
class and there the spacing genuinely is the whole objection:

```bash
rmp graph query -r myproject --query "SHOW  INDEXES"
# Error: validation error: graph query: SHOW INDEXES is a schema-introspection command
#   the engine recognises only with exactly one space between its two keywords ...
#                                                                     exit 6
```

The two surfaces share the classification and differ only in the verdict. The divergence
is specified in both directions in
`SPEC/GRAPH.md § Keyword Spacing in a Schema-Introspection Command`, which is canonical
for it — including the statement that relaxing the CLI rule to align with the endpoint
must fail acceptance criterion 39.

### 3. The `graph update` operation-class refusal string is retired and replaced

| | Line |
|---|---|
| On `1.15.1` | `Error: validation error: graph update accepts only SET/REMOVE queries` |
| On `1.15.2` | `Error: validation error: graph update accepts only SET/REMOVE, index/constraint DDL, and schema-introspection queries` |

The exit code is unchanged at `6`, and so is the condition: a data-writing `CREATE`,
`MERGE`, `DELETE` or `DETACH DELETE` under `graph update`. Only the wording moved, and it
had to — a message naming one class would send a caller looking for a schema subcommand
that does not exist.

The old string no longer appears anywhere in the binary.
`SPEC/COMMANDS.md § Published Error Strings Are Exact` publishes the new one verbatim and
`tests/test_55_error_string_parity.py` drives the published corpus against the binary, so
the specification and the code are one contract rather than two copies.

**Migration.** Any automation, test, or log matcher comparing this line exactly must be
updated. The other four subcommands' class refusals are byte-identical to `1.15.1`.

### 4. Assessed as breaking, and measured not to be: the mixed-statement refusal

`graph update` now refuses a schema statement carrying a further clause, with exit `6`
and a message naming the discarded tail. This was reported as a fourth breaking change.
**It is not one**, and the claim was checked by running both binaries rather than by
reading the diff:

| Invocation | On `1.15.1` | On `1.15.2` |
|------------|-------------|-------------|
| `graph update -q "CREATE INDEX ix FOR (n:Spec) ON (n.key) MATCH (m:Spec) SET m.reviewed = true"` | Exit **6** — refused by the class rule | Exit **6** — refused by the one-statement rule |

On `1.15.1` `graph update` accepted no DDL at all, so the statement was already refused,
by a different rule and with a different message. **No invocation that succeeded on
`1.15.1` fails because of this rule.** What changed is the explanation the caller reads.

The rule is nevertheless load-bearing, because without it the new feature would have
inherited the engine's silent discard. It is documented under
[One statement per invocation](#one-statement-per-invocation), where it belongs.

### Silent output change, and why it reaches nobody

`rmp graph query` and `rmp graph search` accepted `SHOW INDEXES` and `SHOW CONSTRAINTS`
on `1.15.1` and answered **zero rows at exit `0`** whatever the store held. They now
report the schema the store actually holds. The shape and the exit code are unchanged, so
this is a silent change rather than a loud one — the one change in this release that does
not announce itself.

**It is unreachable in practice on an existing roadmap.** No `rmp` path on `1.15.1` could
register a schema, so there is nothing for the old listing to have omitted. A store
written by another GoGraph program is the only case in which a caller would see the
difference.

## What Was Silently Wrong Before

This is the part of the release with the most value per line, and the part the version
number hides most completely. Three defects, none visible from outside, all fixed here.

### 1. The graph checkpoint erased every index and constraint definition from disk

**The operation meant to make the graph durable destroyed the schema declared over it.**

`checkpointGraph` wrote the snapshot with `snapshot.WriteSnapshotFullWithMapperCodec`, a
writer that persists **no schema at all**, and then truncated the write-ahead log — where
the `CREATE INDEX` events were the only surviving record. `runGraphWrite` performs that
checkpoint after **every** graph write.

Reproduction on `1.15.1`, measured rather than argued:

1. open the graph store and create an index on the write path
2. run `checkpointGraph`
3. reopen with `recovery.Open`

| | Reported by `recovery.Open` |
|---|---|
| Before the checkpoint | `Indexes=1` |
| After the checkpoint | **`Indexes=0`** |

The definition was not merely invisible to the wrong constructor. **It was gone from
disk**, and even the constructor that re-registers a recovered schema found nothing,
because nothing had survived to be recovered.

**What that costs is not a missing listing.** It applies to constraints exactly as to
indexes, and a `UNIQUE` constraint whose definition has been erased **stops being
enforced the moment the process exits**. The next write admits the duplicate the
constraint had refused a moment earlier, at exit `0`, with no error anywhere. That is the
defect in one sentence: a guarantee that quietly stopped being one.

**The fix.** The snapshot is written with
`snapshot.WriteSnapshotFullWithMapperCodecConstraintsAndIndexDefs`, fed from
`Engine.ConstraintSpecsForSnapshot()` and `Engine.IndexSpecsForSnapshot()`.
`checkpointGraph` takes the **engine** as a parameter rather than the two slices, so it
reads them itself at the one moment they are correct — from the engine that just ran the
statement, and **before** the log is truncated. That ordering is load-bearing and is now
specified as such: until the snapshot exists, the log holds the only record of every
schema statement the graph has seen.

### 2. Both engine constructors discarded the recovered schema

`recovery.Open` recovered the durable definitions correctly, and neither constructor
Groadmap used re-registered them.

| Constructor | Used on `1.15.1` by | `SHOW INDEXES` after a reopen |
|---|---|---|
| `cypher.NewEngine` | `graph query`, `graph search`, the web read path | **0 rows**, exit `0` |
| `cypher.NewEngineWithStore` | `graph create`, `graph update`, `graph delete` | **0 rows**, exit `0` |

`DROP INDEX` likewise failed with `index: no index by that name` under both. Index
management shipped on those constructors would have been **inert**: every index would
have vanished the moment the process exited.

- **Read path:** `cypher.NewEngine` → `cypher.NewEngineWithOptions` carrying the
  recovered constraints and indexes. `EngineOptions.Store` is left unset, so the read
  path **still opens neither a transactional store nor a write-ahead-log writer** — the
  guarantee the read path and the web interface depend on, unchanged.
- **Write path:** `cypher.NewEngineWithStore` → `cypher.NewEngineWithStoreAndRecovery`,
  which takes the whole recovery result.

**A second symptom of the write-path constructor is worth naming, because it is quiet.**
Under the old constructor the engine auto-registered recovered constraints under
**synthesised** names — `recovered_unique_Spec_key` in place of the declared
`spec_key_uq` — with a warning on stderr. A constraint that did survive could therefore
not be dropped by the name its author gave it.

### 3. The web graph data endpoint answered introspection with an empty graph

Covered in full under [Breaking Changes](#1-the-web-graph-data-endpoint-refuses-schema-introspection-http-200-becomes-400).
It is repeated here because the old behaviour was a defect and not merely a different
contract: the endpoint accepted the statement, executed it against the correct engine,
and then had nowhere to put the result, because its response shape carries nodes and
edges and never tabular rows.

### And three stale counts nobody had noticed

`internal/web/data.go` said "The four kinds" over a constant block holding five;
`internal/web/static/graph.js` said "three"; the `handleGraphData` doc comment in
`internal/web/pages.go` enumerated three of five; and `DOCS/commands/web.md` was **two
kinds behind**, missing `relationship_read_direction`. Four copies of one list, drifting
independently. Each now names the single canonical enumeration —
`SPEC/WEB.md § Query-Bar Error Handling`, rule 5 — rather than repeating it.

## The Upstream Defect That Remains

**GoGraph's DDL sub-parser stops as soon as its grammar is satisfied and discards the
rest of the statement with no error, no notification and no other trace, returning
success.** Measured directly at v0.12.0 on a bare engine:

| Statement | Verdict |
|---|---|
| `CREATE INDEX a1 FOR (n:S) ON (n.k) GARBAGE GARBAGE` | **accepted**, tail discarded |
| `DROP INDEX a2 GARBAGE GARBAGE` | **accepted**, tail discarded |
| `CREATE CONSTRAINT c1 FOR (n:S) REQUIRE n.k IS UNIQUE GARBAGE GARBAGE` | **accepted**, tail discarded |
| `DROP CONSTRAINT c2 GARBAGE GARBAGE` | **accepted**, tail discarded |
| `SHOW INDEXES GARBAGE GARBAGE` | rejected, with a precise message |
| `MATCH (n:S) RETURN n GARBAGE GARBAGE` | rejected |

**The defect is confined to that one sub-parser.** The `SHOW` parser and the general
Cypher grammar both reject a trailing tail correctly, so this is a gap in one parser
rather than a policy the engine applies consistently.

The dangerous shape is not garbage but a *valid* second clause:

```
CREATE INDEX ix FOR (n:Spec) ON (n.key) MATCH (m:Spec) SET m.reviewed = true
```

which creates the index, **silently drops the `MATCH ... SET`**, and exits `0` with
`n.reviewed` still `null`. A caller who writes that is told their write succeeded when
half of it never ran.

This is why `SPEC/GRAPH.md § One Statement per Invocation` makes Groadmap's own refusal
load-bearing rather than delegating the check. The defect is **not filed upstream**; it is
recorded here and in the project's knowledge graph so that the next GoGraph bump can
re-test it.

## On Scale, and a Figure This Project Had Been Repeating

The work was justified throughout on the ground that "the engine's planner does not seek
below 1024 nodes per label", and therefore that no index on a roadmap-sized graph could
ever be used by a plan. **That figure is stale, and correcting it is part of being honest
about what this release does and does not deliver.**

The figure is `rangeSeekMinLabelPopulation`. It was **`1024` at GoGraph v0.11.0** and is
**`64` at v0.12.0** (`cypher/range_seek_plan.go`), lowered upstream after measurement
showed the old floor suppressing the index across the whole range where it wins. The
premise was read at v0.11.0 and carried through the upgrade without being re-read.

So the reasoning no longer holds as it was stated. This project's own graph holds **710
nodes**, and four of its labels sit above the new floor where none was above the old one:

| Label | Nodes |
|---|---|
| `Test` | 278 |
| `Requirement` | 142 |
| `Memory` | 121 |
| `CodeFile` | 111 |
| `Component` | 21 |
| `Doc` | 14 |
| `Spec` | 14 |
| `Release` | 9 |

**No performance win is claimed even so, because none was measured.** Measured through
the CLI over a 300-node label, ten invocations each:

| | Wall clock per invocation |
|---|---|
| No index | **10 ms** |
| With a `hash` index on the queried property | **10–11 ms** |

Process start and store open dominate, and at roadmap scale any planner effect is below
the noise this project can observe through its own command line. **What this release
delivers is that a schema can exist, survive a checkpoint, and go on being enforced — not
that a query got faster.**

## Upgrade Notes

### Step 1 — Do not run a `1.15.1` or older binary against a graph that carries schema

**This is the release's one real upgrade hazard**, and it is a consequence of the
checkpoint fix rather than of the feature. It is stated first because it is silent and it
costs data.

An older binary **reads** such a store correctly. But its first **successful** graph write
checkpoints through the old snapshot writer, and afterwards:

- `constraints.bin` and `indexdefs.bin` are **gone** from `<roadmap>/graph/snapshot/`
- `SHOW INDEXES` and `SHOW CONSTRAINTS` return **zero rows**
- **a duplicate that the `UNIQUE` constraint had refused a moment earlier is accepted at
  exit `0`**

Measured end to end on a store holding one index and one enforced constraint:

```
# with the 1.15.2 binary
graph create ... {key:'auth'}  -> exit 1, constraint violation

# one successful write with the 1.15.1 binary
graph create ... {key:'billing'} -> exit 0     [schema destroyed here]

# back on the 1.15.2 binary
SHOW CONSTRAINTS               -> rows: []
graph create ... {key:'billing'} -> exit 0     [duplicate accepted]
```

**Nothing warns you.** Replace the binary on `PATH` before writing to a graph that has a
schema. A roadmap whose graph carries no schema is unaffected, and its snapshot is
structurally unchanged, because the writer omits a component whose slice is empty.

### Step 2 — There is no database migration

The SQLite schema version is unchanged and no roadmap database is touched. The only
on-disk change is in the graph snapshot, which gains `constraints.bin` and
`indexdefs.bin`, and only for a graph that has a schema.

Backing up remains sensible before any upgrade:

```bash
cp -a ~/.roadmaps/<name> ~/.roadmaps/<name>.pre-v1.15.2
```

### Step 3 — Update your automation

Three things to check, in the order they are most likely to bite:

1. **A client that branches on the web endpoint's `kind`** must rename
   `invalid_keyword_spacing` to `schema_introspection`.
2. **Anything that reads a schema listing through the web endpoint** must move to
   `rmp graph query`, because the endpoint now answers `400`.
3. **Any exact match on** `graph update accepts only SET/REMOVE queries` must be updated
   to the new line.

If you drive `rmp` from an agent, `rmp --ai-help` carries the new surface, the two new
pitfalls, and the corrected guard-rail description.

### Step 4 — Install and verify

```bash
git checkout v1.15.2
make check          # expects exit 0
./bin/rmp --version
# Groadmap version 1.15.2
```

Then confirm the feature is live and durable, in two separate invocations:

```bash
rmp graph update -r <roadmap> --query "CREATE INDEX probe_key FOR (n:Spec) ON (n.key)"
rmp graph update -r <roadmap> --query "SHOW INDEXES"     # probe_key must be listed
rmp graph update -r <roadmap> --query "DROP INDEX probe_key"
```

The second command being a **separate process** is the whole verification: on `1.15.1`
the index would already be gone.

## Why This Is Released as `1.15.2`

**`SPEC/VERSION.md` classifies new backward-compatible functionality as `MINOR` and an
incompatible change as `MAJOR`. This release contains both**, so no single class fits it
and the number was decided rather than derived.

Three readings were put to the project owner with the evidence behind each:

- **`2.0.0` — the strict reading.** Three published contracts were narrowed, and
  Semantic Versioning 2.0.0 makes an incompatible change to a public API a `MAJOR`
  change without regard to how small its reach is.
- **`1.16.0` — the recommended reading, and not taken.** The release's defining change is
  a new feature, and `MINOR` is the class that announces one.
- **`1.15.2` — chosen, by the owner's explicit decision.** `2.0.0` was declined as
  signalling a larger rupture than the changes' real reach.

The reasoning for the choice, recorded so that it can be reviewed rather than inferred:

- The narrowed contracts are all on the graph surface's **edges** — one machine-readable
  enum value on a read-only local web page, one status code on the same page, and one CLI
  error string. None of them touches the roadmap data model, the database, or the task and
  sprint commands that are the tool's centre.
- The affected surface is a **roadmap-authoring CLI and a local read-only web page**, not
  a library API that other code links against. There is no compilation to break and no
  dependency resolver to mislead.
- Every incompatibility **fails loudly and immediately** — a non-zero exit or an HTTP
  `400`, with nothing changed — rather than silently altering a result. In one of the
  three cases the *old* behaviour was the silent one: an empty graph at HTTP `200`.

**This does not soften anything, in either direction.**

A reader who sees `1.15.1 → 1.15.2` and expects a drop-in replacement will be wrong about
three things, and this document is the only thing that warns them. A reader who concludes
from the number that there is nothing new to try will be wrong about the whole point of
the release — which is why
[What Is New](#what-is-new--schema-management-for-the-knowledge-graph) comes before
[Breaking Changes](#breaking-changes) in this document, and why the changelog entry leads
with the feature.

The classification is a project decision. The incompatibility and the feature are both
facts. All three are stated here.

**This release states its own reading.** `1.15.1` reached a comparable conclusion on
different grounds — every change there was the correction of a divergence from a
published contract, and nothing new was built — and it is not cited as cover for this one.
The grounds here are different, because this release does build something new.

### Fixed — Durability of the Graph Schema

- The checkpoint no longer erases the schema; it is written into the snapshot from the

- Both engine constructors carry the recovered schema. The read path keeps its guarantee
  of opening neither a store nor a WAL writer.
- A constraint keeps its **declared** name across a reopen instead of being

### Changed — BREAKING

The three narrowings, in full under [Breaking Changes](#breaking-changes).

### Changed — Toolchain and Dependencies

- **GoGraph `v0.11.0` → `v0.12.0`.** A pre-1.0 `MINOR` release, non-breaking by its own
  audit: no exported identifier removed, no exported signature changed, no exported

  `cypher.NewEngineWithStoreAndRecovery` (`cypher/index_hydration.go`), in a file that
  does not exist at v0.11.0, which GoGraph names **the recommended constructor for
  opening a persisted store**. It hydrates each index from the snapshot payload instead of
  rebuilding it by a full graph scan, and forgetting it is *silent* — the engine still
  opens and still answers correctly. For a CLI that opens the store, runs one statement
  and exits, "on every restart" means **on every invocation**.

- `github.com/RoaringBitmap/roaring/v2` `v2.24.0` → `v2.26.0`, indirect, pulled by
  GoGraph.

### Added — Regression Gates

- `tests/test_64_graph_schema_management.py` — durability across the process boundary,
  the exit codes, and cross-surface agreement. The suite grows from 62 registered modules
  to **63**.
- `internal/commands/graph_schema_durability_test.go` — four tests, proved by **three
  separate mutations**, because three independent defects produce the same zero-row
  symptom. One asserts the write-ahead log is **0 bytes** before reading anything back, so
  a pass cannot come from the log still holding the events. Another asserts its own
  control first — `cypher.NewEngine` returning zero rows on the same store — so the
  positive assertion is a statement about the constructor rather than about the store, and
  fails loudly rather than decaying into a vacuous pass.
- `internal/web/graph_schema_introspection_test.go` — proved by **five mutations**,
  seeding a real index and constraint so the refusal is refusing a statement that would
  have had a real answer.
- `internal/cypherguard/schemastatement_test.go`, plus 19 new E2E cases. The guard-rail
  work as a whole was proved by **four mutations**, each restored: never refusing turns 8
  `cypherguard` subtests and 2 E2E cases red; dropping `OPTIONS` from the grammar walk
  produces a **false refusal** that the runtime plan-equality proof does **not** catch,
  which is the evidence that the grammar walk is doing real work rather than decorating
  the plan check; reverting the CLI read path to `cypher.NewEngine` turns acceptance

## Known Issues

**Nothing here was copied forward on trust.** Every item below states how it was checked
for this release, and each was re-established against this tree rather than inherited
from `1.15.1`'s list. Two items that `1.15.1` recorded are **not** repeated here because
this release did not re-verify them and will not assert what it has not measured; they
are named at the end of the section. The historical entries in `CHANGELOG.md` are left
exactly as written: they record what was known at the time, and editing them would
destroy the record rather than correct it.

### Open

- **A stranded `snapshot.bak` stops every later graph checkpoint, and the write still
  exits `0`.** Upstream GoGraph behaviour, and the one item here that can affect you in
  normal use. **Reproduced on this tree at v0.12.0**, and the archive step was read in
  both versions and is byte-for-byte identical, so the dependency bump neither fixed nor
  worsened it. With a non-removable `snapshot.bak` present, `rmp graph create` wrote

  ```
  {"ok": true}
  ```

  to stdout at exit `0`, and only stderr said anything:

  ```
  Warning: graph checkpoint failed: snapshot write: snapshot: archive live snapshot:
  rename .../graph/snapshot .../graph/snapshot.bak: file exists
  ```

  The exit code is required behaviour rather than an oversight: a checkpoint failure
  *after* a durable commit must not fail the write, because the write-ahead log is intact
  and recovery still works. The cost is that the log grows without bound until the
  stranded directory is removed. **This release makes it matter more than it did**, because
  the snapshot now carries the schema: a graph whose checkpoints are all failing keeps its
  schema only in the log, and the log is what a later successful checkpoint truncates.

- **On a machine with the snap package installed, `make lint` silently runs the wrong
  `golangci-lint`.** Confirmed live on the release host for this release:
  `/snap/bin/golangci-lint` (v2.13.2) precedes the pinned `~/go/bin/golangci-lint`
  (v2.13.1) on `PATH`, and the `Makefile` invokes the bare name. Both versions report 0
  issues on this tree, so nothing was concealed this time, but the gate is not
  self-verifying. Run `which -a golangci-lint` before trusting a lint result.

- **Two nodes of the project's own knowledge graph share the key `tests/run_tests.py`**,
  one `CodeFile` and one `Test`. Key uniqueness is judged on the NFC form and is a
  convention the caller honours rather than something Groadmap enforces
  (`SPEC/GRAPH.md § Node Key Uniqueness`, which publishes the two-step audit that detects
  such a pair). It is a defect in the model rather than a duplicate to delete, and it is
  the same shape as the `README.md` pair that `rmp` task #155 closed by rekeying.

- **Undocumented exit-`6` causes in `DOCS/commands/graph.md`.** Its Exit Codes section
  omits the maximum query length (1 MiB), the relationship **write** and **read**
  direction refusals, the UTF-8 encoding rule, and the property-value control-character
  rule. The relationship-direction rules are documented nowhere in `graph.md`, although
  `web.md` cites them. Deliberately out of scope for this release's documentation task and
  tracked as `rmp` #345.

- **`README.md` carries no worked schema example.** The `graph update` bullet names the
  new classes, but adding a runnable schema example is a new section rather than a
  correction, and it was left to the backlog.

- **`rmp audit stats` exits `4` for a missing roadmap while its published contract
  declares only `{0, 3, 6}`.** Re-verified by execution on this tree:
  `rmp audit stats -r no-such-roadmap` exits **4**, and the contract's `exit_codes` array
  for that subcommand still reads `[0, 3, 6]`. The behaviour is correct; the declaration
  is incomplete, and an agent branching on the array will not expect the code it gets.

- **`DOCS/commands/stats.md` omits exit code `2`, and so does the contract array behind
  it.** Re-verified by execution: `rmp stats -r <name> <token>` exits **2** through the
  CLI-wide arity rule, while the page's Exit Codes table publishes `0`, `3` and `4` and
  the contract array reads `[0, 3, 4]`. Page, array and help block all agree, and all
  three are wrong.

- **`SPEC/COMMANDS.md` publishes a `sprint close` refusal that the binary does not
  write.** The row still states exit `6` with the sentinel `invalid input:`, which the
  catalogue maps to exit `2`, so the row contradicts itself as well as the binary, which
  writes `validation error:`. It is invisible to the error-string parity gate because a
  cell is promoted to a published string only when it contains `Error:`, and this one
  omits the prefix. Re-verified by reading the row on this tree; the wording is unchanged
  since `1.15.1`.

- **A machine carrying a newer Go release will move the board search's Unicode data
  again.** The `go` directive is a floor and a `toolchain` line would be a floor too;
  neither is a ceiling, so the toolchain that runs the build decides. What exists is
  detection rather than prevention: the guard in `internal/web` compares the client
  tables the binary ships against the server's own rule over the whole of Unicode and
  fails the `test` gate the moment they diverge. Unchanged by this release, and carried
  because the mechanism was re-read rather than assumed.

### Recorded by `1.15.1` and deliberately not repeated here

Two items from the previous release's list were **not** re-verified in this cycle, and
this document does not assert them:

- `task list --created-since` and `--created-until` accepting both date forms without
  stating the first-instant reading.
- `--order` being spelled two ways in its own refusals.

Neither is affected by anything in this release. They remain in the `1.15.1` notes, which
is where a reader should look, and they should be re-established by execution before they
