# Release Notes — Groadmap v1.18.0

**Date:** 2026-10-01
**Type:** Minor by the owner's decision — **but it changes command behaviour, exit codes, error lines and the web interface** (see [Breaking Changes](#breaking-changes))
**Tag:** `v1.18.0`
**Previous release:** `v1.17.3` (2026-09-18)

---

## Executive Summary

Groadmap `v1.18.0` enforces sprint membership as an invariant, tightens input
validation across the CLI, hardens the web interface and the graph server, and
rebuilds the web Tasks page as a filtered, paginated list with a dedicated page per
task. It migrates every roadmap database from schema `1.14.0` to `1.17.0` on first
open, and repairs existing sprint-membership violations as it does.

It is also the first release to ship the project's two Claude Code agent skills,
`roadmap-manager` and `knowledge-authority`, as a release asset with their own
installer.

**Read the breaking changes before you upgrade, because the version number will not
warn you.** A strict SemVer reading of this release gives `MAJOR`. The project
publishes `1.18.0` by the owner's explicit decision, recorded in
[Why This Is Released as `1.18.0`](#why-this-is-released-as-1180).

## Breaking Changes

Every before-and-after statement in this section was measured on 2026-10-01 by
running the same command against a `v1.17.3` binary built from its tag and against
the `1.18.0` binary built from this tree, each in an isolated `HOME`.

### Sprint membership is an enforced invariant

The invariant has two halves: a sprint member is never in `BACKLOG`, and a task in
`SPRINT`, `DOING` or `TESTING` always belongs to a sprint. One application guard
checks it inside the transaction of `task create`, `task stat`, `task reopen`,
`sprint add-tasks`, `sprint move-tasks`, `sprint remove-tasks` and `sprint remove`
(`ea76fd8`). Six commands change behaviour:

| Command | `1.17.3` | `1.18.0` |
|---|---|---|
| `task stat <id> BACKLOG` on a sprint member | Exit `0`; the task became `BACKLOG` and stayed a member | Exit `6`: `... a task leaves its sprint only through 'rmp sprint remove-tasks'` |
| `sprint move-tasks` with a `COMPLETED` task | Exit `0`; the task moved | Exit `6`: `task N is COMPLETED in sprint #M; a completed task stays in the sprint it was completed in` |
| `sprint add-tasks` naming a `COMPLETED` task of another sprint | Exit `0`; the task moved | Exit `6`, same line |
| `sprint remove-tasks` on a `COMPLETED` member | Exit `0`; the task became `BACKLOG` and left the sprint | Exit `6`, same line |
| `sprint remove` with a `COMPLETED` member | Exit `0`; the sprint was removed | Exit `6`: `cannot remove sprint #M: completed tasks stay in their sprint: #N` |
| `task reopen` on a `DOING` or `TESTING` task | Exit `0`; the task became `BACKLOG` and left its sprint | Exit `0`; the task becomes `SPRINT` in its sprint, at its position |
| `task reopen` on a `COMPLETED` task | Exit `0`; the task became `BACKLOG` and stayed a member | Exit `0`; the task becomes `SPRINT` in its sprint, at its position |
| `task reopen` on a `SPRINT` task | Exit `0`; the task became `BACKLOG` and left its sprint | Exit `0`; skipped, with the stderr note `task #N is already in SPRINT` |
| `task reopen` while the task's sprint is `CLOSED` | Exit `0` | Exit `6`: `cannot reopen task N: sprint #M is CLOSED; reopen the sprint first with 'rmp sprint reopen'` |

Further rules:

- **An unfinished task changes sprint keeping its status and tracking fields**,
  through `sprint move-tasks` or `sprint add-tasks`. The change is recorded under
  the new audit operation `TASK_SPRINT_CHANGE`, so a move writes three audit rows
  per task: `SPRINT_MOVE_TASK_OUT`, `SPRINT_MOVE_TASK_IN` and `TASK_SPRINT_CHANGE`.
- **`sprint remove-tasks` is the one command that yields `BACKLOG`.** Because a
  non-member is already `BACKLOG` or is `COMPLETED`, which has no transition to
  `BACKLOG`, `task stat ... BACKLOG` can no longer succeed.
- **`task reopen` is refused when reopening `COMPLETED` tasks would take the
  sprint past its `max_tasks` cap** (`7d4beff`).
- **`sprint add-tasks` counts against the cap only the named tasks that are not
  already members of the sprint.** `1.17.3` counted every named task.

**What to change:** park sprint work with
`rmp sprint remove-tasks -r <roadmap> <sprint-id> <id>` instead of
`task stat <id> BACKLOG`; leave finished work in its sprint, or reopen it first.

### Stricter input validation, new exit codes and new error lines

| Input | `1.17.3` | `1.18.0` |
|---|---|---|
| A repeated flag, `task create -t A -t B ...` | Exit `0`; the last value was kept | Exit `2`: `repeated flag: -t`, on every subcommand |
| `task list -p 12` | Exit `0`, `[]` | Exit `6`: `priority must be between 0 and 9, got 12`; the same for `backlog list` and for severity |
| `task list -p x` | Exit `2`, with `strconv.Atoi` text | Exit `2`: `invalid value for --priority: "x" is not an integer in 0-9` |
| `task get -` | Exit `6`: `task_id must be between 1 and 2147483647, got -` | Exit `2`: `invalid task ID: "-" (must be a positive integer)` |
| `audit list --since 0001-01-01` | Exit `0` | Exit `6`; dates must be strict RFC 3339 or `YYYY-MM-DD` within `1970-01-01`..`9999-12-31` |
| `task comment-edit --type NOTE` with data piped on stdin | Exit `0`; the data was ignored | Exit `2`: `standard input carries data, but it is not read when --type is given; supply the new body with --body` |
| A 101-character roadmap name of two-byte characters | `must not exceed 50 characters (got 202)` | `... (got 101)`: length is counted in characters |
| Directories `Bad Name`, `-dash`, `UPPER` under `~/.roadmaps/` | Listed by `roadmap list` | Omitted by `roadmap list` and by the web index |
| A regular file in place of a roadmap home, `task list -r <name>` | Exit `1`, operating-system text | Exit `4`: `resource not found: roadmap "<name>"` (web: `404`) |
| `roadmap create` over that file | Exit `1`, operating-system text | Exit `1`: `cannot create roadmap "<name>": <path> is occupied and is not a directory` |
| `sprint swap` naming a non-member | Exit `6`: `task N does not belong to sprint M` | Exit `6`: `task N is not in sprint #M`, for every ordering command |
| `audit list --entity-id abc` | `invalid entity ID: abc` | `invalid entity ID: "abc" (must be a positive integer)` |
| A relative `HOME` | Exit `0` | Exit `1`: `home directory "<value>" is not an absolute path; refusing to locate the data directory under it` |
| `roadmap remove` while `graph serve` runs for the roadmap | Exit `0`; removed | Exit `6`: `cannot remove roadmap "<name>": a graph server is running for it; stop the server first` |
| A zero-byte `project.db` | Exit `1`: `no such table: tasks` | Initialised; the command succeeds |
| A database with a schema newer than the binary | Opened (see [Downgrading](#downgrading)) | Exit `1`: `<path> has schema version <x>, newer than schema version 1.17.0 supported by this rmp; upgrade rmp to open it`, with nothing written |

In addition, a symbolic-link database file or sidecar is refused before any
permission change, and a file that is not SQLite is refused (`7d4beff`).

**The AI Agent Contract.** `rmp --ai-help` keeps `schema_version` `2.0.0`, the same
command set and the same flag names. Its `AuditOperation` enum gains
`TASK_SPRINT_CHANGE`, and the per-subcommand texts (exit-code conditions,
descriptions, side effects, examples) change with the behaviour above.

### The plain-text help changes on every subcommand

Each of the 55 subcommand helps differs from `1.17.3`. Every subcommand except the
three `roadmap` subcommands gains the repeated-flag condition under exit `2`; the
subcommands that take `-r` gain the invalid-roadmap-name condition under exit `6`;
and the helps of the commands above describe their new behaviour. The `roadmap`
helps change for other reasons: `roadmap list` states that entries breaking a name
rule are skipped, `roadmap create` gains the occupied-entry exit `1`, and
`roadmap remove` gains the graph-server refusal under exit `6`. Besides the version
header (`Groadmap v1.18.0 - ...`), the global help changes two lines:

```
# 1.17.3
  backlog, bl      Query BACKLOG-status tasks. Both subcommands filter on the status alone, so a BACKLOG task that is still a member of a sprint is listed too
  web              Start a read-only web interface for the roadmaps under ~/.roadmaps/

# 1.18.0
  backlog, bl      Query BACKLOG-status tasks. Both subcommands filter on the status alone, and a BACKLOG task belongs to no sprint
  web              Start a web interface for the roadmaps under ~/.roadmaps/
```

The family helps of `task`, `sprint` and `audit` change. Only `rmp ai-help --help`
is unchanged.

### The web interface

| Request or page | `1.17.3` | `1.18.0` |
|---|---|---|
| `GET /roadmaps/{name}/tasks/{id}/data` | `200`, the task as JSON | `404`: the endpoint and the task modal are removed (`6d2251b`) |
| `GET /roadmaps/{name}/tasks/{id}` | `404` | `200`: the new task page |
| Any request with `Host: evil.example` | `200` | `403` `host not allowed` (`2f991be`) |
| Any request with `Sec-Fetch-Site: cross-site` | `200` | `403` |
| Any request with a foreign `Origin` | `200` | `403` `origin not allowed` |
| `<title>` of the Tasks page | `Groadmap — <roadmap> / Tasks` | `<roadmap> - Tasks - <hostname>` (`4e7e971`) |

- **The request guard** runs before routing on every request, `/static/`
  included. It enforces a `Host` allowlist per bind kind (loopback, wildcard,
  specific address) with the bound-port rule, and refuses a `Sec-Fetch-Site` other
  than `same-origin` or `none` and a foreign or `null` `Origin`. A request the
  client abandoned is answered `499` and logged once at `INFO`, never as a `5xx`.
- **The Tasks page is one filtered, paginated list instead of a board** (`134c4ad`,
  `967740c`, `9dcb330`). It has seven columns (ID, Title, Type, Status, Severity,
  Priority, Created), and the title is the only link. Filtering and pagination run
  on the server through the `q`, `sprint`, `status`, `type`, `page` and `size`
  query parameters; `status` and `type` are repeatable. Page sizes are 10, 25, 50
  and 100; the default view shows every status except `COMPLETED`, 25 rows per
  page. The filter state persists in the `rmp_tasks_filters` cookie, and the
  route's responses carry `Vary: Cookie`.
- **The "Min priority" and "Min severity" filters of the Tasks page are removed**
  (`134c4ad`), and their `priority` and `severity` URL parameters are now ignored.
  Search runs on the server through a GET form; under `1.17.3` it ran in the
  browser and rewrote the URL with `history.replaceState`.
- **Page titles** read `<roadmap> - <area> - <hostname>`, the index
  `Roadmaps - <hostname>`, a task page `#<id> <title> - <roadmap> - <hostname>`.
- **The sprint details datagrid holds only Created, Started and Closed**
  (`14db500`); the sprint order and capacity are no longer displayed, and the
  sprint status summary line is removed (`b9d4163`).

**What to change:** read task data with `rmp task get`; filter by priority or
severity with `rmp task list -p`/`--severity`; reach `rmp web` by the host
name and port it is bound to, and not through a proxy that rewrites `Host`.

## New Features

### Agent skills, packaged and installable

The repository's `skills/` directory holds two Claude Code skills that drive `rmp`:
`roadmap-manager` (tasks, sprints and their comment logs) and `knowledge-authority`
(the knowledge graph, through `rmp graph serve` and `rmp graph client`) (`80e29ef`).

- **Release asset.** The release workflow (`.github/workflows/release.yml`, step
  *Package agent skills*) packages them from the tag's checkout as
  `rmp-skills-v1.18.0.tar.gz`, with `rmp-skills-v1.18.0.tar.gz.sha256`, and attaches
  both to the GitHub release.
- **Installer.** `install-skills.sh` downloads the latest release's archive,
  verifies it against its SHA-256 checksum, and installs into
  `$CLAUDE_CONFIG_DIR/skills`, or `~/.claude/skills` when that variable is unset.
  Each run replaces both skills entirely, with rollback on failure, and leaves
  every other skill untouched:

  ```bash
  curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install-skills.sh | bash
  ```

- **Alignment.** A Go test (`internal/aihelp`) holds both skills to the AI Agent
  Contract and requires their declared `rmp-version` to equal the binary version.
  For this release both skills were re-measured against the `1.18.0` binary and
  declare `rmp-version: "1.18.0"`. The corrections this re-measurement made
  include: a failure writes three stderr lines under `AI_AGENT=1`; a type-only
  `comment-edit` checks piped stdin and refuses data; `task reopen` is refused over
  capacity; `sprint move-tasks` writes three audit rows per task; a sprint's
  `tasks` array is `[]` when empty; and the socket-path length limits of
  `graph serve` and `graph client`.

### The web interface

- **A page per task** (`6d2251b`): the sprint context (sprint link, status,
  position, completion progress, or the backlog text), the details (parent,
  depends-on and blocks as links, full commit hashes), the four Markdown fields and
  the comments. Sprint board cards, and task titles on the Tasks page, link to it.
- **Markdown rendering** (`efc5f48`, `705c320`) of the task requirement fields,
  acceptance criteria and completion summary, of task and sprint comment bodies,
  and of the sprint description. Rendering happens on the server; raw HTML is
  omitted, a dangerous URL renders as text, absolute `http(s)` links open in a new
  tab with `rel="noopener noreferrer"`, a remote image renders as a link to it,
  headings are demoted to `h4`-`h6`, and code blocks are highlighted.
- **Timestamps** display as `YYYY-MM-DD HH:mm:ss` in UTC, inside a `<time>` element
  carrying the stored value (`6ffb033`). The CLI and the JSON keep ISO 8601.
- **Collapsible sprint board columns** (`f7c2241`). A column with no task starts
  collapsed when the sprint holds at least one task (`8543d8a`).
- **Sprint board cards carry the id and the task type in their badge line**
  (`ce0f031`, `9d46a71`, `34e83b4`). The `#<id>`, a plain line under the title in
  `1.17.3`, becomes a black badge at the start of the badge line; severity now
  precedes priority (`S<n> P<n>`, where `1.17.3` showed `P<n> S<n>`); and a
  colour-coded task type badge is added. The sprint status badge sits in the page pretitle (`180a5a9`).
- **Tabler `v1.6.0`** replaces `v1.4.0`, CSS and JavaScript together (`b9d4163`).
  The Inter italic face is vendored, so italic is no longer synthesised
  (`705c320`). Dark-theme badge text and the focus outline meet WCAG 2.2 AA contrast
  on the Tasks list and the sprint board (`134c4ad`).

### The CLI

- **The audit operation `TASK_SPRINT_CHANGE`** records a task that changed sprint
  and kept its status (`ea76fd8`).
- **`roadmap create` is safe under concurrency.** It builds `project.db` under a
  temporary name and claims it atomically, so exactly one concurrent creator wins
  and the others exit `5` (`7d4beff`). Schema creation and its metadata run in one
  transaction, so a failure leaves no partial schema (`4c7153e`).
- **`rmp web --help` states what the interface writes** (`2f991be`): every page is
  read-only and no roadmap database is written, but the knowledge-graph query bar
  runs the Cypher typed into it, writes and deletes included, without
  authentication.

## Fixes

- **Concurrent `sprint add-tasks` processes no longer exit `1`** (`704e8e2`).
  Read-write SQLite transactions begin `IMMEDIATE` and wait under the busy timeout
  instead of receiving `SQLITE_BUSY` on the lock upgrade.
- **A lost `sprint start` race yields the sequential refusal**, never raw SQLite
  text; driver failures are classified at one dispatch point (`7d4beff`).
- **A cancelled graph statement is no longer committed** (`2f991be`). The client
  closes the Bolt connection on cancellation, so the server cancels the statement.
  A deadline keeps its published outcome.
- **Migration `1.13.0` handles `v1.0.0`-release databases** lacking
  `sprint_tasks.position` and `idx_one_open_sprint`, and migration `1.1.0` is
  idempotent (`7d4beff`).

## Security

- **Cross-site writes and DNS rebinding against `rmp web` are closed** (CWE-352,
  CWE-350; `2f991be`), by the request guard described under
  [The web interface](#the-web-interface).
- **The graph server's socket is never connectable at a wider mode** (`120e1e6`).
  On POSIX it is bound inside a private `0700` staging directory beside the target,
  set to `0600` there, and hard-linked into place. The commit records that another
  user connected 3 times out of 3 in the window before the former `chmod`. Startup
  removes same-user staging residue, and the length check also measures the
  transient path, refusing before any bind. `graph serve` re-establishes mode
  `0700` on `~/.roadmaps/` and the roadmap home at start, and never creates a
  roadmap home (`7d4beff`).
- **Symbolic-link database files and sidecars are refused before any `chmod`**, and
  a non-SQLite file is refused (`7d4beff`).
- **Markdown is rendered safely** (`efc5f48`); the Content-Security-Policy is
  unchanged.
- **The `rmp_tasks_filters` cookie is `HttpOnly` and `SameSite=Lax`** (`9dcb330`).
  `Secure` is deliberately unset because `rmp web` serves plain HTTP only, and a
  user agent returns a `Secure` cookie only over a secure channel; `19b9dfe`
  registers that as a gosec G124 suppression.

## Internal Changes

These change no output of the binary.

- **No benchmarks and no measurement tests** (`52f21a2`). Timed behaviour is proven
  deterministically through seams, and an AST gate fails on any `Benchmark`
  function. The `heavy` build tag and `make test-heavy` added there were removed in
  `134c4ad`, together with the browser copy of the search they tested.
- **The end-to-end suite is a required job** in CI and in the release workflow
  (`ed2bed6`): nothing is built or published unless it passes. The Makefile asserts
  the pinned `golangci-lint` and `gosec` versions and reports every `PATH` copy on a
  mismatch.
- **Native fuzz targets** for the untrusted-input parsers (`15604e4`).
- **Every SPEC DDL block is held byte-identical to `schema.go`** by a test
  (`0f515ad`); the task transition table is declared once (`9bb76da`).
- **Test harness hardening** (`4e801db`): two flaky gates fixed; the new `test_75`
  checks every `Error:` line and relative link in `DOCS/` and `README.md`. The new
  `test_76` (`7d4beff`) covers the correctness and security fixes, and `test_77`
  (`80e29ef`) the skills installer.
- **Migration-chain fixtures.** `7d4beff` added one immutable fixture per released
  schema version from `1.0.0` to `1.14.0` and a chain test; the release cut adds the
  `1.17.0` fixture.
- **Directory-creation failures under `graph serve` are classified as I/O errors at
  the source**, with messages and exit codes unchanged (`120e1e6`).
- **The generated chroma files are stored byte-exact**, so a clean checkout passes
  the staleness test (`0a1be6d`).
- **Specification and documentation** corrections (`8053d49`, `35d3e37`, `f58becd`,
  `d31f5e4`), the new `SPEC/SKILLS.md` (`390249a`), and project instructions and
  knowledge model (`abc427a`, `ab013a8`, `bd6e163`).

## Known Issues

The list was rebuilt for this release. Each item was verified on this tree, by the
means stated.

- **`rmp audit list --help` still says `TASK_STATUS_BACKLOG` carries `null` "from
  'task stat'".** The help reads `TASK_STATUS_BACKLOG carries a sprint id from
  'sprint remove-tasks' and null from 'task stat'` (`internal/commands/audit.go`).
  `task stat` can no longer write that row: `task stat 1 BACKLOG` on a `SPRINT`
  member and on a `DOING` member both exit `6`, and a non-member has no transition
  to `BACKLOG`. A `null` row now comes only from a binary older than `1.18.0` or
  from the `1.16.0` migration (`SPEC/DATABASE.md`). Verified by execution.
- **`rmp backlog --help` and `rmp backlog list --help` say no 0-9 validation is
  enforced on `--priority`** (`internal/commands/backlog.go`). The binary refuses
  `backlog list -p 12` with exit `6` and
  `priority must be between 0 and 9, got 12`, and `backlog list --help` lists that
  refusal under its own exit codes. Verified by execution.
- **`1.18.0` does not re-check sprint membership when it opens a database already at
  schema `1.17.0`.** The `1.16.0` repair runs once. A violation written afterwards
  by an older binary stays: `task list`, `backlog list` and `sprint tasks` all
  report the task, exit `0`, until a membership command touches it. Verified by
  execution; see [Downgrading](#downgrading).
- **`modernc.org/libc` is a later release than `modernc.org/sqlite` requires**
  (`v1.76.0` in `go.mod`, against the `v1.75.7` that `modernc.org/sqlite v1.59.0`
  declares in `go mod graph`). The driver runs transpiled SQLite inside that C
  runtime, and its author requires the two versions to match. The project accepts
  the risk deliberately (`SPEC/BUILD.md § SQLite Driver Rules`).
- **A failed graph statement can replace an existing relationship**
  (`SPEC/GRAPH.md § Error Handling and Exit Codes`, rule 9). Reproduced on this
  binary: after `CREATE (a:Svc {key:'api'})-[:OLD {p:1}]->(b:Svc {key:'db'})`, the
  statement `MATCH (a:Svc {key:'api'}),(b:Svc {key:'db'}) CREATE (a)-[:NEW]->(b)
  WITH a RETURN 1/0` exits `1`, and the pair is then joined by one relationship of
  type `NEW` with no properties; `OLD {p: 1}` is gone.
- **A list property holding `null` is not stored as written**
  (`SPEC/GRAPH.md § What Groadmap Does Not Check`, item 9). Reproduced:
  `CREATE (n:Probe {key:'nulls', xs:[1,null,3]})` exits `0`, and `n.xs` reads back
  as `[1, 3]`.
- **A property value the engine cannot store is refused with generic text**
  (`SPEC/DATA_FORMATS.md`). Reproduced: `CREATE (n:Probe {key:'map', bad:{a:1}})`
  exits `1` with `An internal error occurred. See server logs for details
  (session: <id>)`; the engine's diagnostic,
  `a nested list or map is not a valid property value`, reaches only the server's
  stderr.
- **Two further engine hazards report success**, as stated in `SPEC/GRAPH.md § What
  Groadmap Does Not Check`: item 4, a relationship property `REMOVE` persists only
  where the pattern walked the relationship in its stored direction; and item 8, a
  relationship bound by `MERGE` or `CREATE` over a node pair that several
  relationships join in the pattern's direction is not reliably the one matched or
  created. Verified in the specification on this tree, not reproduced.
- **The published field-length line has no producer at the pinned engine**
  (`SPEC/GRAPH.md § Field Length Limits`, rule 13). Verified in the specification
  on this tree, not reproduced.
- **The web query bar's `EXPLAIN`/`PROFILE` prefix check runs outside the 5-second
  budget**, because the engine's parser takes no context
  (`internal/web/data.go`, `refusePlanPrefix`). The code comment records that the
  costliest input found at the 1 MiB ceiling parsed in 2.44 s to 2.72 s and
  allocated 1.46 GiB; that figure was not re-measured for this release.

## Upgrade Notes

### Step 1 — Check the programs that drive `rmp`

Read [Breaking Changes](#breaking-changes). A program is affected if it parks sprint
tasks with `task stat ... BACKLOG`, moves `COMPLETED` tasks between sprints,
removes a sprint holding `COMPLETED` tasks, matches any error line or exit code
listed there, repeats a flag, reads the web task data endpoint, or reaches
`rmp web` through another host name or origin. Use `rmp --ai-help` for the exact
per-subcommand exit-code conditions.

### Step 2 — Let the database migrate

The first `1.18.0` command that opens a roadmap migrates it from schema `1.14.0` to
`1.17.0`, in transactions, with no action required. Measured on a roadmap written
by `1.17.3` holding task 1 as a `BACKLOG` member of sprint 1 (produced with
`task stat 1 BACKLOG`): after one `1.18.0` `task list`, the schema version read
`1.17.0`, task 1 was `SPRINT` in sprint 1, and a `TASK_STATUS_SPRINT` audit row had
been written for it.

The migration is not reversed by installing an older binary. Back up
`~/.roadmaps/<name>/project.db` first if you may need to return to `1.17.3`.

### Step 3 — Install the agent skills (optional)

```bash
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install-skills.sh | bash
```

### Step 4 — Install and verify

```bash
rmp --version
# Groadmap version 1.18.0 (commit <commit>)
```

### Downgrading

**A `1.17.3` binary does not refuse a database migrated to schema `1.17.0`, and can
corrupt the sprint-membership invariant in it.** `1.17.3` applies a migration only
when the stored version is lower than its own target, and has no check for a newer
one. Measured on 2026-10-01, with a roadmap created by `1.18.0` in an isolated
`HOME` and the `1.17.3` binary built from its tag:

| `1.17.3` command | Exit | Result |
|---|---|---|
| `task list -r <roadmap>` | `0` | `[]`, then both tasks once created |
| `task create -r <roadmap> -t ... -fr ... -tr ... -ac ...` | `0` | `{"id": 2}` |
| `roadmap list`, `sprint list`, `version` | `0` | Normal output |
| `audit list` | `0` | Lists the `TASK_SPRINT_CHANGE` row written by `1.18.0` |
| `audit list -o TASK_SPRINT_CHANGE` | `6` | `invalid audit operation: "TASK_SPRINT_CHANGE"` |
| `sprint add-tasks`, `sprint start`, `task stat 1 BACKLOG` | `0` | Task 1 became `BACKLOG` while still a member of sprint 1 |

Throughout, `_metadata.schema_version` stayed `1.17.0`, and nothing on stderr
signalled the version mismatch. When `1.18.0` opened that database again, it ran no
migration and did not repair the violation: `sprint tasks 1` listed task 1 in
`BACKLOG`, with exit `0`. The violation disappears only when a membership command
touches the task.

**So do not run an older binary against a migrated roadmap.** To go back, restore
the backup taken before the upgrade. A `1.18.0` binary, by contrast, refuses a
database whose schema is newer than its own, with exit `1` and nothing written.

## Why This Is Released as `1.18.0`

A strict reading of Semantic Versioning 2.0.0 gives `MAJOR`. The items under
[Breaking Changes](#breaking-changes) change exit codes, error lines and command
behaviour that `1.17.3` produced, remove a web endpoint, and refuse web requests
that `1.17.3` served. None of that is backward-compatible.

The project publishes `1.18.0` by the owner's explicit decision, recorded here. It
follows the same decision taken for `1.17.2` and `1.17.3`, and it is the ninth
consecutive release published under a smaller digit than the strict reading gives.

**So do not read the minor digit as a promise that nothing breaks.** Upgrading is
safe unless a program of yours does one of the things listed in
[Step 1](#step-1--check-the-programs-that-drive-rmp).
