# Release Notes — Groadmap v1.14.0

**Date:** 2026-08-17
**Type:** Minor (new build targets, schema introspection, release-pipeline hardening)
**Tag:** `v1.14.0`
**Previous release:** `v1.13.3` (2026-07-14)

---

## Executive Summary

Groadmap `v1.14.0` is a **minor release** that widens what the project can ship
and tightens how it ships it.

The build matrix grows from nine targets to **eleven**: `openbsd/amd64` and
`openbsd/arm64` join it because the SQLite driver added them, and the two Windows
targets — listed as Primary Platforms for several releases — **now actually
compile**. They never did: the graph write lock called `syscall.Flock` from a file
with no build tag, and that symbol does not exist on Windows. No gate compiled the
matrix, so the break was invisible.

**Schema introspection** (`SHOW INDEXES` / `SHOW CONSTRAINTS`) becomes a
specified, deliberately accepted read-only operation class on `rmp graph query`,
`rmp graph search`, and the read-only web query bar. It already executed before
this release — but only because the guard rail failed to recognise it, not because
anyone had decided it was safe. A verdict reached by omission cannot be reviewed
and silently absorbs whatever clause family the engine gains next. It is now a
decision, pinned by tests and published on every contract surface.

Underneath, the knowledge-graph engine moves three minor releases forward
(GoGraph `v0.8.1` → `v0.11.0`) and the SQLite driver moves `v1.53.0` → `v1.56.0`.
The GoGraph upgrade carries a **one-way on-disk migration** of `labels.bin`; that
is the single item in this release that deserves a backup before you upgrade.

Three correctness and security fixes land in the database layer, the most
important of which closes a path by which a database **path** could redirect an
open to a different file or switch off foreign-key enforcement.

**The minimum Go version rises from 1.26.5 to 1.26.6.** Four Go standard-library
advisories were reachable from Groadmap's own code — the vulnerable functions are
called, not merely present in the module graph — and **two of them sit on the
`rmp web` request path**. Go 1.26.6 fixes all four, so the floor moves and
`govulncheck ./...` now reports `No vulnerabilities found`. This release also makes
that scan a **required release step** rather than leaving it to whoever remembers.

Finally, a release-pipeline hardening pass closes two defects that affected every
artefact the project has ever published: archives shipped **without the project's
licence file**, and a `v*` tag could publish binaries with neither the linter nor
the security scanner having run anywhere in the pipeline.

## Highlights

- **Eleven build targets.** OpenBSD on amd64 and arm64 are new; Windows on amd64
  and arm64 compile and ship for the first time. OpenBSD and FreeBSD are
  **build-verified, not runtime-verified** — see the honest statement below.
- **Schema introspection is a specified operation class.** `SHOW INDEXES` and
  `SHOW CONSTRAINTS`, with an optional `YIELD` / `WHERE` / `RETURN` projection
  tail, are accepted by the read subcommands and rejected by the write ones —
  by decision, and now by an anchored matcher rather than by the absence of every
  other class.
- **A database path can no longer inject connection parameters.** The DSN is now
  a percent-encoded `file:` URI.
- **Every published archive now carries `LICENSE` and `README.md`.** Until this
  release, every archive of every target shipped without the project's licence.
- **The Go floor rises to 1.26.6, closing four reachable standard-library
  advisories**, two of them on the `rmp web` request path. `govulncheck ./...` is
  clean at this tag, and running it is now a required pre-release step.
- **One validation gate set, enforced locally, in CI, and at release.** No gate
  may be skipped, and no release may report one as waived.
- **One thing to do on upgrade:** the GoGraph store rewrites `labels.bin` from
  format version 1 to version 2 on first write, and **the migration is one-way**.
  Back up your graph directory if you may need to downgrade.

## Why This Is a MINOR Release

Under Semantic Versioning 2.0.0, MINOR is backward-compatible new functionality.
This release adds:

- Two new supported build targets (`openbsd/amd64`, `openbsd/arm64`), taking the
  matrix from nine to eleven.
- Two targets that were specified but non-functional (`windows/amd64`,
  `windows/arm64`) now build and ship.
- Schema introspection as a newly specified, accepted operation class on
  `rmp graph query`, `rmp graph search`, and the read-only web query bar.

No `rmp` command, subcommand, flag, exit code, or JSON success schema is added,
removed, or renamed. No exit code changes meaning. The database schema version is
**unchanged at `1.8.0`**, so this release adds **no SQLite migration**.

## Changes by Category

### Added — Two OpenBSD Build Targets; the Matrix Reaches Eleven

`modernc.org/sqlite` `v1.56.0` added `openbsd/amd64` and `openbsd/arm64` to its
own supported-platform table. The storage engine was the only component that could
have held those targets back: the `rmp` binary is pure Go and links no C library,
so nothing else in the build was platform-bound.

Both targets build under `CGO_ENABLED=0` and are packaged by the release workflow
as `rmp-{version}-openbsd-{arch}.tar.gz`. The existing naming logic needed no
change — OpenBSD is not Windows, so it takes the `tar.gz` branch.

**These targets are build-verified, not runtime-verified.** The binaries are
cross-compiled and checked with `file(1)`; they are never executed, because no
OpenBSD host is available to the project. `SPEC/BUILD.md` now says so plainly, and
a new Architecture Verification criterion pins the check: the ELF note must read
`version 1 (OpenBSD)`. The measured result is
`ELF 64-bit LSB executable, x86-64, version 1 (OpenBSD)` and
`ELF 64-bit LSB executable, ARM aarch64, version 1 (OpenBSD)`.

The same statement now applies to `freebsd/amd64`, which was in exactly the same
unverified position and had never been documented as such.

**Found and fixed in the same cycle:** `install.sh`'s `detect_os` had no OpenBSD
case. A released OpenBSD archive could therefore never have been installed by the
documented one-line installer — the script would have exited with "Unsupported
operating system" on the very platform whose binary it had just been asked to
fetch. `SPEC/DEPLOY.md § Platform Detection` gained an Operating System Detection
subsection specifying the `uname -s` to `GOOS` mapping and requiring every target
in `BUILD.md` to appear in it, so the two lists cannot drift apart again without
contradicting the specification.

### Added — The Two Windows Targets Compile and Ship

`SPEC/BUILD.md` has listed `windows/amd64` and `windows/arm64` among the Primary
Platforms and required every matrix target to build. **Neither compiled.**
`acquireGraphWriteLock` called `syscall.Flock` from a file with no build tag and
no platform counterpart, and `syscall.Flock` does not exist on Windows. Seven of
the nine targets built. The break was invisible because **no gate compiled the
matrix**.

The system calls now sit behind two primitives, `lockGraphWriteFile` and
`unlockGraphWriteFile`. Everything else — the lock-file path, the file handle's
lifetime, the `ErrDatabase` wrapping, and the release closure — stays in
`acquireGraphWriteLock`, so the contract lives in one place rather than being
duplicated per platform.

| File | Mechanism |
|------|-----------|
| `internal/commands/graph_lock_unix.go` | `flock(2)` with `LOCK_EX\|LOCK_NB`, under `//go:build unix` |
| `internal/commands/graph_lock_windows.go` | `LockFileEx` over the whole byte range with `LOCKFILE_EXCLUSIVE_LOCK\|LOCKFILE_FAIL_IMMEDIATELY`, released by `UnlockFileEx` over the identical range |

Two details are load-bearing:

- The Unix file is tagged `//go:build unix`, **not** `!windows`. The latter would
  also admit `plan9`, `js`, and `wasip1`, where `flock` does not exist either.
- `LOCKFILE_FAIL_IMMEDIATELY` is not optional. `LockFileEx` **blocks** until the
  lock is available unless that flag is set, so omitting it would turn the
  immediate failure that `SPEC/GRAPH.md § Concurrency and Recovery` requires into
  a hang.

The exclusion contract is identical on both platforms: exclusive, never blocking,
with contention surfacing as `utils.ErrDatabase` (exit code 1). The lock is not
incidental — it stops a second writer from checkpointing its own stale in-memory
graph and then truncating the WAL that still holds the first writer's committed
change.

**An `install.sh` regression, introduced by shipping those archives and fixed
here.** The Windows branch did not extract: it moved the downloaded archive into
place as `rmp.exe`, its own comment conceding that it assumed the file was the
binary. That was harmless only while no Windows asset existed, because the
download failed first and the user got a clean error. Publishing `.zip` archives
would have turned that clean failure into **silent corruption** — measured against
the pre-fix script, it exited 0, printed `SUCCESS`, and installed a file reported
as Zip archive data. The branch now requires `unzip` and extracts the binary from
the archive root, as the `tar.gz` branch always did; when `unzip` is missing it
installs nothing and exits 1, naming the tool and the manual download URL. The
Linux and macOS paths are unchanged and gain no new tool requirement.

**Regression guards, both proven to fail when the fix is reverted:**

- `cmd/rmp/build_targets_test.go` — `TestSupportedBuildTargetsCompile` builds
  every target on every run of `go test`; removing the Windows file fails exactly
  the two Windows subtests. `TestSupportedBuildTargetsMatchSpec` parses the
  Primary Platforms table out of `SPEC/BUILD.md`, so the test matrix cannot
  silently drift from the specification it claims to enforce. That gate is what
  caught the OpenBSD specification edit while the test matrix still had nine rows,
  which is exactly what it exists for.
- `internal/commands/graph_lock_test.go` — contention must fail fast and must not
  leak handles. Weakening `LOCK_NB` to `LOCK_EX` (the Unix analogue of forgetting
  `LOCKFILE_FAIL_IMMEDIATELY`) makes the timing test fail after 30 s, which no
  assertion on the returned error would have caught.

Both workflows previously claimed Windows was excluded because GoGraph uses
`syscall.Kill`. That was false: the symbol exists only in GoGraph's crashpoint
layer behind the `gograph_crashinject` build tag, which Groadmap never sets.

### Added — Schema Introspection as a Specified Read-Only Operation Class

`rmp graph query`, `rmp graph search`, and the read-only `rmp web` query bar now
**accept schema introspection by decision**:

```sh
# List the indexes the embedded engine currently holds.
rmp graph query -r myproject --query "SHOW INDEXES"

# Introspection takes an optional YIELD / WHERE / RETURN projection tail.
rmp graph query -r myproject \
  --query "SHOW CONSTRAINTS YIELD name, type WHERE type = 'UNIQUENESS' RETURN name"
```

The accepted forms are `SHOW INDEX`, `SHOW INDEXES`, `SHOW CONSTRAINT`, and
`SHOW CONSTRAINTS`, in any case, each with an optional projection tail. The write
subcommands — `create`, `update`, `delete` — reject them.

**How this class arrived, and why it needed fixing.** The engine gained the
`SHOW` introspection commands and the `FOREACH` updating clause, and extended its
own `cypher/ir.IsDDL` to report the former as DDL. Because
`cypher.QueryHasWritingClause` returns false for whatever `IsDDL` accepts, and
Groadmap's own DDL discriminator matches only
`(CREATE|DROP)\s+(INDEX|CONSTRAINT)`, a `SHOW` query reached the guard rail as
**neither a write nor DDL** and passed the read-only check. It therefore already
executed — while `SPEC/GRAPH.md` described no such class at all. The specified
contract and the implemented one had diverged, and the divergence arrived through
a dependency upgrade rather than through a decision.

That is the real defect. A read-only verdict reached because *nothing matched*,
rather than because the class was *judged* read-only, cannot be reviewed, cannot
be tested for intent, and silently absorbs whatever clause family the engine gains
next.

**What changed in the guard rail.** `Classes` gains an `Introspect` field, set
from `reIntrospect` — a statement-anchored (`\A`), case-insensitive matcher for
the four `SHOW` forms, evaluated on the masked query. `IsReadOnly` now decides
through an explicit switch: a write or DDL disqualifies, `Introspect` returns
read-only **by decision**, and an ordinary read falls to the default. Its verdict
is unchanged for every input that existed before; what changed is that the
introspection case is now stated.

Anchoring is what does the work. Without it, a label, variable, or property named
`show` — `CREATE (n:Panel {show:'indexes'})` — would be read as an introspection
command. Leading whitespace is allowed, which also covers a leading comment, since
`MaskLiterals` has already neutralised it to spaces.

Groadmap's DDL class stays **deliberately narrower** than the engine's, and that
is the only remaining reason the local regex exists: `CREATE INDEX` changes the
schema, while `SHOW INDEXES` only reports it. The schema-mutating forms remain
rejected everywhere, in any case and with arbitrary internal whitespace.

`FOREACH` carries **no discriminator of its own** and is classified by the writing
clauses its body contains. That is sound only because a `FOREACH` body may hold
nothing else — an emergent property of the grammar which, until now, nothing
asserted. A refactor of the classifier could therefore have opened a write path
through a read subcommand with every test still green. It is now pinned.

**Published on every contract surface.** An agent reading any of these could
previously not discover that `SHOW INDEXES` was accepted, and an agent that tried
it got a result the documentation said was impossible:

- `internal/commands/graph.go` — the family listing and the `query` / `search`
  help, each carrying a `SHOW` example.
- `internal/commands/registry_graph.go` — the machine-readable AI contract, with
  worked `SHOW` examples carrying their real stdout.
- `internal/aihelp/pitfalls.go` — `graph_guard_rail_mismatch` no longer claims the
  read subcommands accept only `MATCH` queries.
- `README.md` and `DOCS/commands/graph.md` — the Guard Rail table names the class
  in all five rows.

### Changed — GoGraph `v0.8.1` → `v0.11.0` (Three Minor Releases)

**No Go source file changed.** The upgrade is absorbed entirely by the existing
integration layer, which is what `SPEC/GRAPH.md` mitigation 2 intends.

The integration surface was proven intact by the symbol-diff method the project
already uses for this dependency. Across the eight consumed packages, **12
exported symbols moved**:

| Symbol | Change |
|--------|--------|
| `Graph.View` | Removed |
| `SetActiveConstraintCount` | Removed |
| `SetActiveIndexCount` | Removed |
| The six `snapshot.Write*` functions | Re-signed |
| `txn.Tx.CommitWALOnly` | Re-signed |
| `wal.Writer.SyncGroup` | Re-signed |

**Groadmap calls none of the twelve.** Of the 53 symbols it does consume, all are
present and call-compatible: on `wal.Writer` it calls only `Close`, `Sync`, and
`Truncate`, and on the engine only `Run` and `RunInTx`. The release's semantic
changes are likewise unreachable from the CLI, which calls neither `BeginReadTx`,
`BeginTx`, `MVCCStats`, nor `AllocateCommitTS`, and issues no `MERGE` of its own.

#### The `labels.bin` migration is one-way

This is the one operational item in this release that warrants care.

On-disk compatibility was **demonstrated, not assumed**. Against a replica of the
project's own graph directory written under `v0.8.1`, the new binary read back
**293 nodes and 802 relationships** with an unchanged relationship-type
distribution. A write then succeeded, and the synchronous checkpoint **rewrote
`labels.bin` from snapshot format version 1 to version 2, in place**. After the
rewrite, the same counts and the same distribution still read back.

Reading format version 1 is the retained upgrade path. **The rewrite is one-way.**
Once a `v1.14.0` binary has written to a graph store, that store's `labels.bin` is
at format version 2, and a Groadmap binary older than this release cannot be
expected to read it. If a downgrade is a possibility for you, back up the graph
directory before the first write.

Note carefully that this is **not** the SQLite schema. The database schema version
is unchanged at `1.8.0` and this release adds no SQLite migration. The two
mechanisms are independent, and the phrase "no migration" from recent patch
releases does not carry over to the graph store this time.

`SPEC/GRAPH.md § Dependency Maturity Risk` records the format change under
residual risk 2, and a new mitigation 4 now requires an existing graph directory
to be proven readable across a GoGraph upgrade **empirically, before release**,
rather than inferred from upstream release notes.

#### The single-writer semaphore is retired, and the documentation now names the real mechanism

`v0.11.0` retires the engine-level single-writer semaphore that `SPEC/GRAPH.md`,
`SPEC/IMPLEMENTATION.md`, and the `README.md` index all cited as the reason two
concurrent writers serialise.

Every promised behaviour still holds — including failing fast with
`utils.ErrDatabase` rather than hanging or corrupting the store — but the *reason*
is corrected to the real mechanism: **Groadmap's own exclusive, non-blocking
`flock` on `write.lock`**, taken in `acquireGraphWriteLock` before the store is
opened and held across the whole open, commit, checkpoint, and WAL-truncate
sequence. That span is wider than a transaction, so an engine-level writer
exclusion would never have covered it. No requirement, exit code, or acceptance
criterion changed.

| Module | From | To | Kind |

| `github.com/FlavioCFOliveira/GoGraph` | `v0.8.1` | `v0.11.0` | Direct |
| `modernc.org/sqlite` | `v1.53.0` | `v1.56.0` | Direct |
| `golang.org/x/sys` | `v0.47.0` (indirect) | `v0.47.0` (direct) | Promoted |
| `github.com/RoaringBitmap/roaring/v2` | `v2.21.0` | `v2.24.0` | Indirect |
| `github.com/bits-and-blooms/bitset` | `v1.24.6` | `v1.25.0` | Indirect |
| `github.com/mattn/go-isatty` | `v0.0.22` | `v0.0.24` | Indirect |
| `golang.org/x/exp` | `20260709` snapshot | `20260813` snapshot | Indirect |
| `modernc.org/libc` | `v1.74.1` | `v1.74.4` | Indirect (pinned) |

`golang.org/x/sys` is promoted from indirect to direct because the Windows lock
primitives call it. The `go` directive moves from `1.26.5` to `1.26.6` for the
security reason set out in
[Security — The Go Floor Rises to 1.26.6](#security--the-go-floor-rises-to-1266);
**no `toolchain` directive is introduced**, so the `go` directive stays the single
place any pipeline reads the version from, via `go-version-file: go.mod`.

**`v1.56.0` matters on its own.** It patches the transpiled amalgamation for an
upstream SQLite 3.53.3 **data-corruption bug in journal rollback**. A crash while
committing a multi-database `ATTACH` transaction can leave the super-journal name
zeroed while its length and trailing magic survive; the checksum is a plain byte
sum, so an all-zero name still validates, and `pager_playback` then **deletes the
hot journal without replaying it**. Groadmap issues no `ATTACH`, so the exposure
was low — but it is a reason not to sit on `v1.53.0`.

**A pinning trap, caught and fixed in the same cycle.** `go get -u ./...` floated
`modernc.org/libc` to `v1.75.3` and `modernc.org/memory` to `v1.12.0`, silently
breaking the standing upstream requirement that downstream modules pin the exact
`libc` version `modernc.org/sqlite` itself pins (upstream issue #177). `v1.56.0`
pins `libc v1.74.4` and `memory v1.11.0`. `libc` is the transpiled C runtime that
the SQLite amalgamation executes inside, so a mismatch is a **runtime risk in the
storage engine** rather than a compile error; upstream retracted its own `v1.33.0`
over an attempt at this that broke clients.

The violation **passed every gate** — build, vet, unit tests, `golangci-lint`,
`gosec`, and the full E2E suite — and surfaced only from the driver's CHANGELOG in
the module cache. `SPEC/BUILD.md § External Dependencies` now governs
`modernc.org/sqlite` with its own rules, including the explicit statement that
**no gate run by `make check` detects a violation, so a green build is not
evidence**, and a Build Verification checkbox that makes the manual check part of
the release checklist.

Fourteen modules still report an available update, each accounted for: `libc` and
`memory` are the deliberate pins above, and the other twelve are reachable only
through upstream modules' own test binaries, confirmed one by one with
`go mod why`, so none enters this module's build or tests.

### Fixed — A Database Path Can No Longer Redirect the Open or Inject Connection Parameters

`internal/db` built every DSN as `fmt.Sprintf("%s?_pragma=...", dbPath)`. The
driver splits a DSN at the **first `?`** and, unless the string starts with
`file:`, keeps only what precedes it as the filename. A database path containing
`?` therefore **opened a different file from the one intended**, and everything
after the `?` was parsed as driver query parameters.

The blast radius grew with the `v1.53.0` → `v1.56.0` upgrade. Before `v1.55.0` the
shorthand keys did not exist, so a path tail spelling `_foreign_keys=0` or
`_synchronous=off` was ignored, and the failure was a silent wrong-file open.
**Since `v1.55.0` those keys are recognised**, so a path could switch off
referential integrity or downgrade durability on a connection the application
believed it had configured itself.

The roadmap name is validated; **the home directory the path is rooted in is
not.**

Measured before the fix, driver `v1.56.0` on `linux/amd64`: a home directory named
`home?_foreign_keys=0&_synchronous=off` made every query fail with
`invalid _synchronous "off/project.db?_pragma=foreign_keys(1)", expecting one of:
0 OFF 1 NORMAL 2 FULL 3 EXTRA`, and the intended `project.db` was never created.

`dsnWithPragmas` gives way to `dsnFor(dbPath, readOnly)`, used by both `Open` and
`OpenReadOnly`, over a new `uriPath` helper that follows
[the SQLite URI specification](https://www.sqlite.org/uri.html): convert `\` to
`/`, prepend `/` to a leading drive letter, percent-encode, and emit an absolute
path with the empty-authority `//` prefix (`file:///path`) or a relative one
without it (`file:path`). The drive-letter test is on the string rather than on
`runtime.GOOS`, so it cannot turn a relative path into an absolute one. Because
the DSN now starts with `file:`, the driver hands the whole string to SQLite
instead of truncating it, and SQLite decodes the path itself.

**Nothing changes for an ordinary path**: the same PRAGMAs with the same values on
every pooled connection.

### Fixed — Connection PRAGMAs Now Travel in the Driver's Validated DSN Keys

`foreign_keys`, `busy_timeout`, and `query_only` travelled as
`_pragma=name(value)`. That form is executed exactly as written and is **never
validated**, and it is the one DSN parameter class that can still fail partway
through a DSN: a bad value is rejected by SQLite only as it runs, **after every
earlier `_pragma` in the list has already taken effect** — leaving the connection
half-configured.

`modernc.org/sqlite` `v1.55.0` added first-class keys for exactly these three
settings. Their values are checked against a fixed accepted set **before any
parameter is applied**, so a malformed one fails the connection outright, and the
driver applies them in an order it fixes itself (`_busy_timeout` first,
`_query_only` last) independent of the order they are written in.

`dsnFor` now emits `_busy_timeout=10000&_foreign_keys=1`, plus `_query_only=1` on
a read-only open. Only the primary key names are used: each has an alias (`_fk`,
`_timeout`) which **wins when both are supplied**, so carrying a key and its alias
together is a trap, avoided here by construction. `journal_mode` stays out of the
DSN — it is database-level, recorded in the file header, and set once by
`configureConnection`.

Measured on `v1.56.0`, both forms produce the same end state (`query_only=1`,
`foreign_keys=1`, `busy_timeout=10000`), so **this changes failure behaviour only,
not steady-state behaviour**.

### Fixed — Every Database Opens Through the Driver's Connector

`internal/db` opened with `sql.Open("sqlite", dsn)`. `sql.Open` is documented as
**not connecting**: it only looks up the registered driver. Because
`modernc.org/sqlite` deliberately does not implement `driver.DriverContext`, the
DSN was not examined there at all — so a defect in it was reported not by opening
the database, but by **whichever query first forced the pool to dial**, surfacing
mid-command and attributed to that query rather than to the database being opened.

`v1.56.0` added `NewConnector`, which returns a `driver.Connector` backed by the
same driver the package registers as `"sqlite"`. Connections it opens are
identical — every function, collation, connection hook, and virtual table module
registered through the package still applies — but it validates as much of the DSN
as can be checked without touching the filesystem: that the query string parses,
and that the `vfs` parameters do not conflict. `sql.OpenDB` then builds the
`*sql.DB` from it and registers nothing process-globally.

A DSN defect now surfaces **on open**, where it belongs.

## Security — The Go Floor Rises to 1.26.6

`govulncheck ./...` reported **four Go standard-library vulnerabilities that
Groadmap's own code calls**. Reachability matters here: these are not advisories
sitting unused somewhere in the module graph, but functions on paths the binary
actually executes.

| Advisory | Package | Defect fixed in Go 1.26.6 | Reached via |
|----------|---------|---------------------------|-------------|
| [GO-2026-6091](https://pkg.go.dev/vuln/GO-2026-6091) | `html/template` | JavaScript regexp context tracking | `internal/web/pages.go` → `template.Template.ExecuteTemplate` |
| [GO-2026-6090](https://pkg.go.dev/vuln/GO-2026-6090) | `crypto/tls` | Post-handshake messages accepted without limit | `internal/web/server.go` → `http.Server.Serve` |
| [GO-2026-6089](https://pkg.go.dev/vuln/GO-2026-6089) | `net/http` | `ReadHeaderTimeout` not applied to the unencrypted HTTP/2 check | `internal/web/server.go` → `http.Server.Serve` |
| [GO-2026-5972](https://pkg.go.dev/vuln/GO-2026-5972) | `encoding/asn1` | Maximum recursion depth not enforced | `internal/aihelp/hint.go` → `asn1.Unmarshal` |

**Two of the four sit on the `rmp web` request path.** `html/template` renders
every page the server returns and `net/http` serves them, so both are reachable by
whoever can reach the server. That is what moved this from a housekeeping item to
a release blocker.

These are **toolchain** vulnerabilities, not module vulnerabilities: the Go
toolchain version alone remediates them, and no dependency change can. Go 1.26.6
is the release on the 1.26 line that fixes all four, so:

- `go.mod` declares `go 1.26.6`.
- `SPEC/BUILD.md § Go Toolchain` names 1.26.6 as the floor and the four advisories
  that set it.
- `govulncheck ./...` reports **`No vulnerabilities found`, exit code 0**.

The four advisories that the previous toolchain reported as **not called** —
[GO-2026-6218](https://pkg.go.dev/vuln/GO-2026-6218) (`net/url`),
[GO-2026-5942](https://pkg.go.dev/vuln/GO-2026-5942) (`net`),
[GO-2026-5026](https://pkg.go.dev/vuln/GO-2026-5026) (`net/http`), and
[GO-2026-6088](https://pkg.go.dev/vuln/GO-2026-6088) (`stdlib`) — are fixed by the
same release and are gone as well, which is why the scan is clean rather than
merely free of reachable findings.

**No manual installation step is added.** Because the `go` directive names the
patch version, the toolchain enforces the floor itself: under the default
`GOTOOLCHAIN=auto`, a machine whose installed Go is older downloads and uses the
required toolchain instead of building with the wrong one, and a `GOTOOLCHAIN`
pinned to an older release fails with an explicit error instead of building
silently. The CI and release workflows read the version from `go.mod` via
`go-version-file: go.mod`, so they track the directive automatically.

### The Rule That Moves the Floor Is Now Written Down

Before this release the patch floor was a bare fact. `v1.13.2` raised it from
1.26.4 to 1.26.5 for GO-2026-5856, and nothing said when it would move again, so
each occurrence was re-argued from first principles. `SPEC/BUILD.md § Go Toolchain`
now states the rule:

- A standard-library advisory **reachable** from Groadmap's own code raises the
  floor to the release that fixes it. The section is updated to name that release,
  and `go.mod` with it.
- An advisory that is reported but **not called** does not, by itself, raise the
  floor.

That second clause is what makes the rule workable. Without it, every advisory
anywhere in the module graph would move the floor, and the floor would stop meaning
anything. `govulncheck` is what draws the distinction, because it reports the two
categories separately.

### A Required Pre-Release Vulnerability Check

`SPEC/VERSION.md § Release Process` gains a new **step 1, Pre-Release Vulnerability
Check**. `govulncheck ./...` MUST now be run against the exact tree being released,
and its result acted on, before anything else happens. Every later step is
renumbered, and `SPEC/DEPLOY.md § Release Checklist` gains the matching items.

It is deliberately **step 1**, before the version bump: a finding changes `go.mod`
and `SPEC/BUILD.md`, and those changes belong in the release commit rather than in
a follow-up. This release is the worked example — the check ran, found four
reachable advisories, and the remediation is part of the same commit as the version
bump.

The specification gives the release engineer an outcome table rather than leaving
the judgement open:

| What the report shows | What the release engineer does |
|-----------------------|--------------------------------|
| Nothing (`No vulnerabilities found`) | Continue to the version bump |
| A standard-library vulnerability that **is called** | Stop. Raise the Go floor to the release that fixes it, update `go.mod` and `BUILD.md § Go Toolchain`, re-run until clean. The release MUST NOT be published on the old floor |
| A vulnerability outside the standard library that **is called** | Stop. Remediation means changing a dependency, and the pins are governed by `BUILD.md § External Dependencies`. Refer the decision to the project owner |
| A vulnerability reported but **not called** | Continue; it does not block. Record it in the release notes so the judgement is visible |

**It is deliberately not a seventh gate.** The gate set stays at the six gates of
`SPEC/BUILD.md § Validation Gates`, enforced identically in all three places, and
the specification explicitly forbids adding `govulncheck` to `make check`,
`ci.yml`, or `release.yml`. The reason is that a gate must be reproducible: making
this one a gate would turn a pipeline red because an advisory was published between
two commits, with nothing in the repository having changed. The obligation belongs
to the release procedure, where a person reads the report and decides.

For the same reason, **`govulncheck` is not pinned** to a version, unlike
`golangci-lint` (v2.12.2) and `gosec` (v2.28.0). Those are pinned so that a gate
returns the same verdict everywhere it runs. This check is the opposite case: its
whole purpose is to reflect the vulnerability database as it stands at release
time, so a run that reported nothing last month may legitimately report something
today.

**Why this step exists.** This release was prepared, passed all six gates, passed
the full 48-test end-to-end suite, and was tagged — and its binaries would have
shipped carrying four standard-library vulnerabilities reachable from Groadmap's
own code, two of them on the `rmp web` request path. Every gate was green, because
no gate inspects published advisories. Nothing in the procedure required anyone to
look, so nobody did. This step is what requires someone to look.

## Release Pipeline and Distribution

These four changes are user-visible in the artefacts the project publishes.

### Every Published Archive Now Carries the Licence

`SPEC/BUILD.md § Artifact Structure` has **always** specified three entries per
archive — the binary, `LICENSE`, and `README.md` — while `release.yml` packed the
binary alone. **Every published archive of every target therefore shipped without
the project's licence file.** This is now fixed for release archives and for the
rolling `dev` pre-release alike.

- The `tar.gz` holds `rmp`, `LICENSE`, and `README.md`.
- The Windows `zip` holds `rmp.exe`, `LICENSE`, and `README.md`.

Verified by execution rather than by reading the YAML: `tar -tzf` and `unzip -Z1`
list exactly those entries, both shipped files are byte-identical to the
repository copies, the extracted binary runs, and the `install.sh` extraction path
still finds the binary in the enlarged archive.

Verifying it exposed two specification gaps, closed first: the `zip`'s contents
were never specified (the only statement that the Windows archive holds `rmp.exe`
was a comment in `release.yml` — the string `.exe` appeared nowhere in `SPEC/`),
and the rolling `dev` pre-release sat outside the block's scope by accident. The
licence travels with **every** binary the project distributes, so the structure now
governs every published archive, `dev` included.

### One Validation Gate Set, Enforced in All Three Places

`release.yml` ran `go fmt`, `go vet`, and the tests, and nothing else. `ci.yml` ran
`golangci-lint` but never `gosec`. Only the local `make check` ran all six gates.

**A `v*` tag could therefore be pushed and binaries published with neither the
linter nor the security scan having run anywhere in the pipeline**, resting
entirely on the release engineer having run `make check` on their own machine.

An honest note about the record: **ten release-notes files between `v1.6.0` and
`v1.13.0` record the security gate as skipped** because `gosec` was not installed
on the release host, nine of them citing "per project policy". **No such policy was
ever specified, and none is invented now.** `SPEC/BUILD.md` now states the
opposite, as a rule:

> A missing tool is a failure, never a skip. A workflow MUST install the tools its
> gates need; probing for a tool and continuing without it, reporting a gate as
> waived, and `continue-on-error` are each forbidden. No release may report a gate
> as skipped.

Validation Gates is promoted to a top-level section and made the single
authoritative definition: the same six gates run locally, in `ci.yml`, and in
`release.yml`, whole and unchanged, with no per-pipeline exception. Only three
differences are permitted, and they are enumerated: `fmt` fails instead of
rewriting (`go fmt` then `git diff --exit-code`), the tests run with `-race` and CI
additionally measures coverage, and `build` is a host build locally against a
matrix build in the workflows. The coverage upload is reporting, not a gate.

Both static-analysis tools are now **pinned to an exact version**, and the pins
bind local installations too, because `make lint` and `make security` run whatever
is on `PATH`. A tool's version is part of its gate's meaning.

| Tool | Pin |
|------|-----|
| `golangci-lint` | `v2.12.2` |
| `gosec` | `v2.28.0` |

`ci.yml` also moves to least privilege: `contents: read` at workflow level, with
`contents: write` raised only on `dev-release`, the one job that writes to the
repository.

**Measured, not assumed.** Each of the five gates was made to fail on an injected
violation, one at a time, running the exact commands the steps run: an unformatted
file, a `Printf` verb mismatch, an ineffectual assignment, a failing test, and a
hardcoded credential.

The regression gate, `cmd/rmp/workflow_gates_test.go`, pins both workflows to the
specification — every expected value is **parsed out of `SPEC/BUILD.md` rather than
restated**, so raising a pin in the specification alone fails the test. It asserts
the complete gate set per workflow, both tool pins agreeing across the
specification and both files, the absence of skip constructs and
`continue-on-error`, the `needs:` chain from gates to build to publish, and least
privilege in both workflows. Proven by 24 fault injections, every one caught,
against 8 cosmetic reformattings, every one tolerated.

Two pre-existing defects were found and fixed in the same cycle: the documented
`golangci-lint` install command used the **v1 module path**, which installs
`v1.64.8` and cannot read this project's `version: "2"` configuration, so anyone
following the specification got a linter unable to lint the repository; and
`SPEC/BUILD.md` wrote the release artefact suffix as `{goarch}{goarm}`, naming the
ARM targets `linux-arm6` and `linux-arm7`, while the workflow produces
`linux-armv6` and `linux-armv7` — which is also what `install.sh` asks for.

### `install.sh` Rejects Unsupported Architectures at Detection

**This is a behaviour change users can observe.**

`install.sh` mapped `i386` and `i686` to `arch="386"`, and the guard that followed
rejected only the value `"unknown"`. A 32-bit x86 host therefore passed straight
through platform detection and failed much later, on an HTTP download for
`rmp-{version}-linux-386.tar.gz` — **an asset no release has ever produced**. The
user was shown a download error instead of being told their platform is not
supported.

`SPEC/DEPLOY.md § Architecture Detection` has always specified the opposite: 32-bit
x86 is not produced by the build, and the script exits 1 with a stated message. The
script diverged from the specification, so the script changed.

`detect_arch` now returns `"unsupported"` for an architecture it recognises but the
build does not serve, keeping `"unknown"` for one it does not recognise at all. The
guard rejects **both** — rejecting only one is exactly how this defect arose. Both
guards report the raw `uname` output rather than the mapped name, because the
mapping is what failed.

No working installation is lost: no published binary has ever existed for 32-bit
x86. What changes is that the user is told plainly, at detection, and **before any
network access**. The OS guard was given the same shape so the two failures read
alike, which also changes what the script prints for an unsupported operating
system.

`tests/test_49_install_platform_guards.py` drives the real script end to end in a
hermetic sandbox with stubbed `uname` and `curl` and a `PATH` holding only the
tools under test. It pins exit 1 and the specified message for `i386`, `i686`, and
an unrecognised architecture, the same for an unsupported operating system, and
that **every supported architecture still resolves to its documented target** —
because a guard that rejects too much is as broken as one that rejects too little.
It also asserts that nothing is requested once a guard fires: the `curl` stub
records every invocation, and the recording must be empty.

### The Version `ldflag` Never Worked, and Is Gone

Both workflows built with `-X main.version=...`, which **the linker silently
ignores**: `cmd/rmp/main.go` declares `version` inside a `const` block, and `-X`
writes only to a package-level `var`. Measured rather than reasoned — a build with
`-X main.version=9.9.9-PROOF` still reported `1.13.3`.

The flag is removed from both workflows. This is worth stating plainly: **the
constant in `cmd/rmp/main.go` has always been the real source of the version, and
still is**, which is what `SPEC/VERSION.md` specifies and what the release
procedure already does. No binary changes behaviour, because the flag was already
inert. What is gone is a promise in the YAML that the next reader would have
trusted.

The regression gate parses `cmd/rmp/main.go` with `go/ast` — standard library, no
new dependency — collects the package-level `const` names, and fails any `-X`
naming one, in both the bare and full-import-path forms the linker accepts. It
first asserts that `version` **is** a `const` per `SPEC/VERSION.md`, so flipping
the declaration to a `var` fails loudly instead of quietly re-enabling the flag.

## Upgrade Notes

**There is no SQLite migration.** The database schema version is unchanged at
`1.8.0`. An existing `project.db` opens unchanged.

**The graph store does migrate, and the migration is one-way.** On the first write
by a `v1.14.0` binary, the synchronous checkpoint rewrites `labels.bin` from
snapshot format version 1 to version 2, in place. Reading version 1 is the retained
upgrade path; there is no downgrade path.

```sh
# If you may need to downgrade, back up the graph directory BEFORE the first
# write with v1.14.0. Reads alone do not trigger the rewrite.
cp -a ~/.roadmaps/myproject ~/.roadmaps/myproject.pre-v1.14.0
```

```sh
# Build from source (requires Go 1.26.6+; see Security above).
# Under the default GOTOOLCHAIN=auto an older Go fetches 1.26.6 by itself.
git fetch --tags
git checkout v1.14.0
go build -o ./bin/rmp ./cmd/rmp

# Verify
./bin/rmp --version
# Groadmap version 1.14.0
```

If you install with the one-line installer, note that a 32-bit x86 host is now
rejected at detection with a stated message and exit code 1, rather than failing
later on a download. OpenBSD hosts are recognised by `detect_os` for the first
time.

### Open

Ordered by what actually affects a user of this release.

- **A stranded `snapshot.bak` stops every later graph checkpoint, and the write
  still exits 0.** This is upstream GoGraph behaviour and the one item here that
  can affect you in normal use.

  The snapshot publish is a crash-atomic three-step swap — archive the live
  snapshot to `snapshot.bak`, rename the staging directory into place, then drop
  the backup — chosen so that at every instant at least one complete snapshot
  exists on disk. The cleanup of a stale backup before the swap is best-effort
  (`_ = fsys.RemoveAll(bak)`). If that residue cannot be removed, for example
  because of directory permissions, the archive rename then fails against a
  non-empty `snapshot.bak` and the checkpoint returns an error.

  Groadmap surfaces that error as `Warning: graph checkpoint failed: ...` on
  **stderr** and returns **exit code 0**. That is required behaviour, not an
  oversight: `SPEC/GRAPH.md` FR7 states that a checkpoint failure *after* a durable
  commit MUST NOT fail the write, because the commit is already durable and the WAL
  is intact.

  The practical consequences:

  - **No data is lost.** The WAL is intact and recovery still works.
  - **Automation can miss it.** The exit code is 0 and stdout is the normal success
    JSON; only stderr says anything.
  - **The WAL grows without bound** while the condition lasts, because only a
    successful checkpoint truncates it.

  It **self-heals**: remove `snapshot.bak` from `~/.roadmaps/<roadmap>/graph/` and
  the next write checkpoints and truncates normally. Watch stderr on
  `rmp graph create`, `rmp graph update`, and `rmp graph delete`.

- **The graph read path builds an in-memory engine where the specification requires
  a store-backed one.** `SPEC/GRAPH.md § Engine Construction and Lifecycle`
  requires `cypher.NewEngineWithStore`, stating that the in-memory `NewEngine`,
  `NewEngineWithOptions`, and `NewEngineWithRegistry` constructors are not used for
  persisted graphs. The write path (`internal/commands/graph.go:840`) complies. The
  two read paths — `internal/commands/graph.go:693` and `internal/web/data.go:652`
  — call `cypher.NewEngine(res.Graph)`.

  **No user-visible consequence has been demonstrated, and the claim is limited to
  what the code supports.** Both read paths construct the engine over a graph that
  `recovery.Open` has already loaded from the on-disk snapshot and write-ahead log,
  so a read still observes committed state; the graph end-to-end suites exercise
  exactly that across process exits and pass. It is recorded as a
  specification-conformance divergence, not as a data-correctness defect. Tracked
  as `rmp` task #149.

- **The sprints web page renders plain count badges where `SPEC/WEB.md` requires
  semantic ones.** The tab badges show counts without the status-derived Tabler
  colour variant that `SPEC/WEB.md § Status, Priority, and Severity Badge Colours`
  defines as the single authoritative mapping. Presentation only — the counts are
  correct, and no `rmp` command output is affected. Tracked as `rmp` task #127.

- **Two knowledge-graph nodes share the key `README.md`.** `knowledge-model.md`
  states that every node's `key` is globally unique across the graph, so that
  `MATCH (n {key:'...'})` without a label is unambiguous. A `Doc` node and a `Spec`
  node both carry the key `README.md`. The model contradicts itself rather than
  merely being violated by the data: it keys `Spec` nodes by bare file name and
  `Doc` nodes by repository-relative path, and for `README.md` the two rules
  produce the same string. This concerns the project's own internal knowledge
  graph — not any user's roadmap data, and no `rmp` command output. Tracked as
  `rmp` task #155.

- **`.gosec.yaml` documents three accepted finding classes while the code carries
  six.** The file records G104, G201, and G304 with locations and justifications;
  the sources also carry `#nosec` suppressions for **G204**, **G302**, and
  **G703**, which are undocumented. The `security` gate is green and every
  suppression was individually verified as safe when written, so this is an
  auditability gap rather than an unreviewed suppression: what is missing is the
  written record of why three of the classes are accepted, and nothing detects the
  drift. Internal hygiene; no user-facing behaviour depends on it. Tracked as
  `rmp` task #141.
