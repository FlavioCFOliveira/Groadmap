# Release Notes — Groadmap v1.17.1

**Date:** 2026-09-14
**Type:** Patch by the owner's decision — **but it changes the shape of the AI Agent Contract, removes two bounds from `rmp graph serve`, and makes two commands refuse invocations that used to succeed** (see [Breaking Changes](#breaking-changes))
**Tag:** `v1.17.1`
**Previous release:** `v1.17.0` (2026-09-08)

---

## Executive Summary

Groadmap `v1.17.1` corrects claims the project makes about itself. Most of it makes a
published statement true: the exit codes the AI Agent Contract declares, the examples it
prints, the error strings the specification publishes, and five help texts that said a
command prints nothing when it prints a JSON object. It also takes the graph engine to
GoGraph `v0.14.1`, whose headline fix is an indexed `MATCH` that could return a wrong
answer.

**Read the breaking list before you upgrade, because the version number will not warn
you.** A strict SemVer reading of this release gives `MAJOR`. The project publishes
`1.17.1` by the owner's explicit decision, recorded in
[Why This Is Released as `1.17.1`](#why-this-is-released-as-1171-and-what-that-number-hides).

The three incompatibilities:

1. **`rmp --ai-help` moves to `schema_version` `2.0.0`.** Each subcommand's `exit_codes`
   is a list of objects rather than of integers, and `prerequisites` is omitted when a
   subcommand has none. A consumer written against `1.0.0` cannot read it.
2. **`rmp graph serve` no longer bounds an idle session or its own shutdown.** A session
   that sends nothing is no longer closed after 60 seconds, and a signalled server whose
   client stops reading after the shutdown has begun may never exit.
3. **`rmp stats` and `rmp roadmap list` refuse an unrecognised flag** with exit code `2`,
   where they used to ignore it and print their result. `rmp stats` also prints its help
   for a help token written after the roadmap selector, where it printed the report.

There is **no database migration**. One dependency changes: GoGraph `v0.14.0` →
`v0.14.1`.

---

## Highlights

- **An indexed lookup returns the right rows.** GoGraph `v0.14.1` fixes an equality index
  seek that lost rows the same statement had written and returned rows whose indexed value
  had changed away from the one sought.
- **The contract says when each exit code happens.** Every declared code carries the
  conditions that produce it, and the lists are complete over the conditions a caller
  controls.
- **`rmp task next` tells you it ignores dependencies**, and names `rmp task blockers` as
  the command that answers whether a returned task can be finished.
- **A graph store round-trips between `1.17.0` and `1.17.1`**, in both directions, with
  its data, indexes and UNIQUE constraints intact — measured, not assumed.

## Breaking Changes

### 1. The AI Agent Contract moves to `schema_version` `2.0.0`

`rmp --ai-help` changes shape in two places, and `SPEC/DATA_FORMATS.md` classifies each as
a major change of the contract: a consumer written against a list of integers cannot read
a list of objects, and a consumer that expects `prerequisites` on every subcommand meets a
missing key.

**Each subcommand's `exit_codes` is a list of objects.** On all 56 subcommands, every
entry is `{"code": <integer>, "conditions": [<string>, ...]}`. For `roadmap list`:

```jsonc
// 1.17.0 (schema_version 1.0.0)
"exit_codes": [0],
"prerequisites": []

// 1.17.1 (schema_version 2.0.0)
"exit_codes": [
  {"code": 0, "conditions": ["Every roadmap under ~/.roadmaps/ was written to stdout as a JSON array; an empty array when the directory holds none."]},
  {"code": 2, "conditions": ["A token beginning with - names none of this subcommand's flags.",
                             "More positional arguments were supplied than this subcommand accepts."]}
]
// no "prerequisites" key
```

The lists were incomplete, and are widened at the same time:

| Declared code | Subcommands declaring it in `1.17.0` | In `1.17.1` |
|---|---:|---:|
| `2` | 18 | 56 |
| `4` | 44 | 52 |
| `6` | 38 | 41 |
| All entries | 219 | 268 |

**`prerequisites` is omitted when a subcommand has none.** Under `1.0.0` every subcommand
carried the key, and every one carried it as an empty list. In `2.0.0`, 46 subcommands
carry a populated list and 10 carry no key: `roadmap list`, `task list`, `sprint list`,
`backlog list`, `backlog show-next`, `audit list`, `audit history`, `audit stats`, `stats`
and `ai-help`.

**Additive, and breaking nothing on its own:** each of the 20 pitfalls gains `wrong_exit`
and `wrong_stderr`, the exit code and the exact stderr line its wrong example produces.

**Unchanged:** the top-level `exit_codes` catalogue, `conventions`, `enums`,
`global_flags`, and the set of 56 subcommands.

**The test to apply:** you are unaffected unless a program reads `rmp --ai-help`. Such a
program must accept objects in `exit_codes` and a missing `prerequisites` key. It can tell
the two shapes apart by `schema_version`:

```bash
rmp --ai-help | python3 -c "import json,sys; print(json.load(sys.stdin)['schema_version'])"
# 2.0.0
```

### 2. `rmp graph serve` no longer bounds an idle session or its own shutdown

GoGraph `v0.14.1` ships all four of its timeout defaults disabled. `1.17.0` set two of
them itself: a connection timeout of 60 seconds and a default statement timeout. `1.17.1`
sets neither. The statement budget is carried by the maximum statement timeout alone, which
the engine applies to a client that asks for no timeout of its own, so a statement is still
cut at 5 seconds. Nothing else replaces the connection timeout.

Measured against unmodified binaries built from both trees (see
[Measured Behaviour of `rmp graph serve`](#measured-behaviour-of-rmp-graph-serve)):

| Scenario | `1.17.0` | `1.17.1` |
|---|---|---|
| An authenticated session that sends nothing | Closed by the server after **60.001 s** | **Still open at 150.100 s**, when observation stopped; it then ran `RETURN 1` successfully |
| `SIGTERM` while a client reads a large result, which keeps reading for 1.0 s and then stops | Server exited after **60.448 s**, exit `0` | **Not exited at 150.001 s**; it exited 0.117 s after the client resumed reading, exit `0` |
| `SIGTERM` while a client has already stopped reading a large result | Exited after 7.557 s, exit `0` | Exited after 7.572 s, exit `0` |
| A peer that connects and never speaks Bolt | Dropped after 10.010 s | Dropped after 10.009 s |

**A session that sends nothing is no longer closed after 60 seconds.** It keeps its
connection, and the connection slot it occupies, until the client disconnects or the
server stops.

**A signalled server may never exit.** The shutdown's drain closes the socket of a client
that was already parked in a write when the drain began, and that case is unchanged. A
client that parks **after** that moment — one that stops reading during the drain, or one
that reads just enough for each write to complete and the next to park — is not selected,
and nothing else releases it, because no deadline is armed on a socket write. `SIGKILL` is
then the only remedy. Under `1.17.0` the connection timeout ended that case after 60
seconds.

**One stderr line changes its closing clause.** The `WARN` record for the connections the
shutdown closed keeps its identifying message and its `connections=` count:

```
# 1.17.0
... so nothing else would have ended those sessions before the connection timeout" connections=1

# 1.17.1
... and no deadline is armed on such a write, so nothing else would have ended those sessions at all" connections=1
```

**The test to apply:** you are unaffected unless a Bolt client other than
`rmp graph client` holds a session open without using it and relies on the server to close
it, or a supervisor waits for `rmp graph serve` to exit after `SIGTERM` without escalating
to `SIGKILL`. `rmp graph client` sends one statement per invocation and then disconnects.

### 3. `rmp stats` and `rmp roadmap list` refuse an unrecognised flag

Both commands used to discard an unrecognised flag and print their normal result at exit
`0`, alone among the commands of the CLI. `SPEC/COMMANDS.md § Positional Arguments`, rule
5, already required the refusal. Each now exits `2`, writes nothing to stdout, and prints
the CLI-wide line before the roadmap is looked up. A help token is served before any of
this, wherever it is written (see
[`rmp stats` ignored a help token written after the roadmap selector](#rmp-stats-ignored-a-help-token-written-after-the-roadmap-selector)).

Driven against both binaries under an isolated `HOME`:

| Invocation | `1.17.0` | `1.17.1` |
|---|---|---|
| `rmp roadmap list --nosuchflag` | exit `0`, the listing | exit `2`, `Error: invalid input: unknown flag: --nosuchflag` |
| `rmp roadmap list -r <name>` | exit `0`, the listing | exit `2`, `Error: invalid input: unknown flag: -r` |
| `rmp stats -r <name> --nosuchflag` | exit `0`, the report | exit `2`, `Error: invalid input: unknown flag: --nosuchflag` |
| `rmp stats --nosuchflag -r <name>` | exit `0`, the report | exit `2`, `Error: invalid input: unknown flag: --nosuchflag` |
| `rmp stats -r <missing> --nosuchflag` | exit `4`, `Error: resource not found: roadmap "<missing>"` | exit `2`, `Error: invalid input: unknown flag: --nosuchflag` |
| `rmp stats -r <name> --helpful` or `-help` | exit `0`, the report | exit `2`, `Error: invalid input: unknown flag: --helpful` or `-help` |
| `rmp stats -r <name> --help`, `-h` or `help` | exit `0`, the report | exit `0`, the help |
| `rmp stats -r <name> --zzz --help` | exit `0`, the report | exit `0`, the help |
| `rmp stats --zzz --help` | exit `3`, `Error: no roadmap selected: use -r <name> or --roadmap <name>` | exit `0`, the help |
| `rmp stats --help` / `rmp roadmap list --help` | exit `0`, the help | exit `0`, the help, which now lists exit code `2` |
| `rmp stats -r <name>` / `rmp stats --roadmap <name>` / `rmp roadmap list` | exit `0` | exit `0`, byte-identical output |

**The test to apply:** you are unaffected unless an invocation passes `rmp roadmap list`
any flag other than a help token, or passes `rmp stats` anything besides `-r <name>` or
`--roadmap <name>`. Run the invocation once: an exit `2` naming an unknown flag names the
token to remove, and help printed where you expected the report names a help token to
remove.

## What Was Silently Wrong Before

### An indexed `MATCH` could return a wrong answer

The equality index seek in GoGraph `v0.14.0` was blind to writes the same statement had
made. It **lost rows the statement had written** and **returned rows whose indexed value
had changed away** from the one sought, in a single autocommit statement with no explicit
transaction. An equality lookup of a node by an indexed property is such a seek. GoGraph
`v0.14.1` declines the index for the coordinates a transaction has changed, which turns a
wrong answer into a slower correct one. The same engine release closes four index-build
paths that could put a row in an index that the graph does not contain, or leave one out.

A store written before `v0.14.1` carries index payloads that such a path could have
written, so a server **rebuilds its secondary indexes once** when it first opens such a
store, and the snapshot manifest gains an additive `index_builder_epoch` field at the next
checkpoint. No data changes and no migration step is needed.

### The contract's declared exit codes were incomplete

A subcommand could exit `2`, `4` or `6` without declaring the code. The widened lists are
described under [Breaking Changes](#1-the-ai-agent-contract-moves-to-schema_version-200).

### Four pitfall examples did not demonstrate their own lesson

- `graph_client_without_a_server` published a socket path that exists only on the machine
  that wrote it. It now uses the declared `<socket>` placeholder.
- `missing_commit_hash_on_transition` took its argument from `git` rather than from `rmp`:
  written as `$(git rev-parse HEAD)`, it succeeded or failed on whether the caller stood
  inside a git checkout. It now carries a literal hash.
- `complete_with_open_dependencies` could not reach the dependency guard it describes. Its
  wrong example now starts from `TESTING` and supplies `--commit-close`, so the refusal it
  shows is the dependency guard's own:
  `Error: validation error: cannot mark task #2 as COMPLETED: incomplete dependencies: #1`.
- `invalid_roadmap_name` was split into two arguments by the shell before `rmp` saw it. It
  is now quoted.

### The `record_task_working_log` workflow omitted two prerequisites

Its final step closes the task, which requires the task to be in `TESTING` with no
dependency that is not itself `COMPLETED`, and requires the caller to supply the commit
hash. Both are now listed.

### `rmp task next` did not say that a task it returns may be blocked

The help text now carries, and the contract states the same:

```
The listing is NOT filtered by dependencies, and a task it returns may be
blocked. Selection is on sprint membership and task status alone: a task
whose declared dependencies are not yet COMPLETED is returned like any
other, at its own planned rank, and nothing in the returned object marks it
as blocked.
```

It names `task blockers <task-id>` as the command that answers the readiness question.

### Five `sprint` help texts said the command prints nothing

`sprint reorder`, `move-to`, `swap`, `top` and `bottom` each print a JSON success object.
Their help texts said `Output: empty (exit 0)`. For `sprint top`:

```
# 1.17.0
Output: empty (exit 0). Audits SPRINT_TASK_MOVE_POSITION.

# 1.17.1
Output: a JSON success object naming the sprint, the task, and the position it
now holds (exit 0). Audits SPRINT_TASK_MOVE_POSITION.
```

`SPEC/COMMANDS.md § Move Task to Top/Bottom` made the same false claim, and now publishes
the object with its four keys: `success`, `sprint_id`, `task_id` and `position`.

### Published error strings disagreed with the binary

The `SPEC/COMMANDS.md` Task Ordering tables now publish the seven lines the binary really
prints, and both completion-guard strings in `SPEC/STATE_MACHINE.md` recover the
`validation error: ` prefix they had dropped. The binary's own strings are unchanged.

### `rmp roadmap list --help` and `rmp stats --help` did not list exit code `2`

Both now list it, matching the refusal in
[Breaking Changes](#3-rmp-stats-and-rmp-roadmap-list-refuse-an-unrecognised-flag).

### `rmp stats` ignored a help token written after the roadmap selector

`SPEC/HELP.md` requires a handler to serve `--help`, `-h` and the word `help` anywhere in
its arguments, before any other parsing runs, and `task list` already did. `rmp stats`
looked only at its first argument, so a help token anywhere else was ignored, with the
report printed instead, or never reached because another refusal came first. It now tests
the whole argument list:

| Invocation | `1.17.0` | `1.17.1` |
|---|---|---|
| `rmp stats -r <name> --help`, `-h` or `help` | exit `0`, the report | exit `0`, the help |
| `rmp stats -r <name> --zzz --help` | exit `0`, the report | exit `0`, the help |
| `rmp stats --zzz --help` | exit `3`, no roadmap selected | exit `0`, the help |
| `rmp stats <stray-argument> --help` | exit `3`, no roadmap selected | exit `0`, the help |
| `rmp stats -r <name> --helpful` or `-help` | exit `0`, the report | exit `2`, unknown flag |

The help printed is byte for byte the output of `rmp stats --help`. An unknown flag with
no help token is still refused with exit `2`, and `rmp roadmap list`, which already
served a help token in any position, is unchanged. Regression tests in
`internal/commands/help_token_after_selector_test.go` hold both commands, and two
`task list` controls, to their own help in every position.

### `rmp web` printed its help without the AI-agent banner when the help token was not first

`SPEC/HELP.md § AI agent banner` requires the banner on every help printer. `rmp web`
served a help token itself only when it was the first argument. Anywhere else the token
reached the server's own flag parser, which printed the help without the banner, or
refused the invocation before it reached the token. `rmp web` now tests the whole
argument list, and the defect, present in `1.17.0`, is gone:

| Invocation | `1.17.0` | `1.17.1` |
|---|---|---|
| `rmp web --no-open --help`, `--no-open -h`, `--port 0 --help` or `--host 127.0.0.1 --help` | exit `0`, the help without the banner (1748 bytes) | exit `0`, byte for byte what `rmp web --help` prints (1821 bytes) |
| `rmp web --zzz --help` | exit `2`, `Error: invalid input: unknown flag: --zzz` | exit `0`, the help |
| `rmp web <stray-argument> --help` | exit `2`, `Error: invalid input: unexpected argument: <stray-argument>` | exit `0`, the help |
| `rmp web --port abc --help` | exit `6`, `Error: validation error: --port must be an integer between 0 and 65535 (got "abc")` | exit `0`, the help |
| `rmp web --port --help` | exit `6`, the same line ending `(got "--help")` | exit `0`, the help |
| `rmp web --helpful` or `-help` | exit `2`, unknown flag | exit `2`, unknown flag |

Regression tests in `internal/commands/web_help_banner_test.go` require the
banner-wrapped help in nine positions, each dispatch bounded at 10 seconds so that a
regression which starts the server fails rather than hangs.

### The exit-code exhaustiveness rule did not say what it was exhaustive over

`SPEC/DATA_FORMATS.md` required each subcommand's exit codes to be exhaustive. The rule now
covers the conditions a caller controls — flags and their values, standard input read in
place of an absent flag, positional arguments, the roadmap selector, and the roadmap's
state — and does not enumerate faults in the environment.

## Internal Changes

These change no output of the binary.

- **Gates that drive the binary rather than inspect the source.**
  `tests/test_70_published_contract_execution.py` is a new end-to-end module that executes
  the invocations `rmp --ai-help` publishes and asserts each one's exit code, stderr line
  and stdout shape. `tests/test_55_error_string_parity.py` now reads
  `SPEC/STATE_MACHINE.md` as well as `SPEC/COMMANDS.md`, and fails on a table row that
  publishes an error line without its `Error: ` prefix. New Go tests hold the declared exit
  codes, the prerequisites, the pitfall oracle fields, the workflow steps and the source of
  every published argument.
- **The cost of `SIGKILL` is written once.** The list of what `SIGKILL` skips no longer
  names the store lock, which the kernel releases however the process exits. A test proves
  the lock is released after a killed server, and another refuses a second copy of the
  wording.
- **A concurrency test asserted more than the contract offers.**
  `internal/graphserve/concurrency_test.go` required every one of sixty statements from two
  overlapping writers to succeed; a conflict lost on every retry within the budget is a
  published outcome. It now accepts either a commit or that refusal, and checks the end
  state against each writer's last commit.
- **`tests/test_64_graph_schema_management.py`** re-measured its three version stamps
  against GoGraph `v0.14.1`.
- **Project process and knowledge model.** `CLAUDE.md` working rules, and
  `knowledge-model.md` (the provenance pair, the constraint and index sections).

## Upgrade Notes

### Step 1 — If a program reads `rmp --ai-help`, adapt it to `schema_version` `2.0.0`

Read each subcommand's `exit_codes` as objects, and treat a missing `prerequisites` key as
an empty list. A program that must accept both binaries can branch on `schema_version`.

### Step 2 — If you run `rmp graph serve` under a supervisor, escalate to `SIGKILL`

Give `SIGTERM` a grace period and then escalate. Every acknowledged commit is durable, the
next open replays the write-ahead log, and the kernel releases the store lock; what
`SIGKILL` skips is the shutdown checkpoint and the socket removal, and the next
`rmp graph serve` removes a dead socket itself. A long-lived Bolt client should close a
session it no longer uses, because the server no longer does.

### Step 3 — Remove undeclared flags from `rmp stats` and `rmp roadmap list`

```bash
# Find them across your scripts, agent prompts and stored recipes
grep -rnE "rmp (stats|roadmap list|road list|roadmap ls)" .
```

`rmp roadmap list` takes no flag but a help token. `rmp stats` takes `-r <name>` or
`--roadmap <name>`; `--help`, `-h` or `help` anywhere prints the help instead of the
report.

### Step 4 — There is no database migration

The SQLite schema version is unchanged at `1.14.0` and no migration was added. The first
`rmp graph serve` against an existing graph rebuilds its secondary indexes once. The store
round-trips in both directions (see [Store Round Trip](#store-round-trip)), but **a
downgrade to `1.17.0` brings back the index-seek defect** this release fixes.

### Step 5 — Install and verify

```bash
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install.sh | bash
rmp --version
# Groadmap version 1.17.1

rmp --ai-help | python3 -c "import json,sys; print(json.load(sys.stdin)['schema_version'])"
# 2.0.0
```

## Why This Is Released as `1.17.1`, and What That Number Hides

Semantic Versioning 2.0.0 requires the `MAJOR` version to be incremented "if any backward
incompatible changes are introduced to the public API", and permits a `PATCH` increment
only "if only backward compatible bug fixes are introduced". `SPEC/VERSION.md` defines
`PATCH` as "Bug fixes, backward compatible". This release contains three changes that are
not backward compatible:

1. the AI Agent Contract takes a shape a consumer of the previous one cannot read, which
   `SPEC/DATA_FORMATS.md` itself classifies as a major change of the contract;
2. `rmp graph serve` withdraws a published bound on idle sessions and on its own shutdown;
3. `rmp stats` and `rmp roadmap list` refuse invocations that succeeded on `1.17.0`.

The strict reading therefore gives `2.0.0`.

The project publishes `1.17.1` by the **owner's explicit decision**, taken on 2026-09-14
and recorded here. `1.18.0` and `2.0.0` were considered and not taken.

This is the sixth consecutive release published under a smaller digit than the strict
reading gives, each by a decision recorded at the time: `1.15.0` as a `MINOR`, `1.15.1` as
a `PATCH`, `1.15.2` as a `PATCH`, `1.16.0` as a `MINOR` after it was first tagged as
`2.0.0`, withdrawn and renumbered, and `1.17.0` as a `MINOR`. The `1.17.0` record counts
three predecessors and omits `1.15.1`.

**Do not read the patch digit as a promise that nothing breaks.** The test to apply is
short:

> Upgrading is safe unless a program of yours reads `rmp --ai-help`, a Bolt client of
> yours holds a session to `rmp graph serve` open without using it or your supervisor
> waits for the server to exit without escalating to `SIGKILL`, or you pass `rmp stats`
> anything besides its roadmap selector or `rmp roadmap list` any flag.

**What did not change, and why it does not soften the above.** No command, subcommand or
flag was added or removed. The production code that changed is confined to the flag
refusal in `stats` and `roadmap list`, help-token routing in `stats` and `web`, the
options `rmp graph serve` passes the engine, the contract `rmp --ai-help` generates, and
help text. The top-level exit-code catalogue is unchanged. Of the 64 distinct help
invocations, 55 print byte for byte what `1.17.0` printed. These are reasons the release
is not *more* disruptive than it is; none of them makes it a patch.

---

## What Is Not In This Release

- **No option to bound an idle session or a parked write.** `rmp graph serve` declares no
  timeout flag, and Groadmap arms no deadline of its own.
- **No authentication or transport security on the graph server.** The socket is mode
  `0600` inside a roadmap home that is `0700`, and that filesystem permission is the whole
  of the access control. The engine prints a warning for each at startup.

### Measured Behaviour of `rmp graph serve`

**Method.** Unmodified binaries were built from `git archive v1.17.0` and from `d37229d`,
this release's tree before its version constant moved and before `fb25db4` and `99f6d7a`,
neither of which touches the graph server, the graph client or the graph store. Each run started its own server under an isolated `HOME`, with `--socket`
naming a short path, and drove it through a raw Bolt 5.6 client over the Unix socket. The
large result was `MATCH (n:Row) RETURN n` over 20000 nodes, each carrying an 80-byte
property. Hardware: AMD Ryzen 9 5900HX, 16 logical CPUs; Linux 6.8.0-139-generic x86_64;
`go1.27.0`. The eight runs ran concurrently.

| Run | `1.17.0` | `1.17.1` |
|---|---|---|
| **Idle session.** `HELLO` and `LOGON`, then nothing, observed for up to 150 s | Server closed the session after 60.001 s (`EOF`) | Session open at 150.100 s; `RETURN 1` on it then succeeded. `SIGTERM` with it still open: exit `0` after 7.516 s |
| **Client parks after the drain began.** Read at about 80 KiB/s; `SIGTERM`; kept reading 1.0 s (701 records, 81920 bytes) with the stream still open; then stopped | Exit `0` 60.448 s after `SIGTERM`. Stderr: `bolt: write error ... i/o timeout`, 60.285 s after `SIGTERM` | Still running 150.001 s after `SIGTERM`. The client resumed reading and the server exited `0` 0.117 s later; the client's stream ended with `FAILURE Neo.TransientError.General.RequestInterrupted: context canceled` |
| **Client parked before the signal.** Sent `RUN` and `PULL`, never read, `SIGTERM` after 2 s | Exit `0` after 7.557 s, 180255 bytes waiting, cut record `connections=1` | Exit `0` after 7.572 s, 180255 bytes waiting, cut record `connections=1` |
| **Silent peer.** Connected and never sent the handshake | Dropped after 10.010 s; `bolt: handshake failed ... i/o timeout` | Dropped after 10.009 s; same line |

Both "client parks after the drain began" runs also logged
`graph server teardown reported a failure err="bolt: shutdown: drain timeout exceeded"` at
`ERROR` before exiting `0`; that line is the same under both binaries.

| 4 | `1.17.1` | Opened the store `1.17.0` had written to | Constraint and indexes listed; stage 3's node and changed value found; counts correct; a duplicate refused. It wrote nothing, so it took no checkpoint and the field stays absent until the next write |
