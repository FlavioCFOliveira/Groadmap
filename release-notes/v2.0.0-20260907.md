# Release Notes — Groadmap v2.0.0

**Date:** 2026-09-07
**Type:** Major — **contains backward-incompatible changes that break existing callers** (see [Breaking Changes](#breaking-changes))
**Tag:** `v2.0.0`
**Previous release:** `v1.15.2` (2026-09-01)

---

## Executive Summary

Groadmap `v2.0.0` gives the knowledge graph a **dedicated server** and takes away the
five subcommands through which the graph used to be reached. Those two facts are one
change: the subcommands existed only to enforce an operation class before execution,
that enforcement was withdrawn, and with it went the only thing that told the five
apart. `rmp graph execute` runs what any of them ran.

**This is the first Groadmap release numbered by the strict SemVer reading rather than
by an owner's decision.** `1.15.0` shipped breaking changes as a `MINOR` and `1.15.2`
shipped them as a `PATCH`, each recorded as an explicit exception at the time. Nothing
here overrides SemVer: three independent incompatibilities are present and any one of
them carries `MAJOR` on its own.

1. **Five subcommands are gone with no aliases.** `rmp graph create`, `query`, `update`,
   `delete` and `search` each exit `127`. Every script, agent prompt and stored recipe
   that names one stops working.
2. **Two build targets are withdrawn.** `linux-armv6` and `linux-armv7` are no longer
   produced. A user on 32-bit-only hardware **cannot upgrade at all** — which is the
   strongest incompatibility a distributed binary has.
3. **Published error strings changed across many lines.** `database error: ` no longer
   covers the knowledge graph; four new sentinels carve up what it used to. This project
   treats a published error string as contract and drives a 138-string corpus against
   the binary, so this is a contract change rather than incidental output drift.

**What is new is a server.** `rmp graph serve` opens a roadmap's graph once and answers
Cypher over a Unix domain socket, on the graph engine's own Bolt v5 server. `rmp graph
client` sends one statement to it. Both existing surfaces — `rmp graph execute` and the
web interface's graph page — find a running server and route through it **automatically,
with no flag and no configuration**. Measured on an 8-core / 16-thread workstation,
served reads rise from **2,563 to 18,359 ops/s** between one and 64 concurrent clients,
with the knee at about **16**.

**`EXPLAIN` and `PROFILE` now publish the plan the engine builds**, on `execute` and
`client` alike. The defect this closed is worth naming: an `EXPLAIN` of a *writing*
statement used to print `{"ok": true}` — byte-identical to what a real committed write
reports — over a statement that had written nothing. The output was not merely
uninformative; it was false.

**One change is a deliberate reduction in safety, and it is stated rather than buried.**
The web interface's graph query bar now executes the statement it is given, writes
included, over an unauthenticated `GET`. `?q=MATCH (n) DETACH DELETE n` empties the
roadmap's knowledge graph. `--host 0.0.0.0` has become a **write** grant over every
roadmap's graph where it was a read grant. This is an owner decision taken with the
consequence understood, and it is recorded in full in `SPEC/WEB.md § Security and
Constraints`, rule 3.

**There is no database migration.** The SQLite schema version is unchanged, and the graph
store's on-disk format takes no version step: GoGraph's changes to it are additive, and
the round trip was measured in both directions — a graph and a schema written by `2.0.0`
are read correctly by `1.15.2`, and the reverse holds too. See
[Upgrade Notes](#upgrade-notes), Step 5, for the one narrow caveat.

**Scope.** 44 commits, 177 files, +37,410 / −18,555. Two sprints closed inside the
window — *Dedicated Graph Server* (38 tasks, which carries both the guard-rail withdrawal
and the server) and *Refresh the dependencies that have a newer release* (2 tasks) — plus
**three of the seven tasks** of the sprint that is still open. See
[What Is Not In This Release](#what-is-not-in-this-release).

## Highlights

| | |
|---|---|
| **A dedicated graph server** | `rmp graph serve` holds one roadmap's graph open and answers Bolt v5 over a Unix domain socket until stopped. One server per roadmap, enforced by the store lock. |
| **A client, and automatic routing** | `rmp graph client` sends one statement to a running server. `rmp graph execute` and the web graph page find one and use it with no flag and no configuration. |
| **Query plans** | `EXPLAIN` plans without executing; `PROFILE` executes and measures. Both publish a plan tree, byte-identically across the direct and served paths. |
| **The guard rails are gone** | Five subcommands collapse into `execute`. Groadmap checks a statement's length and nothing else about its content. |
| **Nine build targets, all 64-bit** | `linux-armv6` and `linux-armv7` withdrawn, for reasons that are about data safety rather than about the build. |
| **Errors name the subsystem** | `graph engine error:`, `graph store error:`, `graph server error:` and `I/O error:` replace a `database error:` that named the wrong thing. |
| **Batch refusals name the ids** | `task 99 not found` / `tasks 98, 99 not found`, and a repeated id is no longer a false failure. |

## Breaking Changes

### 1. The five `rmp graph` subcommands are removed, with no aliases

`rmp graph create`, `rmp graph query`, `rmp graph update`, `rmp graph delete` and
`rmp graph search` are each now an unresolved subcommand name, answered as a dispatch
failure: **exit code `127`**, the `graph` help on stderr, nothing on stdout.

The replacement is textual. `rmp graph execute` runs what any of the five ran:

```bash
# Before                                          # After
rmp graph query  -r p --query "MATCH (n) ..."     rmp graph execute -r p --query "MATCH (n) ..."
rmp graph create -r p --query "CREATE (n) ..."    rmp graph execute -r p --query "CREATE (n) ..."
rmp graph update -r p --query "MATCH ... SET ..." rmp graph execute -r p --query "MATCH ... SET ..."
rmp graph delete -r p --query "... DELETE n"      rmp graph execute -r p --query "... DELETE n"
rmp graph search -r p --query "MATCH (n) ..."     rmp graph execute -r p --query "MATCH (n) ..."
```

**Why they could not survive as aliases.** The five differed in exactly one thing: the
operation class each accepted, enforced before execution. That enforcement was withdrawn
in this same cycle, and with it the only distinction between them. Five names for one
behaviour is a difference the CLI can no longer honour, and keeping them would have
published a choice that no longer decides anything.

**What follows from the withdrawal, and what it costs:**

- **`execute` runs what it is given, and the caller owns what that does.** No
  subcommand's contract says a statement cannot delete. Groadmap checks the statement's
  length and nothing else about its content, so a statement's effect is decided by its
  Cypher alone. `SPEC/GRAPH.md § What Groadmap Does Not Check` enumerates the hazards
  that follow, each of which reports success.
- **Exit code `6` no longer means an operation-class mismatch.** On `graph execute` its
  only remaining cause is a statement longer than 1 MiB. The five refusal lines the
  classes published — `graph create accepts only CREATE/MERGE queries` and its four
  siblings — are withdrawn with them.
- **The store lock collapses to one mode.** Groadmap cannot know before running a
  statement whether it will write, so every invocation on the direct path takes the
  advisory lock **exclusively**, across the whole open, execution, commit, checkpoint and
  write-ahead-log truncation sequence. Two statements against one roadmap now serialise
  even when neither writes, where a shared reader hold let them overlap. An invocation
  that finds the lock held now **waits** under bounded backoff instead of failing on the
  first collision. The dedicated graph server is the answer to that cost; the one-shot
  CLI path pays it.
- **A statement that appends nothing to the write-ahead log does not checkpoint**, so an
  ordinary read leaves `snapshot/` and `wal` exactly as it found them.
- **The `--ai-help` contract changed shape**: the `graph` family publishes `execute`,
  `serve` and `client` where it published five, and the `graph_guard_rail_mismatch`
  pitfall is replaced by `graph_statement_is_not_checked`.

The withdrawal deleted `internal/cypherguard` entirely — 11 files, 4,927 lines — and
rewrote 355 in-tree call sites across `internal/`, `DOCS/`, `tests/` and `README.md`.
`release-notes/` was deliberately left untouched: each file records what was true at the
release it names.

### 2. `linux-armv6` and `linux-armv7` are no longer built

The release ships **nine** archives where it shipped eleven. `install.sh` refuses a
32-bit ARM host **at architecture detection**, before any release asset is requested —
the same treatment `i386` and `i686` already received — and its target list narrows:

```
before: architecture <uname -m> is not supported. Supported targets: amd64, arm64, armv6, armv7. ...
after:  architecture <uname -m> is not supported. Supported targets: amd64, arm64. ...
```

The `/proc/cpuinfo` ARM-version fallback is deleted, because with no 32-bit ARM target
left to choose between it has nothing to decide.

**Who is affected.** 32-bit-only hardware: Raspberry Pi Zero, Zero W, Pi 1 and Pi 2.
`linux-arm64` is unaffected and covers the Pi 3, 4, 5 and Zero 2 W. A Pi 3 or later
running a 32-bit operating system recovers by installing a 64-bit one. Every other target
is unchanged, and because no ARM variant remains, every archive is now named
`{goos}-{goarch}` with no ARM exception.

**Three independent facts put 32-bit out of reach, and each alone is sufficient:**

1. **It does not compile.** GoGraph v0.13.0 pads its Bolt transaction registry entry to a
   hard-coded 128 bytes and asserts that size from both directions at compile time. On a
   32-bit platform the structure reaches 80 bytes, one assertion resolves to an array of
   negative length, and `internal/graphserve` — which `rmp` cannot link without — fails
   to build. Measured per version, compiling the engine's `bolt/server` package alone:
   **v0.12.0 builds for `GOARCH=arm` and `GOARCH=386`; v0.13.0 and v0.14.0 do not.** No
   build tag or compiler flag avoids it.
2. **It was never a verified configuration**, and this is about the version being
   *replaced*, not the new one. At **v0.12.0**, GoGraph's own suite compiled for `386`
   already failed three size-pinning tests and would not compile its packstream tests at
   all, while a control run of the same tests on `amd64` at the same commit passed — so
   the word size is the cause and not flakiness. GoGraph publishes Linux and macOS on
   `amd64` and `arm64` only, and runs no 32-bit CI.
3. **The stored graph would not be portable.** GoGraph persists `int`, `uint` and
   `uintptr` as `u64`. A graph written by a 64-bit build is misread by a 32-bit one.

**Restoring the compile would have restored a build, not a working target.** Shipping
those two binaries was a data-safety problem rather than a build problem, which is why
they are withdrawn rather than repaired.

### 3. `database error:` no longer covers the knowledge graph

The prefix survives, **narrowed to a roadmap's SQLite database** — its contents, its
schema, a statement against it, or the `project.db` file. Everything else that used to
arrive under it now carries one of four new sentinels:

| Prefix | What failed | What the reader acts on | Exit |
|--------|-------------|-------------------------|------|
| `graph engine error: ` | The statement reached the engine and did not complete there: a parse failure, a refusal, an exhausted time budget, a lost write conflict | The **statement** | 1 |
| `graph store error: ` | The graph store, its directory, or its exclusive advisory lock | The **filesystem** or the **lock holder** | 1 |
| `graph server error: ` | A graph server, its socket, or the connection to it | The **server**, or `--socket` | 1 |
| `I/O error: ` | Any other stream, socket, file or directory that is not a roadmap's database | The **stream or path** named | 1 |

**The axis is the reader's next action**, which is why four classes are worth having
where one was not: a statement you must rewrite, a lock you must wait out or a filesystem
you must repair, a server you must reach or stop, and a stream you must supply are four
different jobs.

**The dividing line is the artefact, not the layer**, and one consequence looks
inconsistent until that rule is read: moving a legacy `project.db`, or failing to secure
it to `0600`, stays `database error:` although both are file operations, because the
artefact is the database.

Representative lines that moved:

| Before | After |
|--------|-------|
| `Error: database error: graph query failed: <engine diagnostic>` | `Error: graph engine error: graph query failed: <engine diagnostic>` |
| `Error: database error: graph query exceeded the 5s statement time budget; ...` | `Error: graph engine error: graph query exceeded the 5s statement time budget; ...` |
| `Error: database error: graph write conflict: another writer committed first ...` | `Error: graph engine error: graph write conflict: another writer committed first ...` |
| `Error: database error: graph store unavailable: <detail>` | `Error: graph store error: graph store unavailable: <detail>` |
| `Error: database error: no graph server is listening on <socket>` | `Error: graph server error: no graph server is listening on <socket>` |
| `Error: database error: cannot bind 127.0.0.1:8787: ...` (`rmp web`) | `Error: I/O error: cannot bind 127.0.0.1:8787: ...` |
| `Error: reading data directory <path>: database error` | `Error: I/O error: reading data directory <path>` |

Note the last row: it also **inverts**. The old line published the class where the
operating system's diagnostic belongs. A new wrapping rule now binds every wrap in the
tree, published or not, to render the sentinel first.

**No exit code moved.** All four new sentinels reach exit `1` by the same fall-through
`database error:` uses. `cmd/rmp/main.go` — the sole owner of the sentinel-to-exit-code
mapping — is byte-identical across the two commits that made this change, and
`SPEC/ARCHITECTURE.md § Adding New Error Types` now **forbids** an exit-1 sentinel from
having a `handleError` case at all, so the two can never disagree. The web interface is
unaffected: its graph endpoint branches on its own error kind, so no HTTP status changed.

### 4. The store-contention line stops naming a holder it cannot know

```
before: Error: database error: graph store is busy: another invocation still holds it after the bounded wait
after:  Error: graph store error: graph store is busy: still held when the bounded wait was exhausted,
        and nothing records the holder. Another rmp invocation releases it shortly, so run the statement
        again; an rmp graph serve holds it for its whole lifetime, so reach that server with --socket,
        or stop it.
```

The old line **contradicted its own function's documented reasoning** — a bounded wait is
sized against the maximum lawful hold, and a server has none — so it named the one holder
the wait cannot resolve. The two possible holders imply **opposite** remedies: an ordinary
invocation releases shortly, so retrying works; a server holds for its whole lifetime, so
retrying never will. Probing for a server was **rejected rather than overlooked**: a
server can start or stop between the probe and the print, so the line would assert a
holder it cannot know it still has, and the web graph endpoint reaches the same lock with
no socket flag to probe with.

### 5. A batch refusal names the ids it is about

`some tasks not found`, published at six sites for every shape, becomes:

| Condition | Before | After |
|-----------|--------|-------|
| One id missing | `Error: resource not found: some tasks not found` | `Error: resource not found: task 999999 not found` |
| Two or more missing | `Error: resource not found: some tasks not found` | `Error: resource not found: tasks 999999, 999998 not found` |
| `sprint add-tasks`, ids absent | `Error: resource not found: task(s) not found: [999999 999998]` | `Error: resource not found: tasks 999999, 999998 not found` |
| `sprint remove-tasks`, one non-member | `Error: validation error: task(s) not in sprint #N: [2]` | `Error: validation error: task 2 is not in sprint #1` |
| `sprint remove-tasks`, several | `Error: validation error: task(s) not in sprint #N: [2 3]` | `Error: validation error: tasks 2, 3 are not in sprint #1` |

Two orthogonal changes: the ids are **named** rather than merely counted, and the
rendering moves from Go's slice printer — bracketed, space-separated, undeduplicated — to
`4, 5`, each id named once, in the caller's order, never shortened. **The singular form
follows the number missing, not the number supplied**: one absent id out of five prints
the singular line, where `some tasks not found` previously asserted a plural subset of a
batch that did not exist.

Nine commands publish these lines: `task get`, `task prio`, `task sev`, `task reopen`,
`task remove`, `task stat`, `sprint add-tasks`, `sprint remove-tasks` and
`sprint move-tasks`.

### 6. The web graph data endpoint executes writes over an unauthenticated `GET`

`GET /roadmaps/{name}/graph/data` no longer validates the `q` parameter. A `CREATE`, a
`SET`, a `DETACH DELETE` or a schema `CREATE INDEX` submitted through the knowledge-graph
page's query bar is executed, committed and checkpointed, exactly as `rmp graph execute`
would run it. **`?q=MATCH (n) DETACH DELETE n` empties the roadmap's knowledge graph.**

**This is an owner decision taken with the consequence stated.** The server has no login,
no token and no session, so the only access control is the bind address, and
`--host 0.0.0.0` is now a **write** grant over every roadmap's knowledge graph where it
was a read grant. `SPEC/WEB.md § Security and Constraints`, rule 3, records it in full.

Two consequences a caller will meet:

- **The published `kind` set drops from five values to two.** `not_read_only`,
  `schema_introspection` and `relationship_read_direction` are **removed**, along with the
  four-deep precedence rule between them. What remains is `invalid_limit` and `execution`,
  and the only ordering left is that the `limit` is resolved before the statement runs.
- **A slow statement through the query bar now blocks the CLI**, and two graph pages open
  on the same roadmap serialise. The endpoint takes the store's exclusive lock across the
  statement, the commit and the checkpoint, so an `rmp graph execute` against the same
  roadmap waits for it, bounded, and fails with exit code 1 when that wait is exhausted.

`SHOW INDEXES` is now answered `200` with `{"nodes": [], "edges": []}` — executed, not
refused — because the rows it returns carry no node and no edge.

## What Is New

### `rmp graph serve` — a dedicated graph server

`rmp graph serve` opens a roadmap's store once, holds it and its exclusive advisory lock
for the life of the process, and answers Cypher over a **Unix domain socket** until it is
stopped, printing the socket it bound as `{"socket": "<path>"}` on stdout.

The protocol is **Bolt version 5**, served by the graph engine's own server. Groadmap
defines no protocol of its own and **binds no network port**. It is the second long-lived
command after `rmp web`: `SIGINT` or `SIGTERM` drains the work in flight, shuts the server
down, checkpoints, releases the lock, removes the socket and exits `0`.

```bash
# Hold the graph open until Ctrl+C; it prints the socket it bound
rmp graph serve -r backend-platform
# {"socket": "/home/you/.roadmaps/backend-platform/graph.sock"}
```

It **serves a graph that already exists and creates none**: against a roadmap whose store
has never been written it exits `1` rather than making one. Run one `rmp graph execute`
first.

- **One server per roadmap**, enforced by the store lock: a second `rmp graph serve`
  against the same roadmap fails with exit code `1` and leaves the incumbent's socket
  untouched. A server asked to bind a socket another roadmap's server owns is refused by a
  socket probe instead.
- **Access control is the filesystem and there is no other.** The socket is created with
  mode `0600`, set explicitly rather than left to the umask, inside a roadmap home that is
  `0700`. **The server authenticates nobody and uses no transport security**, both
  deliberately, and it prints a warning for each at startup. Any caller that can open the
  socket can read, write, delete and change the schema of that roadmap's graph.
- **What it buys is measured, not asserted.** A caller pays one store open for a whole
  session instead of one per invocation, and statements that used to serialise on the
  store's exclusive lock run concurrently under the store's MVCC. On an 8-core /
  16-thread workstation, served reads go from **2,563 ops/s at one client to 18,359 ops/s
  at 64**, with read throughput reaching roughly seven to eight times the single-client
  rate and stopping at a knee near **16** concurrent clients. Past that knee another
  client buys under 5% more throughput and multiplies the 99th-percentile latency nearly
  fivefold. The connection ceiling is **128**, set well above the knee because a refused
  connection is dropped without a protocol answer and is not retried.

### `rmp graph client` — send one statement to a running server

It resolves the same socket `serve` binds, sends the statement, and writes **byte for
byte** what `rmp graph execute` writes for that statement against that graph. It reads and
writes alike, and it **requires** a server: with nothing listening it fails with exit code
`1` rather than opening the store, because a subcommand that quietly became `execute`
would report a success that says nothing about whether a server was reached. A
serialisation conflict — two clients writing the same nodes at once, which is ordinary
inside a server — is retried under the project's retry policy rather than reported.

### Automatic routing through a running server

`rmp graph execute` and the web graph data endpoint both resolve the roadmap's socket
before they open anything. With a server answering there, the statement is sent to it and
the store is never opened locally; with nothing answering, the store is opened directly
under the exclusive lock exactly as before. **No flag and no configuration selects this**,
and the statement, the result, the output shape and the exit code are the same either way.

Measured: `execute` against a served roadmap goes from **7.51 s and exit 1** to
**0.013 s and exit 0**, and the web endpoint from HTTP 500 to HTTP 200 in 1.9 ms.

**Why it had to change.** A server holds the store's exclusive lock for its whole process
lifetime, and no finite wait can be sized against a hold with no upper bound. Left on the
direct path, both surfaces would have failed deterministically — every invocation and
every graph page request — for as long as a server ran.

Three details a caller should know:

- **A leftover socket file is not an error.** A killed server leaves one behind; the
  refused connection is read as evidence that the roadmap is not served, and the caller
  proceeds on the direct path without removing the file.
- **A probe that answers but yields no server is a failure, not a fallback.** Falling back
  there would send the caller at a lock a server may be holding, so `graph execute` fails
  with exit code `1` and the web endpoint answers HTTP `500`. A connection lost after the
  statement was sent is likewise a failure and is **not** retried against the store: a
  commit is durable before it is acknowledged, so the statement's outcome is genuinely
  unknown, and the error line says exactly that.
- **The web interface cannot follow `--socket`.** It is an HTTP handler with no command
  line, and no request parameter carries a socket path. A server started with `--socket`
  therefore leaves that roadmap's graph page answering HTTP `500` on every request for as
  long as it runs. Start a server without the flag whenever the roadmap is also browsed.

### `--socket <path>` on `execute`, `serve` and `client`

All three default it to `~/.roadmaps/<name>/graph.sock`, derived from the roadmap. The
flag names **which socket is looked at** and nothing else: it does not force a server,
does not forbid one, and does not select the store.

### `EXPLAIN` and `PROFILE` publish the query plan

| Prefix | Runs the statement? | Returns | Member |
|--------|--------------------|---------|--------|
| `EXPLAIN` | No — planned, not executed | Declared columns, **no rows**, and the plan | `plan` |
| `PROFILE` | Yes | Real rows, and what each operator cost | `profile` |

```bash
$ rmp graph execute -r backend-platform --query "EXPLAIN MATCH (s:Spec)-[:IMPLEMENTED_BY]->(c:Code) RETURN s.key"
{
  "columns": ["s.key"],
  "rows": [],
  "plan": {
    "operator": "ColumnarProject",
    "children": [ { "operator": "ColumnarFilter", "children": [
      { "operator": "columnarExpand", "children": [
        { "operator": "NodeByLabelScan", "detail": "Spec",
          "estimatedRows": 1, "estimatedRowsSource": "exact" } ] } ] } ]
  }
}                                                                        exit 0

$ rmp graph execute -r backend-platform --query "PROFILE MATCH (s:Spec) WHERE s.status = 'implemented' RETURN s.key"
{
  "columns": ["s.key"],
  "rows": [["auth"]],
  "profile": {
    "operator": "ColumnarProject", "rows": 1, "timeNs": 19905,
    "children": [ { "operator": "ColumnarFilter", "rows": 1, "timeNs": 13270,
      "rowsRemovedByFilter": 0, "children": [
        { "operator": "NodeByLabelScan", "detail": "Spec",
          "estimatedRows": 1, "estimatedRowsSource": "exact",
          "rows": 1, "timeNs": 3771, "dbHits": 1 } ] } ]
  }
}                                                                        exit 0
```

**The two members are never both present**, which is what stops an estimate being read as
a measurement. An `EXPLAIN` tree carries only `estimatedRows` and `estimatedRowsSource`,
never `rows`, `timeNs`, `dbHits` or `rowsRemovedByFilter`, because it ran nothing and a
figure there would be invented.

- **The two surfaces agree by construction rather than by vigilance.** The client inverts
  the Bolt encoding back onto the engine's own plan node rather than onto JSON, so both
  surfaces then run one mapping. Measured across five statement classes, `EXPLAIN` output
  is byte-identical between `graph execute` and `graph client` with nothing excused; a
  `PROFILE` differs in `timeNs` alone, and it must, because that member measures the
  execution and the two subcommands are two executions. The specification's byte-identity
  claim was narrowed in five places to say so.
- **Four measured keys are pointers rather than plain integers**, so that `omitempty`
  cannot collapse a *counted* zero into an *uncounted* one — the distinction the whole
  feature exists to draw. Which is built is decided by the engine's own known-flags, never
  by the value. `timeNs` publishes whole nanoseconds rather than a millisecond float, so
  the identity above holds on an integer rather than on two float formatters agreeing on a
  last digit.
- **A `PROFILE` of a writing statement is refused**, because profiling it would mean
  committing it, and neither prefix is accepted on a schema statement. Both exit `1` with
  the engine's own diagnostic.

**A statement written with neither prefix produces exactly the bytes it produced before.**

## What Was Silently Wrong Before

### An `EXPLAIN` of a writing statement reported a committed write

On `1.15.2`, `EXPLAIN CREATE (n:ShouldNeverExist)` printed exactly `{"ok": true}` at exit
`0`, and a follow-up `MATCH (n:ShouldNeverExist) RETURN count(n)` returned `0`. The output
was **byte-identical to what a real committed write reports**, over a statement that had
written nothing. It was not merely uninformative; it was false, and nothing distinguished
it from the real thing.

The cause was one discriminator: the output shape was chosen on "does the statement
declare columns", and an `EXPLAIN CREATE` declares none. A prefixed statement now always
returns the `{columns, rows}` shape, with empty arrays beside its plan where it declares no
column of its own.

Two siblings went with it: an `EXPLAIN` of a read returned an empty row set
indistinguishable from a query that matched nothing, and a `PROFILE` discarded its
measurement entirely.

### A repeated id produced a false `resource not found` on all nine batch commands

The membership guard compared a **count** where it meant a **set**, and the database
returns one row per *distinct* id, so the two numbers differ whenever a caller repeats one.

- `rmp task get -r X 1,1` with task 1 present failed at **exit 4** with
  `some tasks not found`. Nothing was missing.
- `rmp sprint add-tasks 1 4,4` was worse: it printed `task(s) not found: []` — a message
  asserting that ids were missing and then naming none.
- `rmp sprint move-tasks 1 2 1,1` refused a valid move at **exit 6**.

A repeated id is now accepted: the list is reduced to the set it denotes, each distinct
task is acted on once, and one audit entry is written per distinct id. The arithmetic lives
once, in `internal/utils/idlist.go`, so *which ids are missing* and *how many are there*
cannot be answered inconsistently. Deduplication is applied at the call site rather than
inside the shared id parser, deliberately: `sprint reorder` shares that parser and a repeat
is a genuine error there.

**No invocation that previously succeeded now fails.** The only movement is failures
becoming successes.

## Upgrade Notes

### Step 1 — Rewrite every call that names a withdrawn subcommand

This is the only mandatory migration, and it is mechanical.

```bash
# Find them across your scripts, agent prompts and stored recipes
grep -rnE 'rmp graph (create|query|update|delete|search)\b' .
```

Replace the subcommand with `execute` and change nothing else: the flags, the statement,
the output shape and the exit codes are the same. A missed call site fails loudly at exit
`127` rather than doing something unintended, so the failure mode is safe.

**Check whether you were relying on a refusal.** If any of your statements depended on
`graph query` refusing to write, that guarantee is gone: `execute` runs what it is given.
The guarantee you need about a statement is now a guarantee about the text you supply.

### Step 2 — Update anything that matches on error text

If you parse stderr, the `database error: ` prefix no longer appears for graph or I/O
failures. Match on the four new sentinels instead, or — better — match on the **exit
code**, which did not change anywhere. `SPEC/ARCHITECTURE.md § Sentinel Error Catalogue` is
canonical for the mapping.

If you match on `some tasks not found`, that string no longer exists. See
[Breaking Changes §5](#5-a-batch-refusal-names-the-ids-it-is-about).

### Step 3 — Check your architecture before upgrading

```bash
uname -m
```

`x86_64`, `amd64`, `aarch64` and `arm64` are served. `armv6l`, `armv7l`, `i386` and `i686`
are **not**, and `install.sh` will refuse before downloading anything. On a Raspberry Pi 3
or later, installing a 64-bit operating system restores the upgrade path; on a Pi Zero,
Zero W, Pi 1 or Pi 2, `v1.15.2` is the last release that runs.

### Step 4 — If you expose `rmp web` beyond loopback, reconsider

`--host 0.0.0.0` is now a **write** grant over every roadmap's knowledge graph. If you were
relying on the interface being read-only, that is no longer true of the graph query bar.
The remedy is the bind address, because the server has no other access control.

### Step 5 — There is no database migration

The SQLite schema version is unchanged and nothing is migrated on first run.

**The graph store's on-disk format takes no version step, and the round trip was measured
rather than assumed.** Both directions were driven with two binaries built from the two
tags. A graph plus a registered index written by `2.0.0` is read back correctly by a
`1.15.2` binary; a graph plus an index written by `1.15.2` is read back correctly by
`2.0.0`, with the index still `ONLINE`; and `1.15.2` still reads its own store correctly
after `2.0.0` has opened it. The snapshot manifest declares `version: 3` in both, and both
carry the same 17-byte `GGMANIF` framing trailer.

**That trailer is not new here, and an earlier draft of this section said it was.** The
CRC32C framing trailer and the manifest's `indexes_commit_ts` field both arrived in GoGraph
`v0.12.0`, which `1.15.2` already shipped, so neither is a change this window makes. The
only wire-level addition in this window is the columnar one described next.

**One narrow caveat, which fails closed.** The columnar file format gained two new wire
values for 1- and 2-byte edge-weight kinds. The existing values keep their meaning, so
every earlier file reads unchanged; an older reader meeting one of the two new values
**refuses the file** with an unknown-weight-kind error rather than misreading it. Groadmap
writes no edge weights of its own, so this is not reachable through `rmp`, but it is the
one place where a downgrade could meet a file it will not open — and it stops rather than
returning wrong data.

Downgrading to `1.15.2` therefore reads the same data, subject only to the subcommand names
differing between the two binaries.

curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install.sh | bash
rmp --version
# Groadmap version 2.0.0

rmp graph execute -r <roadmap> --query "MATCH (n) RETURN count(n)"

## Why This Is Released as `2.0.0`

`SPEC/VERSION.md` defines `MAJOR` as "incompatible API changes or major architectural
changes". Three independent incompatibilities are present, and any one of them carries the
bump on its own: five subcommands removed with no aliases; two build targets withdrawn,
leaving a class of hardware unable to upgrade; and published error strings changed across
many lines, in a project that treats them as contract and pins them against the binary.

**What did not change, and why it does not soften that.** No exit code moved anywhere. No
flag was removed. The JSON success shapes are unchanged except for two additive, mutually
exclusive members — `plan` and `profile` — which appear only for a statement written with
an `EXPLAIN` or `PROFILE` prefix, and those prefixes only became parseable in this same
release window, so no consumer can have depended on their earlier output. `EXPLAIN CREATE`
changing envelope from `{"ok": true}` to the columns shape is a **fix** to a false report
rather than a break, for the same reason. And batch commands now *accept* a repeated id
where they used to fail, which is a bug fix and not an incompatibility.

These are reasons the release is not *more* disruptive than it is. None of them is a reason
to call it `MINOR`.

**On the project's precedent.** `1.15.0` shipped breaking changes as a `MINOR` and `1.15.2`
shipped them as a `PATCH`, each by an owner decision recorded at the time, with the strict
reading stated and overruled in writing. This release overrules nothing: the number is what
SemVer 2.0.0 says it should be, and this section records the reasoning rather than an
exception to it.

## Known Issues

These were measured during this cycle and are **open**. They are listed so that nothing
above is read as a promise the product does not keep.

**Every entry below was re-measured against the released binary immediately before the
tag.** Nothing here is inherited. That discipline mattered this cycle: of the six issues
this release window had accumulated, **three did not survive re-measurement** — one was
narrowed to a precondition that a first re-measurement had missed, and two are withdrawn.
None was quietly dropped.

### Open

- **One statement can drive the process to gigabytes of resident memory.** Every mutation
  a statement has applied is retained until its rollback finishes, across four
  accumulators — the write-ahead-log operation buffer (39%), the applied graph state
  (38%), the undo log (20%), and an index buffer — and nothing bounds how many mutations
  it applies before the time budget cuts it.

  Re-measured for this release under a 4 GB cgroup limit against a ~100 KB / 2,048-node
  store:

  | Statement | Peak RSS | Wall clock | Outcome |
  |-----------|----------|------------|---------|
  | `MATCH (a),(b),(c) CREATE ()` | **2.6 GB** | **~25 s** | exit 1, budget exceeded, nothing written |
  | `MATCH (a),(b),(c) RETURN count(*)` | **~30 MB** | ~5.1 s | exit 1, budget exceeded |

  An earlier run in this same cycle measured 3.3 GB. **Neither figure is a maximum.** The
  cost tracks the statement and the hardware rather than the size of the graph, which is
  flat across stores from 40 KB to 248 KB. There *is* a ceiling: given a budget long
  enough, the engine's own row cap cuts the statement at roughly **20 GB**.

  Note the two rows are different defects rather than one seen twice. The read is cut at
  its 5-second budget and returns promptly on 30 MB; the write costs eighty times the
  memory and takes five times the budget to exit, and that excess is the undo replay.

  The store on disk was byte-identical after every run, including kills delivered
  mid-replay: **this is an availability defect, not a durability one.** A short-lived
  `rmp graph execute` returns the memory to the operating system by exiting;
  `rmp graph serve` and `rmp web` have no exit to return it at. The server's connection
  ceiling bounds how many such statements run at once, not what each of them costs.

- **A server's shutdown is not bounded.** A statement the budget cut while it was writing
  is inside an undo replay that takes no cancellation, and the store cannot close until
  that call returns. Re-measured: `SIGTERM` to a server with one such statement in flight
  held for **16.2 s** and **27.3 s** across two trials; an earlier run this cycle measured
  35.6 s. **These are the largest observed, not a maximum**, and no ceiling has been
  established. The caller's own backstop fires first and says so — `the graph server at
  <socket> did not answer within 7.5s; the statement's outcome is unknown` — which is the
  designed behaviour rather than a second defect. The socket is removed and the store is
  intact afterwards.

  A supervisor that escalates `SIGTERM` to `SIGKILL` after a short grace period may kill
  the server mid-replay. Every acknowledged commit is still durable and the next open
  replays the log, but the shutdown checkpoint is lost.

- **A `SET` on a relationship bound by a `MERGE` that matched an existing relationship is
  silently discarded when the ordered node pair already carries a parallel relationship.**
  This is what survives of a broader hazard the dependency bump otherwise closed. **All
  three conditions are required:**

  1. the relationship variable is bound by a `MERGE` clause in the same statement;
  2. that `MERGE` **matched** rather than created;
  3. the same ordered pair `(source, target)` already carries another relationship **in
     the same direction**.

  When all three hold, the statement exits 0, reports `{"ok": true}`, and writes nothing;
  a following read shows the previous value. Measured:

  | Arrangement | `MERGE`-matched `SET` |
  |-------------|----------------------|
  | Isolated pair, no parallel relationship | Written |
  | Parallel relationship in the **same** direction | **Silently not written** |
  | Parallel relationship in the **reverse** direction | Written |
  | Plain `MATCH … SET`, parallel relationship present | Written |
  | `CREATE`-bound `SET`, parallel relationship present | Written |

  Both the map form (`SET e = {…}`) and the scalar form (`SET e.c = …`) lose the write.
  The defect is keyed on the **ordered pair**, which is why the reverse-direction parallel
  relationship does not trigger it, and it needs the `MERGE` binding, which is why a plain
  `MATCH` is safe.

  **The remedy:** bind with `MATCH` rather than `MERGE` when you intend to update a
  relationship that already exists, or set the properties in a second statement after a
  fresh `MATCH`.

- **An undirected or incoming `SET` on a relationship does not write every relationship it
  matched, and how much it loses depends on the data.** A write persists only where the
  row's left-hand node is the relationship's stored source and its right-hand node the
  stored target. Re-measured on a single stored `(alice)-[:MENTORS]->(bob)`:

  | Statement | Result |
  |-----------|--------|
  | `MATCH (a {k:'alice'})-[e:MENTORS]-(b {k:'bob'}) SET e.level = 'X'` | Written |
  | `MATCH (b {k:'bob'})-[e:MENTORS]-(a {k:'alice'}) SET e.level = 'X'` | **Silently not written.** Exit 0, `{"ok": true}`, property unchanged |
  | `MATCH (x)-[e:MENTORS]-(y) SET e.level = 'X'` (unanchored sweep) | Written. `count(e)` returns **2** for one stored edge |
  | `MATCH (b {k:'bob'})-[e:MENTORS]-(a {k:'alice'}) DELETE e` | Deleted correctly |

  **The selective statement is the hazardous one and the sweeping one is safe**, which
  inverts a careful reader's intuition: an unanchored sweep emits each relationship twice
  and one of the two rows is always correctly oriented. Nothing in the output
  distinguishes a complete write from a partial one, so the same statement may write all
  of what it matched, some of it, or none, according to the data.

  **The remedy:** write through an *outgoing* pattern, which can be anchored on either
  endpoint. `DELETE` is unaffected — the engine knows this defect and fixed it there, with
  a helper that `SET` and `REMOVE` never received.

- **The lint gate can silently run at the wrong version on a host with a shadowing
  install.** `make lint` runs whatever `golangci-lint` `PATH` resolves, and on the release
  host `/snap/bin` precedes `~/go/bin`, so a plain `make check` runs v2.13.2 where
  `SPEC/BUILD.md` pins v2.13.1 — and reports 0 issues either way, so nothing signals the
  substitution. The gate for this release was run with the pinned binary first on `PATH`
  and the resolved version confirmed inside it. `which -a golangci-lint` is the check;
  `golangci-lint --version` alone answers for whichever binary `PATH` resolved and proves
  nothing.

### Withdrawn after re-measurement

- **`SET` on a relationship bound by `CREATE` — CLOSED; the `MERGE`-matched case is
  NARROWED, not closed.** The broad hazard was published earlier in this same window,
  measured at GoGraph v0.12.0. The move to **v0.14.0** closed most of it. Proven by
  building the commit immediately before the dependency bump and the released tree and
  running the same eight statement shapes against both, each on its own fresh node pair:
  **all eight lose the write before the bump; all eight persist after it** — `CREATE` with
  a scalar `SET`, with `SET e = {…}`, with `SET e += {…}`, through a `WITH`, inside a
  `FOREACH`, `MERGE` creating a new relationship, `MERGE` matching one that already
  existed, and both hops of a multi-hop `MERGE`. That closure is recorded under
  [Fixed](#fixed).

  **A first re-measurement reported the `MERGE`-matched case as still open and a second
  reported it as closed; both were testing something the other was not.** The difference
  is a precondition neither had controlled for — whether the ordered node pair already
  carried a parallel relationship — and it is now published as its own open issue above.
  It is recorded here because the discrepancy is the useful part: a hazard measured on
  fresh fixtures and a hazard measured on reused ones gave opposite answers, and only
  isolating the third variable reconciled them.

  **`SPEC/GRAPH.md § What Groadmap Does Not Check` item 8 still publishes the hazard in
  its original, broader form and is inaccurate as shipped.** Correcting a specification
  file belongs to the `specification-manager`, so it is left open deliberately rather than
  edited during the release. `DOCS/commands/graph.md` and this document carry the
  corrected scope.

- **The `SPEC/DATA_FORMATS.md § Graph Client Result` contradiction — GONE.** It was
  published as requiring both byte-identical client output and a millisecond-precision UTC
  rendering for temporal values, which `rmp graph execute` has never produced. The file as
  released states neither: the byte-identity rule excludes `timeNs` and nothing else, and
  the temporal rule renders each of the six kinds in the ISO 8601 form of **its own type**
  rather than as an instant in UTC. Verified against the binary as well as the text — the
  same temporal statement through `graph execute` and `graph client` produces
  byte-identical output, for example `2026-03-05T12:23:47.12Z` for a date-and-time and
  `14:23:47+02:00` for a time keeping its own offset.

- **Retry-ladder exhaustion on a hot node — NOT REPRODUCED.** Published as "about 1% of
  writers to a single hot node exhaust the client's retry ladder", on a sample of **2
  failures in 200**. Re-measured at 16 concurrent `rmp graph client` writers to one node
  over 100 rounds — **1,600 invocations, 0 failures** — with the final counter matching the
  number of successful writes exactly, so no update was lost either. Under a stable 1%
  rate, zero failures in 1,600 trials has probability of order 10⁻⁷.

  **This is reported as not reproduced rather than as fixed.** The original harness is not
  available, and a tighter connection barrier producing truer simultaneity than 16
  independently launched processes might still trigger it. The remedy, if it is met, is
  unchanged and is published: spread concurrent writes across distinct nodes. Measured
  earlier in this cycle, the same 16 writers over 8 or more nodes gave zero failures in
  6,000 while throughput rose from 474 to 3,494 ops/s.

### Recorded elsewhere and not repeated here

Two error-classification residuals are recorded on `rmp` task #418 rather than as product
defects: the symlink refusal in `internal/utils/path.go` deliberately keeps
`database error:`, because the `lstat` succeeded and what follows is Groadmap's own
security decision rather than a failed operation; and the data-directory read line
discards the operating-system cause it was given.
