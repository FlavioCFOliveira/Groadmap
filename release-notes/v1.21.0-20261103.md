# Release Notes — Groadmap v1.21.0

**Date:** 2026-11-03
**Type:** Minor — one new stderr diagnostic record in `rmp graph serve`, with a compatibility note on the order of stderr when a start fails late (see [Why This Is Released as `1.21.0`](#why-this-is-released-as-1210))
**Tag:** `v1.21.0`
**Previous release:** `v1.20.0` (2026-10-28)

---

## Executive Summary

Groadmap `v1.21.0` makes `rmp graph serve` report, on every start, the Go runtime
`GOMAXPROCS` setting that governs every parallel worker count of the graph engine,
and where that setting came from. The server does not change the setting: the Go
runtime's default stays in force, or the operator's `GOMAXPROCS` environment value
when one is set.

The new record is written to stderr before the listener is bound. On a start that
fails at or after the bind, it therefore precedes the `Error:` line, which is no
longer the first line of stderr (see [Compatibility](#compatibility)).

The SQLite schema does not change: databases stay at schema `1.17.0`. `go.mod` and
`go.sum` are unchanged, and the graph engine stays at GoGraph `v0.17.2`. The AI
Agent Contract that `rmp --ai-help` emits is identical to that of `v1.20.0` apart
from `tool.binary_version`.

## New Features

### The processor-parallelism record of `rmp graph serve`

(`5ab6696`, `f487e36`, rmp tasks #645 and #647; `SPEC/GRAPH.md § Processor
Parallelism`, `SPEC/COMMANDS.md § Serve Output`)

Every parallel worker count the graph engine derives — the parallel scan, the index
backfill, the label count and the bulk load among them — is read from the Go
runtime's `GOMAXPROCS` setting when the work starts. That setting is therefore the
single lever over how many processors the engine's work may occupy at once, and the
server now states it on every start, in one `INFO` record on stderr:

```text
time=<UTC timestamp> level=INFO msg="processor parallelism" source=derived gomaxprocs=<n> cpus=<n>
```

| Attribute | Value |
|---|---|
| `source` | `derived` when the `GOMAXPROCS` environment variable is absent or empty; `environment` when it is set |
| `gomaxprocs` | The setting in force at startup; equal to `cpus` when `source` is `derived` |
| `cpus` | The usable CPU count; present only when `source` is `derived` |

**What the server does with the setting.** Nothing: it reads it and never sets it.

- **Without the environment variable**, the Go runtime's default stays in force. It
  is the usable CPU count, which the runtime derives from the machine's logical
  CPUs, the process's CPU affinity mask and, on Linux, the cgroup CPU quota. No
  host-specific value is fixed anywhere. Because the server never sets the value,
  the runtime keeps updating it while the server serves when the affinity mask or
  the cgroup quota changes.
- **With the environment variable**, the operator's value is left unchanged for the
  life of the process, and the record carries no `cpus` attribute, because the
  runtime's default is not observable without changing the setting.

The record states the value in force at startup only; no further record is written
when the runtime updates it.

**What does not change.** The parallel-scan threshold stays at the engine's
default, no memory budget or soft memory limit is set, and the connection and
transaction quotas are unchanged.

**A doubling that was never released.** `5ab6696` first set `GOMAXPROCS` to twice
the usable CPUs. `f487e36` withdrew it on the same sprint, because the measurement
recorded in rmp task #646 (an 8-core, 16-thread host, 21 latency and concurrency
cells) found no significant difference between the CPU count and twice the CPU
count, with a geometric-mean delta of `-0.72%`. That measurement is quoted from the
commit message of `f487e36`; it was not repeated for these notes. No released binary
has set `GOMAXPROCS`.

Tests: `TestProcessorParallelism_Derivation`,
`TestSettleProcessorParallelism_LeavesTheSettingAndRecords`,
`TestServe_DerivesProcessorParallelismBeforeTheAnnouncement`,
`TestServe_LeavesAnEnvironmentParallelismUnchanged` and
`TestServe_ARefusedStartWritesNoParallelismRecord`, in
`internal/graphserve/parallelism_test.go`.

## Compatibility

The new record changes what `rmp graph serve` writes to stderr. Stdout is unchanged
in every case.

### A start that fails at or after the bind

(`5ab6696`, `c91e305`, #648; `SPEC/GRAPH.md § Server Startup`, step 5, and
`§ Processor Parallelism`, rule 4)

The record is queued before the listener is bound. A start that then fails — at the
bind itself, at the pre-migration backup, at the store open or at the engine
construction — empties the queue before it writes its error line, so the `Error:`
line is **no longer the first line of stderr**:

| `AI_AGENT` | Order of stderr |
|---|---|
| not `1` | the `processor parallelism` record, the `Error:` line, a blank line, the AI-agent hint, a blank line |
| `1` | the AI-agent hint, a blank line, the `processor parallelism` record, the `Error:` line |

Stdout stays empty, and the exit code and the text of the `Error:` line are
unchanged. A failure at the bind, the backup or the store open writes neither of
the two startup warnings, because the engine emits them only while the server is
being constructed.

A start refused before the bind — at Server Startup steps 1 to 4, a socket path
that is too long among them — writes no record, so its stderr is exactly that of
`v1.20.0`.

**Action for scripts and supervisors:** a script that reads the error of
`rmp graph serve` with `head -1` must select it with `grep '^Error:'` instead. That
is already the documented way to read any `rmp` error, because the AI-agent hint
can precede it.

### A start that succeeds

The record is the first of the startup records, ahead of the two startup warnings
(no authentication, no TLS), and all three reach stderr before the socket object
reaches stdout. A healthy server that serves a write and stops on `SIGINT` writes
those three records and nothing further.

## Internal Changes

These change no output of the binary.

- **The E2E suite expects the record** (`5ab6696`, `c91e305`).
  `tests/base_test.py` gains `split_serve_failure_stderr`, which validates the
  single leading record — its attributes, its UTC timestamp and its position
  relative to the AI-agent hint — and returns the stderr after it.
  `tests/test_65_graph_server_client_e2e.py` asserts the record and then the
  `Error:` line on a failed bind, with empty stdout.
  `tests/test_55_error_string_parity.py` accepts the record ahead of the bind and
  backup failure lines only. `tests/test_69_graph_field_length.py` expects it as
  the first of a healthy server's three startup records.
- **Specification.** `SPEC/GRAPH.md` gains `§ Processor Parallelism` and updates
  `§ Server Startup`, step 5, `§ Server Diagnostics on Stderr` and acceptance
  criterion 71; `SPEC/COMMANDS.md § Serve Output` describes the record and the
  ordering above.
- **The release cut aligns both shipped skills with `1.21.0`**, and the
  `knowledge-authority` skill records that `1.21.0`, like `1.19.0` and `1.20.0`, is
  built against GoGraph `v0.17.2`.

## Known Issues

The list was rebuilt for this release. No code outside `internal/graphserve/`
changed since `v1.20.0`, and `go.mod` and `go.sum` are unchanged, so each item of
the `v1.20.0` list still holds; each was re-checked by the means stated.

- **Node `id()` values jump across a restart of `rmp graph serve`, and are not
  dense** (#634; `SPEC/GRAPH.md`). Identity is the `key` property, never `id()`.
  Not re-measured for this release: the engine and the store close path are
  unchanged since `v1.20.0`, which measured it.
- **While a write cut by the statement budget rolls back, an unlabelled read can
  observe uncommitted state** (#633). Reads anchored on a label or filtered on a
  property value stay correct, and the exposure ends with the rollback. Verified in
  `SPEC/GRAPH.md § Concurrency and Recovery`; not re-measured for this release.
- **A write of a `UNIQUE` value that a concurrent transaction is freeing can be
  refused** with `Neo.ClientError.Schema.ConstraintValidationFailed`, and the
  shipped clients do not retry it (#638); the same write run again succeeds.
  Verified in `SPEC/GRAPH.md`; not reproduced for this release.
- **`rmp audit list --help` still says `TASK_STATUS_BACKLOG` carries `null` "from
  'task stat'"**, which `task stat` cannot produce since `v1.18.0`. Verified by running the
  `1.21.0` help.
- **`rmp backlog --help` and `rmp backlog list --help` still say no 0-9 validation
  is enforced on `--priority`**; the binary refuses `rmp backlog list -p 12` with
  exit `6` and `Error: validation error: priority must be between 0 and 9, got 12`.
  Verified by running the `1.21.0` helps and the command.
- **`1.21.0` does not re-check sprint membership when it opens a database already at
  schema `1.17.0`**, as `v1.20.0` did not. Verified in the code: `internal/db/` is
  unchanged since `v1.20.0`.
- **`modernc.org/libc` is a later release than `modernc.org/sqlite` requires**
  (`v1.79.1` against the `v1.79.0` that `modernc.org/sqlite v1.61.0` declares). The
  project accepts the risk deliberately (`SPEC/BUILD.md § SQLite Driver Rules`).
  Verified by `go.mod` and `go.sum` being unchanged since `v1.20.0`.
- **The web query bar's `EXPLAIN`/`PROFILE` prefix check runs outside the 5-second
  budget**, because the engine's parser takes no context (`internal/web/data.go`,
  `refusePlanPrefix`). `internal/web/` is unchanged since `v1.20.0`; not
  re-measured for this release.

## Upgrade Notes

### Step 1 — Install and verify the binary

```bash
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install.sh | bash
rmp --version
# Groadmap version 1.21.0 (commit <commit>)
```

The roadmap database and the graph store need no action: neither format changes.

### Step 2 — Update the agent skills

```bash
rmp skills install
```

Both skills now declare `rmp-version` `1.21.0`.

### Step 3 — Check how you read the stderr of `rmp graph serve`

A supervisor or script that takes the first line of `rmp graph serve`'s stderr as
the error must select the `Error:` line instead (see
[Compatibility](#compatibility)). A log pipeline that collects the server's stderr
receives one more `INFO` record per start.

### Downgrading

A `v1.20.0` binary reads the database and serves the graph store that `1.21.0`
uses, because neither format changes. Downgrading removes the
`processor parallelism` record and nothing else.

## Why This Is Released as `1.21.0`

A strict reading of Semantic Versioning 2.0.0 gives `MINOR`, which matches the
owner's decision for this release.

- **The release adds backward-compatible functionality**: one diagnostic record on
  stderr. The project's output contract puts machine-readable output on stdout,
  which is unchanged, and the AI Agent Contract is identical apart from
  `tool.binary_version` (measured: see [Test Evidence](#test-evidence)).
- **The reordering of stderr on a late failure is a compatibility note, not a
  breaking change.** The exit codes and the text of every `Error:` line are
  unchanged, and reading the first stderr line was never a reliable way to find
  the error, because the AI-agent hint already precedes it under `AI_AGENT=1`.
