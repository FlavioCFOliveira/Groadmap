# Release Notes — Groadmap v1.15.0

**Date:** 2026-08-21
**Type:** Minor by decision — **contains two backward-incompatible changes** (see Breaking Changes)
**Tag:** `v1.15.0`
**Previous release:** `v1.14.0` (2026-08-17)

---

## Executive Summary

Groadmap `v1.15.0` is the release in which a task stops being a status and starts
being a **record**. Three sprints — 81 completed tasks across 87 commits — land
together, and they all push in the same direction: making the roadmap able to
answer *what happened*, not merely *where things stand*.

**Comments** arrive: a typed, timestamped log attached to a task or a sprint.
Groadmap recorded what work was planned and what state it was in, but nothing of
what was learned while doing it. Eight new subcommands, four in each family, give a
task or a sprint the ability to answer — months later, and to someone who was not
there — what was tried, what was found, and why it went the way it did.

**Commit tracking** arrives with them, and it is mandatory. Entering `DOING` now
requires `--commit-open` and reaching `COMPLETED` requires `--commit-close`, so
every task points at the region of code history that produced it. Both invocations
previously succeeded with no flag; both now exit **6**.

**The audit log stops being generic.** One `TASK_STATUS_CHANGE` becomes five
destination-named operations. One `TASK_UPDATE` becomes one entry per changed
field. `SPRINT_MOVE_TASK` becomes a directional pair. Relational operations name
**both** entities instead of one, closing a defect in which adding three tasks to a
sprint wrote three rows that recorded which sprint but never which tasks. Every
entry gains two keys, `related_entity_id` and `commit_hash`. The operation
catalogue grows from **23 to 43**, four of them retained as a documented `LEGACY`
group so existing queries still reach the rows already stored.

**The task `specialists` field is removed entirely**, taking `task assign`,
`task unassign`, the `-sp` flag on three subcommands, the stored column, the web
presentation, and two audit operations with it. Nothing replaces it, and the stored
values are dropped by the migration and are not recoverable afterwards.

**The read-only web interface is rebuilt** around how work is actually read. The
roadmap tasks page becomes a Kanban board with a header search and three filters;
the sprint page's member-task table becomes a three-column board whose counts
cannot disagree with the summary line above it; the task detail modal is filled on
demand from a JSON endpoint; the graph data endpoint gains a 5-second per-request
time budget. And the server's absorbed errors — previously **discarded**, leaving an
operator with a silent terminal — are now written to the console through `log/slog`.

A security pass occasioned by the comment surface closed a **guard-rail bypass** by
which a non-ASCII homoglyph smuggled schema DDL past a rail that classifies
read-only queries, on an interface documented as read-only.

The database schema advances **four migrations in one release, `1.8.0` → `1.12.0`**.
They run automatically and in order, they are forward-only, and one of them deletes
data. Read [Upgrade Notes](#upgrade-notes) before running a `1.15.0` binary against
a roadmap you care about.

## Highlights

- **Comments on tasks and sprints.** Eight subcommands, a per-entity type enum, a
  body from `--body` or standard input, and a read-only timeline on the web
  interface. Strictly additive: no existing contract, exit code, or transition
  changes on their account.
- **BREAKING — `task stat DOING` and `task stat COMPLETED` now require a commit
  hash.** Every script, agent, and CI step that drives those transitions must be
  updated. There is no opt-out.
- **BREAKING — the task `specialists` field is gone**, along with `task assign`,
  `task unassign`, and the `-sp/--specialists` flag. The stored values are deleted
  by the migration.
- **The audit log now says what happened.** 43 operations, up from 23. Five
  destination-named status operations, nine per-field edit operations, a
  directional move pair, both entities named on every relational operation, and the
  bracketing commit on the two operations that can carry one.
- **Historical audit entries are reclassified in place**, by exact timestamp
  equality and nothing else. Nothing is deleted, renumbered, or compacted.
- **A Kanban tasks board, a three-column sprint board, header search and three
  filters** on the read-only web interface — which stays read-only throughout:
  `GET` and `HEAD` only, no control that moves a task, no new write path.
- **`rmp web` finally speaks.** Structured `log/slog` records on stderr for every
  failure the server absorbs, with UTC timestamps and no access-log noise.
- **A guard-rail bypass closed**, plus a limit bypass, an unbounded standard-input
  read, and a `0600` guarantee that was applied only at file creation.
- **Four schema migrations, `1.8.0` → `1.12.0`, forward-only.** One of them drops a
  column. Back up first; see [Upgrade Notes](#upgrade-notes).

## Breaking Changes

**Two changes in this release will break existing callers.** Both fail loudly and
immediately — non-zero exit, nothing changed — rather than silently altering a
result. Neither has an opt-out, an environment variable, or a compatibility flag.

### 1. `task stat DOING` and `task stat COMPLETED` require a commit hash

`rmp task stat <ids> DOING` now requires `--commit-open` (short `-co`), and
`rmp task stat <ids> COMPLETED` now requires `--commit-close` (short `-cc`).

| Invocation | On `1.14.0` | On `1.15.0` |
|------------|-------------|-------------|
| `rmp task stat -r p 42 DOING` | Exit 0, task moved | **Exit 6**, nothing changed |
| `rmp task stat -r p 42 COMPLETED` | Exit 0, task closed | **Exit 6**, nothing changed |
| `rmp task stat -r p 42 COMPLETED --summary "..."` | Exit 0 | **Exit 6**, nothing changed |

The exact messages, verified against the shipped binary:

```
Error: --commit-open is required when transitioning to DOING
Error: --commit-close is required when transitioning to COMPLETED
```

**What you must write instead:**

```bash
rmp task stat -r myproject 42 DOING --commit-open $(git rev-parse HEAD)
rmp task stat -r myproject 42 COMPLETED --commit-close $(git rev-parse HEAD) --summary "Shipped"
```

**Every route into those two states is affected**, including the re-entry into
`DOING` from `TESTING` after testing sent the work back. On a re-entry the supplied
hash **replaces** the stored one; no history of earlier values is kept.

**Each flag is rejected on any other target state** (exit 6), mirroring the rule
that already governs `--summary`:

```
Error: --commit-open flag is only allowed when transitioning to DOING
Error: --commit-close flag is only allowed when transitioning to COMPLETED
```

**Nothing partial can happen.** The commit flags are validated at step 4 of the
`stat` validation order — before ID resolution, before the state-machine check, and
before any write — so a batch in which any check fails leaves **every** task in the
batch untouched.

**One hash applies to the whole batch.** Every task named in a comma-separated
`<task-ids>` receives the same value, exactly as every task receives the same
`--summary`. A caller who needs different hashes issues separate commands.

**Format.** 7 to 64 hexadecimal characters, stored lowercase, enforced by a `CHECK`
constraint as well as by the application. `5F93B51` and `5f93b51` are the same
value; the stored form is always the lowercase one. Groadmap **derives nothing**: it
invokes no git command, reads no working directory, inspects no repository, and does
not check that the hash names a commit that exists anywhere.

**Neither field is editable.** `task create` accepts neither flag, because a task is
created in `BACKLOG`, and `task edit` cannot change either value. A wrong hash is
corrected by performing the transition again where the state machine allows it.

### 2. The task `specialists` field is removed

The field recorded which specialists a task was assigned to. It is removed from the
model, from storage, from the command surface, from the web interface, and from the
audit catalogue. **Nothing replaces it.**

| Invocation | Result on `1.15.0` |
|------------|--------------------|
| `rmp task assign <ids> <specialists>` | **Exit 2** — unknown subcommand |
| `rmp task unassign <ids> <specialists>` | **Exit 2** — unknown subcommand |
| `rmp task create ... -sp/--specialists <v>` | **Exit 2** — unknown flag |
| `rmp task edit <id> -sp/--specialists <v>` | **Exit 2** — unknown flag |
| `rmp task list -sp/--specialists <v>` | **Exit 2** — unknown flag |

**The `Task` JSON object no longer carries a `specialists` key**, on any command
that returns a task (`list`, `get`, `next`, `subtasks`, `blockers`, `blocking`) and
on the web interface's task detail modal. A consumer that reads
`task["specialists"]` must stop doing so; a consumer that reads it defensively sees
the key simply absent.

**The stored values are deleted and are not recoverable.** Migration
`1.9.0 → 1.10.0` drops the `tasks.specialists` column. See
[Upgrade Notes](#upgrade-notes) for how to export them first.

**Two audit operations are removed.** `TASK_ASSIGN` and `TASK_UNASSIGN` are no
longer in `ValidAuditOperations` and are no longer accepted by
`rmp audit list --operation`. Historical rows carrying those values are **not**
deleted — the migration touches no audit row — but they can no longer be selected by
operation.

## Upgrade Notes

### Step 1 — Export `specialists`, if you need it

Migration `1.9.0 → 1.10.0` drops the column. Run this **before** any `1.15.0`
command touches the roadmap:

```bash
sqlite3 ~/.roadmaps/<name>/project.db \
  "SELECT id, title, specialists FROM tasks WHERE specialists IS NOT NULL;" \
  > specialists-backup.txt
```

### Step 2 — Back up the roadmap; the migrations are forward-only

```bash
cp -a ~/.roadmaps/<name> ~/.roadmaps/<name>.pre-v1.15.0
```

There is **no downgrade path**. A `1.14.0` binary opening a roadmap migrated to
schema `1.12.0` will not read it.

### Step 3 — The migration path: `1.8.0` → `1.12.0`

Four migrations run automatically, in order, on the first command executed against
an existing roadmap. There is nothing to invoke and no flag to pass.

| Migration | What it does | Deletes data? |
|-----------|--------------|---------------|
| `1.8.0` → `1.9.0` | Adds `task_comments` and `sprint_comments`, plus one index each on `(parent_id, created_at ASC)` | No |
| `1.9.0` → `1.10.0` | **Drops** `tasks.specialists`. No table rebuild — the column is plain nullable `TEXT`, not indexed, in no `CHECK`, no foreign key, no view, and no trigger | **Yes** — the column's values |
| `1.10.0` → `1.11.0` | Adds `tasks.commit_open` and `tasks.commit_close`, each nullable `TEXT` with its own `CHECK` (`NULL`, or 7 to 64 lowercase hexadecimal characters). No backfill, no index | No |
| `1.11.0` → `1.12.0` | Adds `audit.related_entity_id` and `audit.commit_hash`, then reclassifies historical `TASK_STATUS_CHANGE` rows onto the five destination-named operations | No |

`ADD COLUMN` can only append, so a migrated table lists the new columns in a
different physical order from a freshly created one. The DDL text differs; the
behaviour does not, and a test asserts identical accept/reject answers across an
eleven-case matrix on both databases.

### Step 4 — Update your automation

Any script, agent, or CI step that drives `task stat ... DOING` or
`task stat ... COMPLETED` must pass a commit hash. Any consumer reading
`task["specialists"]` must stop. Any consumer reading audit entries should expect
**seven** keys rather than five, and should expect the destination-named and
per-field operation values rather than the generic ones.

### Step 5 — Install and verify

```bash
git checkout v1.15.0
go build -o ./bin/rmp ./cmd/rmp

./bin/rmp --version
# Groadmap version 1.15.0
```

## Why This Is Released as `1.15.0`

Under a strict reading of Semantic Versioning 2.0.0, a change that makes a
previously successful invocation fail is a `MAJOR` change, and this release
contains two of them. The version number is nevertheless `1.15.0`, by the project
owner's explicit decision. The reasoning recorded here so that it can be reviewed
rather than inferred:

- The affected surface is the **roadmap-authoring CLI**, not a library API that
  other code links against. There is no compilation to break and no dependency
  resolver to mislead.
- Both incompatibilities **fail loudly and immediately** — exit 2 for the removed
  surface, exit 6 for the missing commit flags — and neither silently changes a
  result, corrupts data, or produces a wrong answer that a caller might act on.
- The remediation for each is mechanical and local: add a flag, or delete a call.

**This does not soften the incompatibility.** If you drive `rmp` from automation,
treat this release as a breaking one and read
[Breaking Changes](#breaking-changes) in full before upgrading.

Everything else in the release is backward-compatible new functionality: the eight
comment subcommands, the two new task fields, the two new audit columns, the
enriched operation catalogue (whose four superseded values remain readable), the web
interface rebuild, and the `rmp web` console log. No other exit code changes
meaning, and no other JSON key is removed or renamed.

## Changes by Category

### Added — Comments on Tasks and Sprints

Groadmap recorded what work was planned and what state it was in, but nothing of
what was learned while doing it. A comment is a typed, timestamped log entry
attached to a task or a sprint; a task or sprint holds as many as the work needs,
and the log is read oldest first, because the order is the story it tells.

Eight subcommands, four in each family, in the flat form `<family> comment-<verb>`.
There is no separate `rmp comment` family and no three-level
`rmp task comment add` form.

| Subcommand | Alias | Takes | Purpose |
|------------|-------|-------|---------|
| `task comment-add` / `sprint comment-add` | `c-add` | the TASK's or SPRINT's id | Add one typed comment |
| `task comment-list` / `sprint comment-list` | `c-ls` | the TASK's or SPRINT's id | List the log, oldest first, optionally filtered by `--type` |
| `task comment-edit` / `sprint comment-edit` | `c-edit` | the COMMENT's own id | Change the type and/or the body |
| `task comment-remove` / `sprint comment-remove` | `c-rm` | the COMMENT's own id | Delete one comment, irreversibly |

```bash
rmp task comment-add -r myproject 42 --type FINDING \
  --body "The parser accepts the boundary second exactly; no rounding occurs."

rmp task comment-add -r myproject 42 --type DECISION < decision.txt

rmp task comment-list -r myproject 42                  # the whole log, oldest first
rmp task comment-list -r myproject 42 --type DECISION  # filtered

rmp task comment-edit   -r myproject 12 --type NOTE    # takes the COMMENT's id
rmp task comment-remove -r myproject 12
```

**A per-entity type, mandatory and without a default.** A task comment accepts
`FINDING`, `HYPOTHESIS`, `TEST`, `DECISION`, `PROGRESS`, `UPDATE`, and `NOTE`; a
sprint comment accepts only `FINDING`, `DECISION`, `PROGRESS`, and `UPDATE`. The
asymmetry is deliberate — a sprint records how the sprint went, not the execution
diary of its individual tasks — so the three task-only values are rejected on a
sprint with exit code 6 and a message naming the valid set:

```
Error: validation error: invalid comment type "NOTE" for a sprint comment; valid types: FINDING, DECISION, PROGRESS, UPDATE
```

The database enforces the same two subsets independently, through a `CHECK`
constraint on each comment table.

`-y, --type` therefore carries two unrelated enums in the `task` family: a task type
on `list`, `create`, and `edit`, and a comment type on the comment subcommands. A
value from one set is rejected by the other. Each family's help lists only its own
set, and the AI Agent Contract exposes them as two separate enum keys,
`TaskCommentType` and `SprintCommentType`.

**A body from standard input.** The body comes from `--body` or, when that flag is
absent, from standard input — the same mechanism the `graph` subcommands already use
for `--query`, so a multi-line finding can be piped or redirected in without shell
quoting. There is no `--body-file` flag and no path argument; the commands open no
file. On `comment-edit` standard input is read only when `--type` is absent too, so
a type-only edit never blocks waiting for input. `--type` is validated before the
body is resolved, so a missing or invalid type fails immediately rather than leaving
the command waiting on input it would reject anyway.

The read is **bounded**: it stops the moment the body cannot fit, so an oversized
body is refused without ever being buffered. Bodies are trimmed at the edges,
preserve interior line breaks, are capped at 4096 characters, and reject control
characters like every other free-text field.

**Comment ids are per-family.** The two tables are independent, so
`rmp task comment-edit 7` and `rmp sprint comment-edit 7` address two unrelated
comments, and an id that exists only in the other family is a not-found condition
(exit code 4).

**An edit is a replacement.** `comment-edit` replaces the stored body in place and
stamps `updated_at`; the previous text is not retained anywhere and cannot be
recovered. The audit log records that an edit happened, not what it replaced.

**Comments are strictly additive.** They are accepted in every task and sprint
status, including `COMPLETED` and `CLOSED`; no comment subcommand checks or changes
an entity's status, no comment ever gates a transition, and `task reopen` does not
touch comments. The `Task` and `Sprint` JSON objects carry no `comments` array and
no comment count: comments are read only through `comment-list` and the web
interface.

### Added — Commit Tracking on the Task Entity

Two nullable fields, `commit_open` and `commit_close`, recording the commit the work
started from and the commit it was concluded at. Both are returned on every `Task`
JSON object, `null` until the task reaches `DOING` and `COMPLETED` respectively, and
both are shown on the web interface's task detail modal.

The write path is the mandatory flag pair described in
[Breaking Changes](#breaking-changes). It is the **only** way either value is ever
written.

**`commit_open` survives a return to `BACKLOG`; `commit_close` does not.** All four
routes back — `task stat <ids> BACKLOG`, `task reopen`, `sprint remove-tasks`, and
`sprint remove` — clear `commit_close` and leave `commit_open` untouched. The
asymmetry is deliberate and differs from the lifecycle timestamps, which are all
cleared: reopening invalidates where the work **ended**, not where it began.

Verified live on this tag:

```
after reopen: commit_open = 5f93b51 | commit_close = None | closed_at = None
```

The historical audit entry keeps its hash across the same reopening, proving the log
immutable where the task's own columns are not.

### Changed — The Audit Log Now Says What Happened

The audit log recorded that something changed but rarely what. This release replaces
the generic operations with specific ones, at two levels, and adds the two columns
that make a relational or bracketed operation self-describing.

**Five destination-named status operations.** `TASK_STATUS_BACKLOG`,
`TASK_STATUS_SPRINT`, `TASK_STATUS_DOING`, `TASK_STATUS_TESTING`, and
`TASK_STATUS_COMPLETED` replace the single `TASK_STATUS_CHANGE`, whose destination
was recoverable only by replaying the whole history.

**Nine per-field edit operations.** `TASK_TITLE_CHANGE`, `TASK_TYPE_CHANGE`,
`TASK_FUNCTIONAL_REQUIREMENTS_CHANGE`, `TASK_TECHNICAL_REQUIREMENTS_CHANGE`,
`TASK_ACCEPTANCE_CRITERIA_CHANGE`, `SPRINT_TITLE_CHANGE`,
`SPRINT_DESCRIPTION_CHANGE`, `SPRINT_MAX_TASKS_CHANGE`, and `SPRINT_ORDER_CHANGE`
replace `TASK_UPDATE` and `SPRINT_UPDATE`. An edit writes **one entry per field
supplied**, in the deterministic field order the `UPDATE` statement is already built
with, all sharing one `performed_at`.

A row is written per flag **supplied**, not per value that differs: supplying a
value equal to the stored one still writes its row, exactly as `task prio` already
did unconditionally. The alternative would give one operation two triggers depending
on which command produced it.

This also settles an inconsistency: `task prio <id> 5` wrote `TASK_PRIORITY_CHANGE`
while `task edit <id> -p 5`, performing the identical mutation, wrote `TASK_UPDATE`.
Both now write `TASK_PRIORITY_CHANGE`. Verified live — a single
`task edit -t "..." -p 7` writes two entries:

```
10 TASK_TITLE_CHANGE     TASK 1
 9 TASK_PRIORITY_CHANGE  TASK 1
```

**A directional move pair.** `SPRINT_MOVE_TASK_OUT` and `SPRINT_MOVE_TASK_IN` are
written against the source and the destination sprint respectively. Previously one
row was written against the destination only, so the source sprint's history had no
record of losing the tasks, and no row named a task at all.

**Both entities are named on every relational operation.** Adding three tasks to a
sprint previously wrote three rows identical in every column but `id`, all carrying
`entity_id` = the sprint. Which tasks were added was recorded nowhere, and
`audit history TASK <id>` showed nothing even though the task's status had changed
from `BACKLOG` to `SPRINT`. `sprint add-tasks` and `sprint remove-tasks` now write a
mirrored pair, and both dependency writers name the counterpart task. Verified live:

```
3 SPRINT_ADD_TASK      entity=SPRINT 1  related=1
4 TASK_STATUS_SPRINT   entity=TASK   1  related=1
```

**Two new columns, and seven keys on every entry.** `related_entity_id` names the
counterpart of a relational operation and `commit_hash` carries the bracketing
commit. Both are returned on **every** entry from `rmp audit list` and
`rmp audit history`, `null` where unused, taking the entry from five keys to seven:

```
keys: ['commit_hash', 'entity_id', 'entity_type', 'id', 'operation', 'performed_at', 'related_entity_id']
```

**The invariants are structural, not conventional.** `LogAuditTx` — the package's
only audit writer after this release — refuses a commit hash on any operation
outside `TASK_STATUS_DOING` and `TASK_STATUS_COMPLETED`, and refuses a counterpart
on any operation outside the eight relational ones. The table-wide invariant is
enforced by the writer rather than restated at each call site: the wrong call cannot
compile a row into existence.

**The catalogue grows from 23 to 43 operations**, four of them in a documented
`LEGACY` group — `TASK_STATUS_CHANGE`, `TASK_UPDATE`, `SPRINT_UPDATE`, and
`SPRINT_MOVE_TASK`. LEGACY values are published last in `ValidAuditOperations` and
remain accepted by `audit list --operation`, so a query still reaches the rows
already stored, while no code path writes them again.

### Changed — Historical Audit Entries Are Reclassified in Place

Migration `1.11.0 → 1.12.0` rewrites the `operation` value of matching historical
rows so that a roadmap's existing history gains the same specificity as its new
entries.

**Reclassification is by exact equality and nothing else.** An entry becomes
`TASK_STATUS_DOING`, `TASK_STATUS_TESTING`, or `TASK_STATUS_COMPLETED` only when its
`performed_at` equals **exactly one** of the owning task's three lifecycle
timestamps. It keeps `TASK_STATUS_CHANGE` when it matches none — a transition to
`BACKLOG` stamps no timestamp, and a reopening clears the ones that would have
matched — when it matches more than one, and when the task no longer exists.

The predicate is narrow on purpose: `operation = 'TASK_STATUS_CHANGE'` excludes
`TASK_UPDATE`, `SPRINT_UPDATE`, and `SPRINT_MOVE_TASK`, and `entity_type = 'TASK'`
keeps a sprint-scoped entry out even when its `entity_id` collides with a task id.
The three statements are mutually exclusive and order-independent.

**Nothing is lost.** The `audit` table is never rebuilt: no `DELETE`, no id rewrite,
no compaction, no new index, no backfill of the two new columns, and no audit entry
of the migration's own. Ids, `entity_type`, `entity_id`, and `performed_at` are
identical before and after.

The migration was verified against a copy of a live database: 1529 rows and ids
1–1529 unchanged, 637 of 661 candidate rows reclassified (213 / 212 / 212), 24 left
as `TASK_STATUS_CHANGE`, both new columns `NULL` throughout, the 35 `TASK_UPDATE`
rows untouched, and a second run a no-op. It was also fault-injected seven ways —
dropping each predicate, inferring `related_entity_id`, rebuilding instead of
appending, omitting the `CHECK`s, removing the `columnExists` guard — and every
injection is caught by a test.

### Added — The Read-Only Web Interface, Rebuilt

**The roadmap tasks page is a Kanban board.** `/roadmaps/{name}/tasks` presents
every task of the roadmap as a read-only board of five fixed status columns, each
header carrying a count badge. The page reads every task of the roadmap, so its
per-column counts state facts about the roadmap rather than about a page of it. Each
card is a `<button>`, reachable by pointer, touch, and keyboard, and opens the
read-only task detail modal. The board is the page's only task presentation: there
is no table view.

**Header search and three filters.** A search box in the page header plus `type`,
`priority`, and `severity` filters, carried in the URL as the `q`, `type`,
`priority`, and `severity` query parameters. On a cold load they are applied in
memory over the rows already read; narrowing in the browser issues no request at
all, because every card is already in the document. The search term is trimmed and
case-folded with the **server's** whitespace set and mapping, not the browser's, so
the same term selects the same cards on both paths.

**The task detail modal is filled on demand from a JSON endpoint**, so the page's own
read does not grow with the number of tasks rendered.

**The sprint page's member tasks are a three-column board.**

| Column | Holds | Ordered by |
|--------|-------|-----------|
| `WAITING` | `BACKLOG` or `SPRINT` | Planned in-sprint execution order (`position` ascending) |
| `DOING` | `DOING` or `TESTING` | Most recent first |
| `CLOSED` | `COMPLETED` | Most recent first |

This is the same grouping the sprint's status summary line already uses — pending,
open, completed — rather than a second categorisation invented for the board. That
is what makes the two agree by construction: the `WAITING` count is the summary
line's `P`, `DOING` is its `A`, `CLOSED` is its `C`, and the three sum to its `T`.
Each column is ordered by the question it answers: `WAITING` is a queue of work not
yet started, so the plan is what you want from it; `DOING` and `CLOSED` are records
of what has happened, so they lead with the most recent.

`WAITING` groups `BACKLOG` with `SPRINT` rather than showing `SPRINT` alone because
`rmp task stat <id> BACKLOG` returns a task to the backlog **without** removing it
from the sprint, so a `BACKLOG` sprint member is a reachable state.

**Comments are surfaced on two read-only places.** The task detail modal renders the
task's comments as a chronological timeline placed last in the modal body; the
sprint page gains a Comments card after the member-tasks card. Both show, per entry,
the type as a neutral badge, the creation timestamp, an edited marker when the
comment has been changed, and the body with the author's line breaks preserved; both
show a clear empty state. The comments of every task rendered on a page are loaded
in **one grouped query**, never one query per task.

**The interface remains read-only throughout.** `GET` and `HEAD` only. No
drag-and-drop, no control that moves a task, no new write path, no new exit code,
and no schema requirement from the web work. The CLI remains the sole write path for
comments and for everything else.

Two full-height regions — the tasks board and the knowledge-graph card — now have
their height computed by the layout instead of subtracted from the viewport. The
sprints page tabs are coloured by the status each one groups. The read-only footer is
removed from every page, the selected roadmap is named in the top navbar, and every
page header renders through one shared partial.

### Added — A Structured Console Log for `rmp web`

The web server absorbs every per-request failure into an HTTP status and keeps
serving, and its response body is deliberately opaque so no internal detail reaches
the browser. That detail was not merely withheld, it was **discarded**: every `500`
path dropped the error value and no package imported `log/slog` at all, so an
operator faced with a failing page had a silent terminal.

The console is now the counterpart of the opaque response. One package-level
`slog.Logger` over a `TextHandler` on **stderr** at level `INFO`, with a
`ReplaceAttr` hook rewriting the time attribute to UTC in the project's canonical
`YYYY-MM-DDTHH:mm:ss.sssZ` form — `TextHandler` stamps the local zone with an offset
by default, which satisfies neither the always-UTC rule nor the `Z`-suffix rule.

Each record carries the method, the path, the caller's roadmap and subject, the
status, and the error, in that order. All nine `500` paths log before answering —
the index, sprints, tasks, task detail, audit and sprint handlers, the graph view,
plus the two render helpers, which detect and answer their own failures and so log
their own subject. The graph data endpoint's `400` is a `WARN` carrying the same
kind the JSON body carries — the **user's** query failed, not the server — so console
and page agree on the classification. The three ad-hoc `warning: ` lines at startup
become `WARN` records, so stderr speaks with one voice.

**Deliberate exclusions, specified rather than omitted.** `404` and `405` are not
logged, there is no access log, and the client address is not recorded — logging
ordinary navigation would bury the genuine failures under every mistyped URL.
Nothing is redacted: an error may name a path under `~/.roadmaps/`, which is the
diagnostic value and never reaches the response.

**Log integrity.** A request path, roadmap name, Cypher query, and error text are all
attacker-reachable. `TextHandler` quotes and escapes any value carrying whitespace, a
quote, or a control character, so a newline followed by a forged
`level=ERROR msg="..."` stays inside its quoted value and cannot terminate the
record. A regression test drives that exact payload through both the path and the
error.

Stdout still carries only the startup URL object. The log adds no flag, no
configuration surface, and no dependency.

### Added — A Time Budget on the Graph Data Endpoint

The server's connection timeouts bound the connection, not the work a handler does.
A client that sends its headers promptly, stays connected, and reads the response as
soon as it arrives satisfies all of them however long the server takes. The graph
data endpoint is the one route whose work a caller drives, because the caller writes
the query — so it now bounds its own work.

- **A 5-second deadline** covering the run against the engine's read path and the
  walk over the result it produces.
- **Derived from the request's own context**, so the two sources of cancellation
  compose: a client that disconnects still cancels the query immediately, and a
  client that stays connected can no longer hold a query running beyond the budget.
- **The budget bounds the work; the node `LIMIT` bounds only the result.** A query
  that aggregates over a Cartesian product scans the whole product before any limit
  applies: its cost grows with the store while its response stays a few bytes long.
  The time budget is the only bound on that work.
- **No new status and no new error class.** Exhausting the budget is answered exactly
  as any other execution failure: HTTP `400` with `kind` `execution`. The process is
  never terminated and the server keeps serving.

The endpoint also **stopped injecting a node `LIMIT` into statements that admit
none**. Appending one to a schema-introspection command or a standalone `CALL` makes
the statement fail in the parser, so a read form the guard rail accepts, and that
`rmp graph query` runs, was unusable through this endpoint. Both forms are now
recognised on the masked normalization of the query and anchored to the start of the
statement, so a keyword appearing only inside a string literal, a comment, or a
backtick-quoted identifier does not affect the decision.

### Fixed — Security

**A guard-rail bypass let DDL through on an interface documented as read-only.**
This is the most serious finding of the release, discovered by an adversarial audit
of the whole application occasioned by the comment surface.

GoGraph's `ir.IsDDL` compares keyword prefixes with an ASCII fold, but as soon as a
non-ASCII byte appears in the prefix window it falls back to
`strings.HasPrefix(strings.ToUpper(stmt), ...)`. `strings.ToUpper` maps `U+0131`
(dotless i) to `I` and `U+017F` (long s) to `S`. The guard rail's own discriminator
used Go's `(?i)`, which is Unicode **simple case folding** and does **not** contain
the `I`/dotless-i pair. The guard rail therefore saw an ordinary read where the
engine saw DDL:

```
rmp graph query -r g -q "CREATE ıNDEX idx FOR (n:Seed) ON (n.k)"    exit 0
GET /roadmaps/<n>/graph/data?q=CREATE ıNDEX evil ...                HTTP 200
```

An unauthenticated `GET` on an interface documented as read-only therefore executed
schema DDL, reaching the index and constraint executors. There was no durable effect
— the read path builds an engine with no store and the write paths reject the
spoofed form — but only as an accident of the engine's own exemption, not because the
guard rail held.

The classifier now evaluates each discriminator **twice**: over the masked text and
over its `strings.ToUpper` copy, which is exactly the transformation the engine
applies. It can only add detections, since `ToUpper` never turns an ASCII keyword
letter into something else, so no legitimate read became rejected. The decisive
regression test anchors the invariant to the engine's real predicate rather than to
the two known code points.

**A node-limit bypass and an unbounded standard-input read** were closed in the same
pass. Seven further findings were recorded as tracked tasks rather than left
undocumented.

**The `0600` guarantee on `project.db` is enforced on every open, not only at
creation.** It was applied and verified only on the branch that **creates** the file.
Opening an existing database neither re-applied nor verified it, while the
surrounding directories were re-hardened to `0700` and re-verified on every open.
Measured: `chmod 666 project.db`, then run any command — it exited 0 and the file was
still `666` afterwards, while the two directories were silently restored to `700`.

A database arrives mis-permissioned in ordinary ways: restored from an archive that
carried no modes, copied off a FAT or NTFS mount, `rsync`'d without `-p`, produced by
an older binary under a permissive `umask`. The comment bodies this release exists to
create live in that file. Groadmap now hardens and verifies on **every** open and
**fails** when the file cannot be hardened, rather than warning.

**A roadmap directory that is a symbolic link now fails with exit code 1, not 2.**
The specification classified the refusal as a database error; the code raised a
misuse error. A symlink is a condition of the filesystem's state, not a syntax or
flag error, and exit 2 is documented as misuse. Two call sites were already
contradicting the old classification, `rmp web` among them, so the binary reported
two different codes for the same condition depending on the entry point.

### Fixed — Contract and Documentation Drift

**`rmp --ai-help` published stale wording for 16 of the 43 audit operations.** Four
were actively wrong rather than merely dated: `TASK_STATUS_CHANGE`, `TASK_UPDATE`,
`SPRINT_UPDATE`, and `SPRINT_MOVE_TASK` are `LEGACY` values that the per-destination
and per-field operations replaced, yet the contract still described them as the live
way to record a status change, an edit, or a move. An agent reading only the contract
was told to expect operations that no command writes.

No regression test was added, because the gate that failed **is** the regression
test: it re-derives all 43 descriptions from the canonical catalogue at test time and
compares byte for byte, so the transcription cannot drift again in either direction
without turning red.

**`DOCS/commands/audit.md` listed 21 of the 43 operations** and, by omitting both
commit-carrying operations, denied the feature's existence. The four `LEGACY` names
were presented as live, and its `audit ls -o TASK_STATUS_CHANGE` example names a value
that returns an empty array on every roadmap written at schema `1.12.0` or later.
Both `Output:` lines said an entry has five keys where the contract requires seven,
and the command help under-documented the same shape in two places, so `commit_hash`
was undiscoverable from `rmp audit list --help`. A new enum-coverage gate — the
fourth of its family, joining the help gate, the specification gate, and the contract
gate — now requires the document to name every operation the code can write and to
name none it cannot.

**`DOCS/commands/task.md` documented a `stat` command that no longer runs.** Its
usage line, flag table, rules, and examples showed `task stat ... DOING` and
`task stat ... COMPLETED` with no commit flag — invocations that now exit 6. Fixed in
this release: the section documents both flags with their mandatory states, format,
batch semantics, and a full error table; `reopen` states that it clears
`commit_close` and preserves `commit_open`; the Task object key list gains
`commit_open` and `commit_close`; the exit-code table names the new exit-6 causes;
and the output-format line no longer names the removed `assign` and `unassign`
subcommands. `DOCS/commands/sprint.md` now states what `remove-tasks` and `remove`
clear when a member task falls back to `BACKLOG`.

**Six stale specification defects were settled against the binary** rather than
against each other. `DATABASE.md`'s reopen SQL did not clear `completion_summary`
while `COMMANDS.md` and `STATE_MACHINE.md` said it did; observation settled it, and
`DATABASE.md` was wrong rather than outvoted. Six `DATABASE.md` sections documented a
`SELECT` shape no query in the repository has ever used, which is what hid
`subtask_count` from the file. `COMMANDS.md` claimed an ordering flag sorts by
severity where the code and the binary's own help sort by sprint position, carried a
malformed table row, and gave fifteen invalid-id messages that differed from the
bytes the binary prints. `STATE_MACHINE.md` omitted the manual `SPRINT` → `BACKLOG`
transition, making a reachable state look impossible. The sprint summary line's own
example was arithmetically impossible.

### Internal

**Three unreachable `internal/db` helpers were deleted, and the class that produced
them is now gated.** `DeleteSprint` duplicated the transaction in
`commands.sprintRemove` and had already drifted from it — it never received the fix
that clears the lifecycle fields when a member task falls back to `BACKLOG` — so a
published atomicity guarantee was being asserted against a copy the binary does not
run. `LogAuditEntry` and `LogAuditEntriesBatch` opened their own connection, which the
architecture forbids for an audit row: it must be written inside the transaction of
the modification it records, or it can outlive a rollback. `LogAuditTx` is now the
package's only audit writer.

A new AST sweep fails on any exported identifier in `internal/db` that no non-test
file in the module names, and it fails **both ways** — an unlisted dead export and a
listed one that has since gained a caller — so the allow-list may only shrink.

**A test class that never ran.** `tests/test_22_task87_sprint_capacity.py` declared
`TestAC6CapacityPctZero` twice. Python binds the name to whichever definition it
evaluates last, so the first was never collected. The two bodies were diffed before
anything was touched and were functionally identical, so no coverage was at risk —
the defect is that anyone correcting the AC6 assertions had an even chance of editing
the definition that does not run.

**The Go test suite is hermetic** and no longer writes to the developer's home
directory. **196 end-to-end call sites across 26 modules** were updated to pass a
commit hash, through a `commit_flags_for(status)` helper for the sites that build the
target status dynamically; no assertion was weakened, and several were strengthened,
because tests asserting a transition guard would otherwise have started passing for
the wrong reason — a missing flag rather than the guard. The end-to-end module index
is complete and gated against the registry.

**The vendored Tabler Icons webfont advances `3.44.0` → `3.46.0`.** Every other
vendored web asset was audited against the npm registry and the GitHub release feed
and was already current: D3.js 7.9.0, d3-sankey 0.12.3, Tabler core 1.4.0, and the
Inter variable webfont. Pre-release channels are excluded by policy. No rendering

**An experiment was reverted rather than hand-edited back.** A git-style audit

  self-contradiction in the specification, which both required and excluded the tabs
  from the badge-colour mapping: rule 2 spoke of badge *kinds* — what a badge writes
  — where what the tables determine is the *colour*. Tracked as `rmp` task #127, now
  closed.

- **The `.gosec.yaml` suppression register had drifted from the tree**, recorded
  under `[1.14.0]` as task #141 and **fixed in this release**. The register declares
  that a suppression not listed in it is a review failure, and one had become
  unlisted: `#nosec G306` in `internal/db/permissions_test.go`, added when the
  `0600` enforcement work landed. Three per-class counts had also drifted as code

### Open

Ordered by what actually affects a user of this release.

- **A stranded `snapshot.bak` stops every later graph checkpoint, and the write still
  exits 0.** Upstream GoGraph behaviour, unchanged this release (no dependency moved),
  and the one item here that can affect you in normal use. The snapshot publish is a
  crash-atomic three-step swap, and the cleanup of a stale backup before the swap is
  best-effort; if that residue cannot be removed, the archive rename fails against a
  non-empty `snapshot.bak` and the checkpoint returns an error.

  Groadmap surfaces that as `Warning: graph checkpoint failed: ...` on **stderr** and
  returns **exit code 0** — required behaviour, not an oversight: a checkpoint failure
  *after* a durable commit must not fail the write, because the commit is already
  durable and the write-ahead log is intact.

  - **No data is lost.** The WAL is intact and recovery still works.
  - **Automation can miss it.** The exit code is 0 and stdout is the normal success
    JSON; only stderr says anything.
  - **The WAL grows without bound** while the condition lasts, because only a
    successful checkpoint truncates it.

  It **self-heals**: remove `snapshot.bak` from `~/.roadmaps/<roadmap>/graph/` and the
  next write checkpoints and truncates normally. Watch stderr on `rmp graph create`,
  `rmp graph update`, and `rmp graph delete`.

- **The local lint gate ran at `v2.13.1` where the specification pins `v2.12.2`.**
  `SPEC/BUILD.md § Linter` states that a tool's version is part of its definition, and
  both GitHub workflows request `v2.12.2`. The `golangci-lint` on the release
  machine's `PATH` is `v2.13.1`. The run reports **0 issues**, so nothing is being
  suppressed, but a newer linter can differ in both directions and the local run is
  therefore not the gate the specification defines. The CI job on this branch runs the
  pinned version and is authoritative; confirm it is green before tagging.

- **The graph read path builds an in-memory engine where the specification requires a
  store-backed one.** `SPEC/GRAPH.md § Engine Construction and Lifecycle` requires
  `cypher.NewEngineWithStore`. The write path complies
  (`internal/commands/graph.go:840`); the two read paths —
  `internal/commands/graph.go:693` and `internal/web/data.go:1871` — call
  `cypher.NewEngine(res.Graph)`.

  **No user-visible consequence has been demonstrated.** Both read paths construct the
  engine over a graph that `recovery.Open` has already loaded from the on-disk
  snapshot and write-ahead log, so a read still observes committed state, and the
  graph end-to-end suites exercise exactly that across process exits and pass. It is
  recorded as a specification-conformance divergence, not a data-correctness defect.
  Tracked as `rmp` task #149.

- **Two knowledge-graph nodes share the key `README.md`.** `knowledge-model.md`
  states that every node's `key` is globally unique, so that `MATCH (n {key:'...'})`
  without a label is unambiguous. A `Doc` node and a `Spec` node both carry the key
  `README.md`. The model contradicts itself rather than merely being violated by the
  data: it keys `Spec` nodes by bare file name and `Doc` nodes by repository-relative
  path, and for `README.md` the two rules produce the same string. Verified still
  present at this tag. This concerns the project's own internal knowledge graph — not
  any user's roadmap data, and no `rmp` command output. Tracked as `rmp` task #155.
