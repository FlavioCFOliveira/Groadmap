# Release Notes — Groadmap v1.19.0

**Date:** 2026-10-28
**Type:** Minor by the owner's decision — **but it changes the behaviour and the error lines of `rmp graph client`** (see [What Breaks](#what-breaks))
**Tag:** `v1.19.0`
**Previous release:** `v1.18.0` (2026-10-02)

---

## Executive Summary

Groadmap `v1.19.0` moves the knowledge graph onto GoGraph `v0.17.2`, which corrects
the relationship writes, the failed-statement rollback and the error reporting that
`v1.18.0` documented as engine hazards. It converts each graph store to the
engine's new on-disk format on its first start, after taking a backup. The web
interface gains a roadmap dashboard as its landing page and a sprint progress gauge,
and moves to Tabler `v1.7.1`. The Go floor rises to `1.27.3`, which fixes ten
standard-library advisories reachable from Groadmap's code.

The SQLite schema does not change: databases stay at schema `1.17.0`. No CLI
command, subcommand or flag is added or removed, and the AI Agent Contract that
`rmp --ai-help` emits is unchanged apart from `tool.binary_version`.

**Read [What Breaks](#what-breaks) before you upgrade, because the version number
will not warn you.** A strict SemVer reading of this release gives `MAJOR`. The
project publishes `1.19.0` by the owner's explicit decision, recorded in
[Why This Is Released as `1.19.0`](#why-this-is-released-as-1190).

## What Breaks

All four changes affect `rmp graph client` only, and all four come from the engine
upgrade (`5687e48`, `1550047`, `72cc0d1`), specified in `47ca57e`. Every
before-and-after statement in this section was measured on 2026-10-28 by running the
same statement against a `v1.18.0` binary built from its tag and against the
`1.19.0` tree, each against a throwaway roadmap in an isolated `HOME`.

### 1. `PROFILE` of a writing statement executes the write

`v1.18.0` published, in `SPEC/GRAPH.md § Query Plans: The EXPLAIN and PROFILE
Prefixes` rule 4, that `PROFILE` refuses a statement that writes. `1.19.0` executes
it, commits it once, and publishes the `profile` tree beside its rows.

| Statement | `v1.18.0` | `1.19.0` |
|---|---|---|
| `PROFILE CREATE (s:Spec {key:'GRAPH.md'}) RETURN s.key` | exit `1`, `Error: graph engine error: graph query failed: An internal error occurred. See server logs for details (session: <id>)` | exit `0`, members `columns`, `rows`, `profile`, `counters` |
| `MATCH (s:Spec) RETURN count(s) AS n`, afterwards | `0` | `1` |

A caller who wants a writing statement's plan without its effect uses `EXPLAIN`,
which executes nothing. `PROFILE` is not a way to inspect a write safely.

### 2. `counters` can appear beside `profile`

`v1.18.0` published, in `SPEC/DATA_FORMATS.md § Graph Query Counters` rule 5, that a
consumer may rely on never seeing `counters` beside `plan` or `profile`. In `1.19.0`
the guarantee holds for `plan` only. A `PROFILE` of a statement that changed the
graph publishes `counters` after `profile`, with the values the same statement
publishes without the prefix: in the measurement above,
`{"nodesCreated": 1, "propertiesWritten": 1, "labelsAdded": 1}`. A `PROFILE` of a
statement that changed nothing publishes no `counters`.

### 3. A property value that is a list holding `null` is refused

| Statement | `v1.18.0` | `1.19.0` |
|---|---|---|
| `CREATE (c:Component {key:'graphstore'}) SET c.tags = ['storage', null] RETURN c.key` | exit `0`, `nodesCreated: 1`; `c.tags` reads back `null` | exit `1`, `Error: graph engine error: graph query failed: exec: SET tags: exec: InvalidPropertyType: a list containing null is not a valid property value`; no node is created |

`v1.18.0` stored such a value other than as written in every form: an assignment
stored nothing, a map entry was dropped, and an inline map stored the list without
its `null` elements. `1.19.0` refuses every form, on a node and on a relationship,
and the transaction rolls back whole (`SPEC/GRAPH.md § What Groadmap Does Not
Check`, item 9).

### 4. An over-long field has its own error line

| Statement | `v1.18.0` | `1.19.0` |
|---|---|---|
| ``CREATE (n:`<70000 × L>`)`` | exit `1`, `Error: graph engine error: graph query failed: txn: field too long for its WAL length prefix: node label is 70000 bytes, maximum 65535` | exit `1`, `Error: graph engine error: graph field too long; nothing was written. Shorten the field the engine names: token too long: node label is 70000 bytes, maximum 65535` |

The `1.19.0` line is the one `SPEC/COMMANDS.md § Client Error Cases` already
published and declared unreachable at the earlier engine. `rmp` selects it by the
two failure codes the engine's server now assigns,
`Neo.ClientError.Schema.TokenLengthError` and
`Neo.ClientError.Data.DataUnsupportedByStoreFormat`, and by nothing else. The exit
code and the sentinel, `utils.ErrGraphEngine`, are unchanged. The web graph data
endpoint answers the condition as an `execution` failure carrying the engine's
diagnostic.

### Migration guidance

- Replace `PROFILE` with `EXPLAIN` wherever a script relied on the refusal to keep a
  write harmless.
- Accept `counters` beside `profile` in any consumer of the client's JSON.
- Remove `null` elements from a list before writing it as a property.
- Match `graph field too long; ` instead of `graph query failed: ` to detect an
  over-long field.

## New Features

### Web: the roadmap dashboard is the landing page

`GET /roadmaps/{name}` now serves a dashboard (`5bf0457`, `479b0c9`, `2a491dc`,
`7ac0a75`, `ad926a5`; `SPEC/WEB.md § Roadmap Dashboard Page`). It holds six blocks:

1. **KPI row** — open, completed and backlog tasks, each with a donut of its task
   types when its value is not `0`, and the average velocity `rmp stats` reports.
   The Completed card carries a `<c> of <m> tasks` row and a progress bar.
2. **Current sprint** — titled `Current sprint: <title>`, the title linking to the
   sprint page, with a progress row (`<p>% complete`, start date and days elapsed),
   a segmented status bar, its legend and the capacity line.
3. **Work in progress** — the tasks in progress.
4. **Highest-severity open tasks.**
5. **Upcoming sprints** — the `PENDING` sprints.
6. **Recent activity** — the ten most recent audit entries.

Every figure is read in one read-only transaction with a fixed statement count,
reusing the CLI's velocity and audit queries. The chart data travels in an
`application/json` element (`SPEC/DATA_FORMATS.md § Dashboard Chart Data`), so the
Content-Security-Policy keeps `script-src 'self'` and no template carries an inline
style. ApexCharts `7.0.0` and the Tabler vendors stylesheet are vendored for the
charts. During the cycle the dashboard also briefly carried a weekly throughput
chart, a sprint burndown and three chart blocks; they were removed before this
release, and `rmp sprint stats` keeps its burndown.

### Web: a Sprint progress card on the sprint page

The sprint page opens with a summary row: Sprint details beside a new Sprint
progress card (`c8c48bd`, `3918718`). Its radial gauge shows the member tasks in the
board's `WAITING`, `DOING` and `CLOSED` columns, with the completed percentage at its
centre; hovering an arc shows its count. The legend and the total (`<n> Tasks`,
`1 Task`, `0 Tasks`) are rendered by the server, so they read without JavaScript.
The counts come from the board's own status grouping, so they equal its column
badges (`SPEC/DATA_FORMATS.md § Sprint Progress Chart Data`).

### Graph store backup before the format conversion

`rmp graph serve` copies a store still in the single-file write-ahead-log format to
`~/.roadmaps/<name>/graph-backup-<T>/` before the engine converts it (`5687e48`);
see [Graph Store Format](#graph-store-format). A backup that cannot be completed
stops the start with exit `1` and the new line
`Error: graph store error: graph store backup failed; the store was not migrated: <detail>`,
and the store is neither opened nor converted.

### Release: the GitHub Release body is the CHANGELOG section

`scripts/changelog-section.sh` extracts the version's `CHANGELOG.md` section, and
`release.yml` publishes it as the GitHub Release body, followed by the generated
Full Changelog link (`005a8fd`; `SPEC/DEPLOY.md § GitHub Release Body`). A missing,
empty or duplicated section fails the workflow before the release is created.

## Other Changes

### Web: the sprints page moves to `/roadmaps/{name}/sprints`

Measured with `rmp web` against a fresh roadmap:

| Request | `v1.18.0` | `1.19.0` |
|---|---|---|
| `GET /roadmaps/{name}` | `200`, title `<name> - Sprints - <host>` | `200`, title `<name> - Dashboard - <host>` |
| `GET /roadmaps/{name}/sprints` | `404` | `200`, title `<name> - Sprints - <host>` |

The sidebar lists Dashboard, Sprints, Tasks, Audit and Graph, and the roadmap
index links land on the dashboard (`5bf0457`). A bookmark of the old landing URL
opens the dashboard, from which Sprints is one click away.

### Graph: relationship writes reach the relationship the statement bound

Under `v1.18.0` the following reported success while acting on the wrong
relationship or on none (`SPEC/GRAPH.md § What Groadmap Does Not Check`, items 4
and 8). Under `1.19.0` each acts on exactly the relationships the statement bound.

- **`REMOVE` through an incoming or undirected pattern.** Measured: after
  `CREATE (s:Spec {key:'s1'})-[:VERIFIED_BY {last_commit:'abc1234'}]->(t:Test {key:'t1'})`,
  the statement `MATCH (v:Test {key:'t1'})<-[e]-(s) REMOVE e.last_commit` returned
  `{"ok": true}` and left `last_commit` at `abc1234` under `v1.18.0`; under
  `1.19.0` it returned `counters` `{"propertiesWritten": 1}` and the property reads
  back `null`.
- **A `MERGE` that matches over a node pair joined several times in the pattern's
  direction** now matches every such relationship, one row each, so `SET`,
  `REMOVE`, `DELETE` and the counters act on exactly those; an inline-map `MERGE`
  whose map an existing relationship satisfies no longer creates a duplicate.
- **`DELETE` through a relationship bound by `CREATE`** deletes the created
  relationship rather than a pre-existing one of the pair.

The last two are covered by `internal/commands/graph_mergebinding_test.go` and
`internal/commands/graph_relwrite_test.go`, and were not re-measured against
`v1.18.0` for these notes. The forms recommended for the earlier engine — a
re-binding outgoing `MATCH`, or an assignment of `null` — remain correct on both.

### Graph: a budget-cut statement can leave node-identifier reservations

A statement cut by the 5-second budget still rolls back whole and changes no node,
relationship, property, label, index or constraint. The write-ahead log may now
keep the engine's reservations of identifiers for nodes the statement had created;
`v1.18.0` left the log as the statement found it (`5687e48`; `SPEC/GRAPH.md
§ Statement Time Budget`, rule 3).

### Web: Markdown and layout

- **CommonMark line breaks** (`d102b44`): a single newline inside a paragraph is a
  soft break, shown as a space; two trailing spaces or a trailing backslash still
  render `<br>`. `v1.18.0` rendered every newline as `<br>`. Plain multi-line graph
  property values keep their breaks.
- **Full-width Markdown** (`b1ba436`): the `80ch` cap on the sprint page's
  description and comment bodies is removed.
- **Tabler `v1.7.1` and Tabler Icons `v3.50.0`** (`5687e48`, `e178208`), from
  `v1.6.0` and `v3.46.0`. The icon font is served as 48 `unicode-range` `woff2`
  chunks, replacing the single `woff2`, `woff` and `ttf` files. Every page renders
  a `<main>` that holds the page header and body. The six scrollable tables are
  focusable regions labelled by their card titles, with a focus outline meeting
  3:1 contrast.

### CI and the release process

The CI workflow publishes nothing: the `dev` pre-release and the CI build artefacts
are removed, and `release.yml` is the only workflow that publishes (`3d97685`,
`c7fdf44`). The release process now pushes `main` first and pushes the tag only
after the CI run on that push has succeeded (`SPEC/VERSION.md § Release Process`).

## Fixes

- **A failed graph statement no longer replaces an existing relationship**
  (`5687e48`; `SPEC/GRAPH.md § Error Handling and Exit Codes`, rule 9). Measured:
  after `CREATE (a:Svc {key:'api'})-[:OLD {p:1}]->(b:Svc {key:'db'})`, the statement
  `MATCH (a:Svc {key:'api'}),(b:Svc {key:'db'}) CREATE (a)-[:NEW]->(b) WITH a RETURN 1/0`
  exits `1` on both binaries. Afterwards the pair is joined by `NEW` with no
  properties under `v1.18.0`, and by `OLD {p: 1}` under `1.19.0`.
- **A property value the engine cannot store is refused with the engine's own
  diagnostic** (`5687e48`). Measured with `CREATE (n:Probe {key:'map', bad:{a:1}})`:
  both exit `1`; `v1.18.0` wrote
  `An internal error occurred. See server logs for details (session: <id>)`, and
  `1.19.0` ends the line in
  `InvalidPropertyType: a nested list or map is not a valid property value`.
- **Graph server memory is released at the end of a statement that overlapped a
  release** (`c67db02`). A release taken while statement A ran counted A's live heap
  into the baseline, so A's end never passed the growth gate and up to 2 GiB stayed
  resident. Covered by `internal/graphserve/memrelease_overlap_test.go`.

## Graph Store Format

The engine upgrade changes the store's on-disk format twice: GoGraph `v0.16.0`
replaces the single-file write-ahead log with `wal.control` and a segmented
`wal.d/`, and `v0.17.0` writes a new snapshot manifest version at the first fold
(`SPEC/GRAPH.md § Dependency Maturity Risk`).

On its first start against a store in the single-file format, `rmp graph serve`:

1. copies the store to `~/.roadmaps/<name>/graph-backup-<T>/`, `<T>` being the UTC
   instant in the form `YYYYMMDDTHHMMSSZ`, with modes `0700` and `0600`;
2. opens it, and the engine converts it during the open;
3. removes the copy once the conversion has succeeded and the store is open,
   reporting both steps on stderr at `INFO`.

When the conversion or the open fails, the copy is kept and its path reported.

Measured on 2026-10-28: a store written by `v1.18.0` (holding `snapshot/`, `wal`,
`wal.lock` and `write.lock`) was backed up, converted and served by `1.19.0` with
its 4 nodes intact, and the backup was removed. The converted store holds
`wal.control`, `wal.d/` and `wal.prefix-truncated`. A `v1.18.0` `graph serve`
against it then exited `1` with
`Error: graph store error: graph store unavailable: wal: unsupported frame version`.

## Known Issues

The list was rebuilt for this release. Each item was verified on this tree, by the
means stated. Four items of the `v1.18.0` list are resolved and are listed under
[Fixes](#fixes) and [What Breaks](#what-breaks): the failed statement that replaced
a relationship, the list holding `null`, the generic text for an unstorable value,
and the unreachable field-length line. The two engine hazards of items 4 and 8 are
resolved under [Other Changes](#other-changes).

- **`rmp audit list --help` still says `TASK_STATUS_BACKLOG` carries `null` "from
  'task stat'".** `task stat` cannot write that row since `v1.18.0`. Verified by
  running the `1.19.0` help.
- **`rmp backlog --help` and `rmp backlog list --help` still say no 0-9 validation
  is enforced on `--priority`.** The binary refuses `-p 12` with exit `6`. Verified
  by running the `1.19.0` helps.
- **`1.19.0` does not re-check sprint membership when it opens a database already at
  schema `1.17.0`**, as `v1.18.0` did not. A violation written by a binary older
  than `1.18.0` stays until a membership command touches the task. Verified in the
  code: the migrations are unchanged since `v1.18.0`; not reproduced for this
  release.
- **`modernc.org/libc` is a later release than `modernc.org/sqlite` requires**
  (`v1.79.1` in `go.mod`, against the `v1.79.0` that `modernc.org/sqlite v1.61.0`
  declares in `go mod graph`). The project accepts the risk deliberately
  (`SPEC/BUILD.md § SQLite Driver Rules`). Verified with `go mod graph`.
- **The web query bar's `EXPLAIN`/`PROFILE` prefix check runs outside the 5-second
  budget**, because the engine's parser takes no context (`internal/web/data.go`,
  `refusePlanPrefix`). The code comment records that the costliest input found at
  the 1 MiB ceiling parsed in 2.44 s to 2.72 s and allocated 1.46 GiB; that figure
  was not re-measured for this release.

## Upgrade Notes

### Step 1 — Check the programs that drive `rmp graph client`

Read [What Breaks](#what-breaks). A program is affected if it runs `PROFILE` on a
writing statement, assumes `counters` never accompanies `profile`, writes a list
holding `null` as a property, or matches the error line of an over-long field.
Nothing outside `rmp graph client` changes its output, apart from the web pages.

### Step 2 — Back up each graph store, if you may need to go back

The first `1.19.0` `rmp graph serve` on a roadmap converts its graph store, one
way. It takes and then removes its own backup, so keep a copy yourself if you may
return to `v1.18.0`:

```bash
cp -a ~/.roadmaps/<name>/graph ~/.roadmaps/<name>/graph.v1.18.0
```

Stop any running `rmp graph serve` first. The SQLite database needs no action.

### Step 3 — Update a bookmark of the sprints page

The sprints page is now at `/roadmaps/{name}/sprints`; `/roadmaps/{name}` is the
dashboard.

### Step 4 — Install and verify

```bash
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install.sh | bash
rmp --version
# Groadmap version 1.19.0 (commit <commit>)
```

To update the agent skills as well:

```bash
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install-skills.sh | bash
```

### Downgrading

**A `v1.18.0` binary cannot serve a graph store that `1.19.0` has converted.**
Measured: it exits `1` with
`Error: graph store error: graph store unavailable: wal: unsupported frame version`.
To go back, stop the server and restore the copy taken in Step 2; every graph write
made after the copy is lost. The roadmap database is unaffected, because its schema
does not change.

## Why This Is Released as `1.19.0`

A strict reading of Semantic Versioning 2.0.0 gives `MAJOR`. The items under
[What Breaks](#what-breaks) withdraw a refusal and a JSON guarantee that `v1.18.0`
published, refuse writes that `v1.18.0` accepted, and move a condition to another
error line. None of that is backward-compatible.

The project publishes `1.19.0` by the owner's explicit decision of 2026-10-28,
recorded here. It follows the same decision taken for `1.18.0` and its
predecessors.

**So do not read the minor digit as a promise that nothing breaks.** Upgrading is
safe unless a program of yours does one of the things listed in
[Step 1](#step-1--check-the-programs-that-drive-rmp-graph-client).
