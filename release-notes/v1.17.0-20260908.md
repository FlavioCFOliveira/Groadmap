# Release Notes — Groadmap v1.17.0

**Date:** 2026-09-08
**Type:** Minor by the owner's decision — **but it removes a subcommand and breaks every caller that used it** (see [Breaking Changes](#breaking-changes))
**Tag:** `v1.17.0`
**Previous release:** `v1.16.0` (2026-09-07)

---

## Executive Summary

Groadmap `v1.17.0` finishes what `v1.16.0` started. That release gave the knowledge
graph a dedicated server and left `rmp graph execute` beside it, opening the store
directly whenever no server answered. This release **withdraws `execute`**. The `graph`
command now has exactly two subcommands — `serve` and `client` — and a graph is reached
through a running server or not at all.

**Read the breaking list before you upgrade, because the version number will not warn
you.** A strict SemVer reading of this release gives `MAJOR`: a documented public
subcommand is removed with no alias and no fallback. The project publishes `1.17.0` by
the owner's explicit decision, on the same footing as `1.15.0`, which shipped breaking
changes as a `MINOR`, `1.15.2`, which shipped them as a `PATCH`, and `1.16.0`, which was
cut as `2.0.0` and renumbered. Each was recorded at the time rather than inferred later.
This is that record.

The one incompatibility that matters:

1. **`rmp graph execute` is gone.** It exits `127` with `unknown graph subcommand`.
   Every script, agent prompt and stored recipe that reaches a graph without first
   starting a server stops working. There is no one-shot form and none is planned.

Two further changes are incompatible in effect rather than in signature: the web
interface's graph page answers HTTP `503` where it used to fall back to reading the
store, and a roadmap whose derived socket path exceeds the platform bound is now refused
at **every** surface rather than at two of the four.

Alongside the withdrawal, two features arrive that make the graph easier to work with
honestly: **a write now reports what it changed**, and **a field the durable format
refuses now says so** — including the one refusal that can never heal.

There is **no database migration**, **no dependency change**, and no exit code moved.

---

## Highlights

- **Two subcommands, one way in.** `rmp graph serve` opens the store and holds it;
  `rmp graph client` runs every statement against that server. Nothing else opens a
  store.
- **Starting a server is what creates a graph.** Against a roadmap that has never had
  one, `serve` creates `~/.roadmaps/<name>/graph/` and serves it empty.
- **A write reports its effects.** A `counters` object names nodes and relationships
  created and deleted, properties written, labels added and removed, and indexes and
  constraints added and dropped.
- **The durable-format limits are published, and the trap in them is named.** A property
  value between 1 GiB and 4 GiB commits successfully and then breaks every subsequent
  checkpoint, permanently. `1 GiB` is the figure to write under.
- **An over-long socket path explains itself** instead of reporting `bind: invalid
  argument`.

## Breaking Changes

### 1. `rmp graph execute` is withdrawn

```bash
# Before                                     # After
rmp graph execute -r proj -q "MATCH (n) ..." rmp graph serve -r proj &      # once, and leave it
                                             rmp graph client -r proj -q "MATCH (n) ..."
```

`rmp graph execute` now exits `127`:

```
Error: unknown graph subcommand: execute
```

This follows the precedent `v1.16.0` set for the five subcommands it withdrew.

**Why.** A server holds the store's exclusive advisory lock for its whole life, and no
finite wait can be sized against a hold with no upper bound. That is why a two-path
resolution — send to a server if one answers, otherwise open the store — existed at all,
and it still bit any surface that reached the store without resolving first. Withdrawing
every such surface makes the resolution concept unnecessary rather than merely unused,
and it dissolves the regression in which `execute` and the web endpoint refused over an
over-long derived socket path that neither of them needed.

**`rmp graph client` will not quietly become `execute`.** With nothing listening it fails
with exit code `1` rather than opening the store. A subcommand that silently fell back
would report a success that says nothing about whether a server was reached.

### 2. The web interface's graph page answers `503` instead of reading the store

The graph data endpoint reaches the graph through the same client mechanism as the CLI
and through nothing else. With no server running for that roadmap it answers HTTP `503`
and logs at `WARN`, because starting a server clears the condition and nothing in the
server is at fault.

A socket path over the platform bound remains HTTP `500` at `ERROR`. The two conditions
are deliberately distinct: one is a dependency awaiting an operator, the other is a
layout that can never work.

### 3. Every surface refuses an over-long socket path, however it was chosen

The previous rule split on the **provenance** of the path: a `--socket` value over the
platform's bound failed everywhere, while a **derived** path over the bound failed only
`serve` and `client` and left `execute` and the web endpoint to open the store.

The uniform rule replaces it, by the owner's decision. The split was breaking a
requirement stated elsewhere — that the surface a statement ran through is not observable
in what it writes — and it reported a roadmap's genuinely broken layout at two surfaces
while concealing it at two others.

**The cost is real and is not softened.** A sufficiently deep home directory now makes a
graph unreachable through every surface at once. On the command line the way back is
`--socket` naming a path inside the bound, given to **both** ends of the pair. The web
page has no such flag, so its only remedy is a shorter home directory or a shorter
roadmap name.

### 4. The store-busy lock line is withdrawn from the caller-facing surface

Nothing but a server takes the store lock now, so the only contender a server can meet is
another server.

### 5. The AI Agent Contract loses its `execute` entry

`rmp --ai-help` describes two graph subcommands where it described three, and the `graph`
command's own description is rewritten around the server-and-client pair. A machine
consumer that enumerates graph subcommands from the contract sees one fewer.

## What Is New

### A write reports what it changed

```bash
rmp graph client -r myproject --query "CREATE (:Spec {key:'rate-limiting', status:'draft'})"
```

```json
{
  "ok": true,
  "counters": {
    "nodesCreated": 1,
    "propertiesWritten": 2,
    "labelsAdded": 1
  }
}
```

Until now this answered `{"ok": true}`, which says a statement succeeded and not the
thing a caller writing to a graph most needs to know: two invocations that both printed
it may have created a node and matched an existing one, or deleted a thousand
relationships and deleted none.

**The member is additive and costs no existing caller a byte.** A counter that is zero is
left out, and a statement that changed **nothing** carries no `counters` key at all —
every read, every `EXPLAIN`, a `MERGE` that matched an existing element, a `DELETE` whose
pattern matched no row. `ok` keeps its meaning, its value and its position.

**`propertiesWritten` folds two engine counters into one.** openCypher counts a property
assignment and a property removal separately; the Bolt statistics vocabulary has one
property counter and no counterpart for a removal, so a served result arrives with the
two already summed and the split cannot be recovered. A `REMOVE` that reports
`propertiesWritten` is correct, not a defect. Telling a `MERGE` that created from one that
matched rests on the node and relationship counters, which cross the protocol faithfully.

### The durable-format field limits, and the refusal that cannot heal

GoGraph's write-ahead log and its snapshot each refuse a field too long for their length
prefix. Groadmap recognised neither, so a caller had to read English to tell a length
refusal from a Cypher syntax error, and a checkpoint that failed for this reason was
reported with the general message — which tells an operator to expect the next checkpoint
to reconcile, when this one never can.

**Four limits, and the one that binds is not the one a reader expects:**

| Format | Label or property key | Property value |
|---|---|---|
| Write-ahead log | 65535 bytes | 4294967295 bytes |
| Snapshot | 1 MiB | 1 GiB |

So the log's key bound fires first and the snapshot's key bound is unreachable, while for
a **value** the snapshot binds at a quarter of the log's figure. **1 GiB is the number to
write under.**

**The two failures differ in the way that matters:**

- **Too long for the log** and the commit is refused. Nothing is written, the store stays
  usable, and the invocation exits `1`.
- **Short enough to commit and too long to fold** — a property value between 1 GiB and
  4 GiB — and the write succeeds and exits `0`, and then **every checkpoint of that graph
  fails from that moment on**. The offending field is committed graph state, so the
  write-ahead log is never folded again and never reclaimed: it grows, and every open
  replays more of it. It persists until a statement shortens or removes the field.

## What Was Silently Wrong Before

### An over-long socket path reported the bare errno

```
# Before
Error: graph server error: cannot bind <path>: listen unix <path>: bind: invalid argument

# After
Error: graph server error: socket path is too long: <path> is 236 bytes and
this platform allows at most 107. Use --socket to name a shorter path.
```

The old line printed the path twice, named neither its length nor the limit, and sent a
reader looking at the roadmap, the store, or the permissions.

**The default path is reachable, and this was found by accident rather than by design.**
With no `--socket` flag at all, a three-character roadmap name under a deep home directory
produced a 139-byte path and the server refused to start.

**The bound is derived, not written down**, because it is not one number: 107 bytes on
Linux and Windows, 103 on macOS, FreeBSD and OpenBSD. A literal `107` would have been
correct on two of the five operating systems and would have silently accepted four
unbindable paths on each of the other three — handing back the very errno the change
exists to replace. Length is counted in **bytes**, never in runes.

### `rmp sprint stats --help` described `days_elapsed` backwards

The published help text said "For CLOSED sprints it spans `started_at` -> `closed_at`". A
CLOSED sprint reports `null`: the field is set only while a sprint is `OPEN`. This was
published contract rather than prose, and the same false sentence had been copied into
`DOCS/commands/sprint.md`. A regression test now pins the help text to what the model
computes, and it is mutation-proved.

### `README.md` claimed `sprint remove` required a `CLOSED` sprint

It does not. `PENDING`, `OPEN` and `CLOSED` are all removable, and every member task
returns to `BACKLOG` whatever status it held — `COMPLETED` included, with `commit_close`
cleared and `commit_open` preserved. The claim was false in the dangerous direction: it
told a reader an `OPEN` sprint was protected when it was not.

### Six further documentation defects, each measured against the binary

- `DOCS/commands/stats.md` typed `sprints.current` as an integer described as an
  "identifier or count". It is the open sprint's id, or `null`, and never a count. Its
  example carried sprint counts that are arithmetically impossible while a sprint is open.
- `DOCS/commands/backlog.md` omitted `commit_open` and `commit_close` from the task-key
  list, disagreeing with `task.md`; described a leading `--limit` on `show-next` as
  "ignored" when it is read as the `count` itself and refused with exit `6`; and had no
  exit-`4` row.
- `DOCS/commands/web.md` omitted the listener-stopped cause from its exit-`1` row, and
  omitted `/roadmaps/{name}/tasks/{id}/data` from a route table the README calls the full
  route list.
- `DOCS/commands/sprint.md` carried a sentence classifying which commands carry an
  **Audit** block that was false in both directions.
- `DOCS/commands/graph.md` stated the exit code of the two plan-prefix refusals but not
  that one of them tells the caller nothing actionable.
- `SPEC/GRAPH.md` promised that the refused `PROFILE` reports a diagnostic naming the
  remedy. The caller receives generic internal-error text naming only the session; the
  real diagnostic reaches the **server's** stderr. Traced into the pinned engine: the
  refusal carries no sentinel, so the Bolt failure-code mapping falls through to a
  generic database-error code and the session substitutes the message. The remedy belongs
  in the engine, and the specification now says so instead of claiming it for Groadmap.

## Upgrade Notes

### Step 1 — Start a server before you reach a graph

Every graph statement now needs a running server. Start one per roadmap and leave it
running:

```bash
rmp graph serve -r myproject &
# {"socket": "/home/you/.roadmaps/myproject/graph.sock"}

rmp graph client -r myproject --query "MATCH (n:Spec) RETURN n.key"
```

Wait for the `{"socket": ...}` line on stdout before sending anything.

### Step 2 — Rewrite every call that names `execute`

```bash
# Find them across your scripts, agent prompts and stored recipes
grep -rn "graph execute" .
```

Each becomes `rmp graph client` against a running server. The statement text does not
change, and `client` writes byte for byte what `execute` wrote for the same statement
against the same graph.

### Step 3 — Check your home directory depth

The derived socket path is `~/.roadmaps/<name>/graph.sock`. If that exceeds 107 bytes on
Linux or Windows, or 103 on macOS, FreeBSD or OpenBSD, every graph surface now refuses it:

```bash
python3 -c "import os;p=os.path.expanduser('~/.roadmaps/myproject/graph.sock');print(len(p.encode()),p)"
```

On the command line, pass `--socket` naming a shorter path to **both** `serve` and
`client`. The web interface has no such flag, so a page for that roadmap stays
unavailable until the home directory or the roadmap name is shortened.

### Step 4 — If you browse a roadmap, start its server without `--socket`

`rmp web` has no way to receive a socket path: it is an HTTP handler serving every
roadmap at once, and no request parameter carries one. A server started with `--socket`
therefore leaves that roadmap's graph page answering `503` for as long as it runs.

### Step 5 — There is no database migration

The SQLite schema version is unchanged at `1.14.0` and no migration was added. `go.mod`
and `go.sum` are byte-identical to `v1.16.0`, so the graph engine is the same GoGraph
`v0.14.0` and the graph store's on-disk format takes no version step. A graph written by
either binary is read by the other.

### Step 6 — Install and verify

```bash
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/Groadmap/main/install.sh | bash
rmp --version
# Groadmap version 1.17.0

rmp graph execute -r myproject -q "RETURN 1"
# Error: unknown graph subcommand: execute        <- expected; use serve + client
```

## Why This Is Released as `1.17.0`, and What That Number Hides

`SPEC/VERSION.md` defines `MAJOR` as "incompatible API changes or major architectural
changes". This release removes a documented public subcommand with no alias and no
fallback, which is an incompatible change by any reading, and the strict reading therefore
gives `2.0.0`.

The project publishes `1.17.0` by the **owner's explicit decision**, recorded here. It is
the fourth consecutive release to do this: `1.15.0` shipped breaking changes as a `MINOR`,
`1.15.2` shipped them as a `PATCH`, and `1.16.0` was cut as `2.0.0` and renumbered before
it was tagged. The project has a convention for overruling the strict reading in writing,
and this entry follows it.

**Do not read the minor digit as a promise that nothing breaks.** The test to apply is
short:

> Upgrading is safe unless you invoke `rmp graph execute`, rely on the web graph page
> reaching a store with no server running, or run under a home directory deep enough that
> the derived socket path exceeds 107 bytes on Linux and Windows, or 103 elsewhere.

**What did not change, and why it does not soften the above.** No exit code moved. No flag
was removed or added outside the `graph` family. The top-level help is byte-identical to
`v1.16.0`, and so is every subcommand help but one: `rmp sprint stats --help`, whose
`days_elapsed` description was corrected because it was false. These are reasons the
release is not *more* disruptive than it is; none of them is a reason to call it `MINOR`.

---

## What Is Not In This Release

- **No one-shot graph invocation.** `execute` is not coming back in another spelling, and
  no flag restores the old fallback.
- **No authentication or transport security on the graph server.** The socket is mode
  `0600` inside a roadmap home that is `0700`, and that filesystem permission is the whole
  of the access control. Any caller that can open the socket can read, write, delete and
  change the schema of that roadmap's graph. The engine prints a warning for each at
  startup.
- **No way for `rmp web` to reach a server started on a non-default socket.**
- **No engine-side fix for the sanitised `PROFILE` refusal.** The remedy belongs in
  GoGraph's Bolt failure-code mapping; this release documents the limitation rather than
  working around it.
